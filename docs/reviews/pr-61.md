## 要約

blocker 2件、should 11件、consider 8件。指摘ゼロの観点は無い。

**検査を新設する PR は、その検査自身の抜け道を問われる。** [#54](https://github.com/nashiusagi/slide-design-system/issues/54) が「検査を新設する PR は構造的に上限周回に当たる」と書いた形が、そのまま出た。`inspection/rule-has-bypass` は累計18回で、このリポジトリで最も多い壊れ方だ。

blocker は2つとも**緑が嘘になる**形。(1) 閉じていないコードフェンスが1つあると、そのファイルの以降すべてが無検査になる——しかもフェンスの閉じ忘れは PR #60 で実際に起きている。(2) `extractPaths` がルート直下のファイルと末尾スラッシュのディレクトリを取りこぼし、既存の冒頭欄23件が一度も検査されていない。決定2（正本に実装コードを挙げない）も、ルート直下に書けば回避できる。

should は3系統。(1) **宣言と実装の食い違い**——走査対象・リンク検査の範囲・状態欄の主張が、どれも実装より広いか狭い。(2) **既存 DR の直し残し**——DR-0040 の帰結がまだ「正本」と呼び、DR-0046 の同型が手つかず。(3) **テストの検出力**——ミューテーションで3つの分岐が生き残った。

## blocker

### `code/unclosed-fence-disables-remaining-checks` — 閉じていないコードフェンスが1つあると、そのファイルの以降が丸ごと無検査になる

- **場所**: `scripts/check-decisions.mjs`（`stripCodeBlocks` と、それを呼ぶ3つの検査）
- **指摘した観点**: 検査ルールの実効性 / コード品質（2観点から独立に指摘）
- **累計**: 1回目（新規）
- **何が起きているか**: `stripCodeBlocks` は ``` 行ごとに `inFence` を反転させるだけで、ファイル末尾で `true` のまま残っても報告しない。閉じ忘れ以降の行はすべて空行になり、3つの検査が「何も書かれていない」とみなす。統合時に実際に確かめた——`# x` + 開いたままのフェンス + `DR-9999` + 壊れたリンク、という入力に対し、剥がした結果は `"# x\n\n\n\n"` で、参照の検査は空配列を返した。
- **なぜ問題か**: この PR が捕まえると宣言した `decisions/wrong-dr-citation` と `code/relative-link-wrong-depth` が、上流のフェンス1つで無効化される。**フェンスの閉じ忘れはこのリポジトリで実際に起きている**（PR #60 の `code/unclosed-fence-swallows-trailing-prose`）。DR-0054 の却下理由は「緑が何も保証しない検査は、無い方がましだ」と書いているが、ファイル単位でその状態が作れる。
- **失敗シナリオ**: `docs/` の文書にフェンスの閉じ忘れが入る → その後ろに書いた DR 参照・リンクが何本壊れても `pnpm check` は緑 → DR-0054 の帰結「どれも `main` へ入る前に落ちる」を信じた人が壊れたまま通す。
- **提案**: `stripCodeBlocks` が閉じ忘れも返す形にし、5つ目の検査として載せる。副産物として `code/unclosed-fence-swallows-trailing-prose` そのものも機械で捕まえられる。

### `inspection/rule-has-bypass` — `extractPaths` がルート直下と末尾スラッシュを取りこぼし、既存の冒頭欄23件が無検査のまま

- **場所**: `scripts/check-decisions.mjs`（`extractPaths` の判定と、それを使う冒頭欄の検査）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 19回目
- **何が起きているか**: 判定が「スラッシュを1つ以上含み、末尾がスラッシュでない」ことを要求している。統合時に確かめた——`package.json` / `DESIGN.md` / `design/layouts/` / `eslint.config.js` / `src/runtime/` はすべて空配列を返す。既存 DR の `**正本**:` / `**実装**:` 行のうち、抽出できたのは54件、パスなのに落ちたのが23件。バッククォート無しで書いたパスも全部素通りする（docstring は「素の形も拾う」と書いているのに）。
- **なぜ問題か**: 冒頭欄のパスが実在するかは決定1の4項目目そのもので、3割超が対象外になっている。さらに**決定2（`**正本**:` に実装コードを挙げるのを禁じる）は拡張子判定に依存しており、パスが抽出されなければそこへ到達しない**。この PR は DR-0039 / DR-0040 を直したが、`eslint.config.js` のようにルート直下へ書けば同じ違反が通る。
- **失敗シナリオ**: 冒頭欄に `- **正本**: \`eslint.config.js\`, \`存在しない.md\`` と書く → 4項目すべて緑、終了コード0。実装コードが正本として通り、存在しないファイルも検出されない。
- **提案**: 抽出条件から「スラッシュ必須」を外し、拡張子を持つか末尾がスラッシュかで判定する。ディレクトリを正本に挙げた場合の扱いを DR-0054 へ書く。docstring も実装に合わせる。

### `writing/inaccurate-rationale` — 「この検査は DR へのリンクだけを見る」が、実装の挙動と逆

- **場所**: `docs/decisions/0054-decision-reference-checked-by-machine.md`（決定1・却下理由）、`scripts/check-decisions.mjs`（`checkLinksResolve`）
- **指摘した観点**: 日本語ドキュメント / フェーズスコープ（2観点から独立に指摘）
- **累計**: 18回目
- **何が起きているか**: `checkLinksResolve` は `.md` で終わる相対リンクを**すべて**解決して実在を確かめる。DR 番号による絞り込みは無く、番号の一致判定だけが DR 固有だ。走査対象の相対 `.md` リンク652本のうち102本はリンクテキストに DR 番号を持たないが、それらも実在を要求される。一方 DR-0054 は「この検査は DR へのリンクだけを見る」と書き、それを却下理由（文書全体のリンク検査は別の仕事）にしている。

- **提案**: 決定1と却下理由を実装に合わせる（走査対象の中の相対 `.md` リンクはすべて見る、番号の一致判定は DR リンクに限る）。却下案は「走査対象の外へ広げること」に絞る。

### `inspection/rule-has-bypass`（同一カテゴリのため計上は1回） — フェンスの長さを追っておらず、4文字以上のフェンスで偽陰性と偽陽性の両方を出す
