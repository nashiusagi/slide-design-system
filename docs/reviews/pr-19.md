## blocker

### `code/state-reset-not-recovered` — 同一スライド内で hash が変わると段階数が 0 のまま復帰せず、以降の段階が飛ばされる

- **場所**: `src/runtime/Deck.tsx`:131（`handleHashChange` 内の `setStepCount(0)`）、`src/runtime/Slide.tsx`:56-60
- **指摘した観点**: コード品質
- **累計**: 1回目
- **何が起きているか**: `handleHashChange` はスライドが変わったかどうかに関わらず `setStepCount(0)` する。段階数を Deck へ報告するのは `Slide` の `useLayoutEffect` で、依存は `[reportStepCount, stepCount]`。同じスライドに留まる hash 変更では `Slide` は再マウントされず Slide 側の `stepCount` も変わらないため、この effect は再実行されない。Deck の `stepCount` は 0 に落ちたまま復帰しない。
- **なぜ問題か**: 段階数が 0 だと `goNext` の `position.step < stepCount` が常に偽になり、残りの Fragment を出さずに次のスライドへ飛ぶ。DR-0029 は URL を現在位置の表現とし、measure（DR-0011）も URL を組み立てて全段階を巡回するので、「URL を触った後は段階送りが壊れる」は巡回の前提を壊す。
- **失敗シナリオ**: 再現テストで確認した。(1) `ArrowRight` で 2 枚目へ移動（Fragment 2 個）、(2) `window.location.hash = '#/2/1'`、(3) `ArrowRight` を 1 回。期待は「二つ目」の表示だが、実際は 3 枚目へ遷移し hash は `#/3` になる。段階 2 が丸ごと飛ぶ。
- **提案**: リセットという操作自体をやめる。`Slide` が「どのスライドの段階数か」を添えて報告し、Deck は現在位置と一致する報告だけを採る。そうすれば `goToSlide` と `handleHashChange` の `setStepCount(0)` は両方とも不要になり、古い報告は自動的に無視される。

### `writing/ambiguous-criterion` — DR-0029 の3箇所が二通りに読め、うち1つは実装が経路ごとに分かれている

- **場所**: `docs/decisions/0029-position-in-url-and-explicit-fragment-index.md`:15,17,52、`src/runtime/Deck.tsx`:122-133、`src/runtime/Fragment.tsx`:7
- **指摘した観点**: 日本語ドキュメント、決定記録（複数観点から指摘された）
- **累計**: 4回目
- **何が起きているか**: 3点ある。(1)「書式に合わない hash は無視して先頭のスライドを表示する」が「何もしない」とも「先頭へ移動する」とも読め、実装は読み込み時が後者、`hashchange` 時が前者になっている。(2) `Fragment` の `index` の基数が DR に無い。「段階は 0 始まり」の一文から `index=0` を正当と解釈しうるが、実装は 1 始まり。(3)「範囲を超えるスライド番号は端へ丸める」の外延に `#/0` が入るか不明で、実装は `#/0` を書式違反として扱っている。
- **なぜ問題か**: この DR は measure が URL を組み立てて巡回するための規則で、「規則が曖昧だと巡回する側とランタイムで解釈がずれる」ことを文脈自身が問題として挙げている。(1) は URL と表示が乖離したまま残る不変条件の破れでもある。
- **失敗シナリオ**: measure が巡回中に `#/nowhere` を投げ「先頭に戻ったはず」として次を測る → 実際は直前のスライドが表示されたままで、そのスライドを二重に測り、先頭は一度も測られない。#7 の lint 実装者が `index=0` を正当としてルールを書くと、`#/3` と `#/3/1` の見た目が同じになる。
- **提案**: 決定の箇条書きを経路ごとに分けて書く。`index` は 1 始まりで段階 N では `index <= N` が出ていることを明記する。`#/0` と負値が書式違反であることを明記する。実装側は、表示中に書式外の hash が来たら現在位置で URL を書き戻す。

### `inspection/rule-has-bypass` — キャンバスの `overflow: hidden` により、はみ出しが描画結果に痕跡を残さない

- **場所**: `src/runtime/runtime.css`:21
- **指摘した観点**: 検査ルールの実効性
- **累計**: 3回目
- **何が起きているか**: `.slide-canvas` に `overflow: hidden` が入り、はみ出した要素は画面にもスクリーンショットにも出ない。DR-0011 は `no-overflow` を「キャンバスから要素がはみ出していない」としか書いておらず、レイアウト矩形で比較すること（描画された可視性で比較しないこと）はどこにも書かれていない。
- **なぜ問題か**: `no-overflow` は DR-0011 が本命と呼ぶルールで、プロジェクトの主張そのものを支えている。違反が視覚的に痕跡を残さない状態が作られたので、measure の実装方法しだいで検査が丸ごと空振りする。
- **失敗シナリオ**: `<ul>` に長い項目を積みテキストが y=720 を超える。`overflow: hidden` で描画結果には出ない。#8 の measure がスクリーンショット比較や `checkVisibility()` で実装されると「収まっている」と判定され `no-overflow` が緑で通る。
- **提案**: `overflow: hidden` の直上に「ここでクリップするので `no-overflow` は必ずレイアウト矩形で比較すること。可視性やスクリーンショットで判定すると違反が消える」を残す。

### `inspection/measure-state-unspecified` — 現在スライドの段階数がランタイムから観測できず、measure が段階を取りこぼしても検出できない

- **場所**: `src/runtime/Deck.tsx`:178-180、`docs/decisions/0029-position-in-url-and-explicit-fragment-index.md`（帰結）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 2回目
- **何が起きているか**: `Deck` はスライド数・スライド位置・現在段階を DOM へ出すが、段階数は出さない。DR-0029 の帰結は段階数の導出を measure 側の静的解析に委ね、かつ段階の丸めをしないと決めているので、`#/2/99` は `#/2/99` のまま表示は最終段階と同じになる。
- **なぜ問題か**: DR-0011 は「未実行を pass と区別する」ために実行済みルール ID を残すと決めているが、段階についてはその区別の手段が無い。段階数は Fragment の**最大 index** であって個数ではないので、measure 側が個数で数えると欠番のあるスライドで最終段階に到達しない。
- **失敗シナリオ**: `index={1}` と `index={3}` を持つスライドで measure が段階数を 2 と導出し `#/2` `#/2/1` `#/2/2` だけを巡回する。`index={3}` は一度も描画されないまま `no-overflow` が緑で通る。
- **提案**: `Deck` のルートに `data-step-count` を足し（`data-slide-count` と形が揃う）、DR-0029 の帰結へ「measure は巡回後に `data-step` が `data-step-count` に達したことを確認する」と「段階数は最大 index であり個数ではない」を加える。

#### `inspection/measure-state-unspecified` — 入れ子の Fragment は登録されず、`data-step-count` が実際の段階数より小さく出る

- **場所**: `src/runtime/Fragment.tsx`:45-46、`src/runtime/Slide.tsx`:27-37,52、`docs/decisions/0029-position-in-url-and-explicit-fragment-index.md`:60-62
- **指摘した観点**: 検査ルールの実効性
- **累計**: 2回目（この PR で計上済みのため加算しない）
- **何が起きているか**: `Fragment` は `context.step < index` のとき `return null` で子を描画しない。登録は `useLayoutEffect` なので自分自身は未到達でも登録されるが、**内側の Fragment はマウントすらしないので登録されない**。`Slide` の段階数は登録済み Map の最大値なので、`<Fragment index={1}><Fragment index={2}>…</Fragment></Fragment>` は段階 0 の時点で `data-step-count="1"` になる。一方 DR-0029 の帰結は `index` の連番を lint で検査すると決めており、静的には 1 と 2 が読めるので lint は通る。同じ帰結の中で「段階数 = 最大 index」と「ランタイムが出す `data-step-count`」が同じものを指す前提になっているが、入れ子では一致しない。既存テストに入れ子のケースは無い。`Fragment` の JSDoc は `<li>` や表のセルごと囲めることを設計意図として書いており、入れ子は想定外の書き方ではない。
- **なぜ問題か**: `data-step-count` は「巡回の取りこぼしを measure 側だけの責任にしない」ために足した歯止めそのもので、その入力値が過少になる。帰結は measure が `data-step-count` を**いつ読むか**を規定していないので、巡回開始時に一度読んで計画を立てる実装だと最終確認も通ってしまう。DR-0011 の「最終段階が最も要素が詰まった状態になる」という前提が、まさにその段階で破れる。
- **失敗シナリオ**: `<Fragment index={1}><li>…<Fragment index={2}><span>長いテキスト</span></Fragment></li></Fragment>` を持つスライド。lint は連番として通す。measure は段階 0 で `data-step-count="1"` を読み、`#/2` と `#/2/1` を測って終了。最終確認も `data-step`(1) と読み込み済みの `data-step-count`(1) で成立する。段階 2 で初めて出る `<span>` がキャンバス下端を超えても検出されない。
- **提案**: DR-0029 の帰結へ「`data-step-count` は各段階で読み直し、巡回中に増えたら巡回を延長する」を明記する。より確実には、決定へ「Fragment を入れ子にしない」を足し、lint（#7）の検査に入れ子の検出を含める。ランタイムの段階数が「静的に読める最大 index」と一致することが、この帰結が成り立つ条件になっている。

#### `writing/ambiguous-criterion` — DR-0031 の「端では止まる」と DR-0029 の「達した」が、それぞれ二通りに読める

- **場所**: `docs/decisions/0031-navigation-keys-and-no-history.md`:16-17,25、`src/runtime/Deck.tsx`:93-99、`docs/decisions/0029-position-in-url-and-explicit-fragment-index.md`:24,61

#### `inspection/rule-has-bypass` — 「Fragment は入れ子にしない」を守る lint 提案が、コンポーネント境界を挟むと素通りする

- **場所**: `docs/decisions/0029-position-in-url-and-explicit-fragment-index.md`:19,64、`src/runtime/Fragment.tsx`:37-51、Issue #7 へのコメント
- **指摘した観点**: 検査ルールの実効性
- **累計**: 4回目（この PR で計上済みのため加算しない）
- **何が起きているか**: Issue #7 へ提案した検査方法は「`<Fragment>` の子孫に `<Fragment>` がある場合を invalid にする」という JSX の AST 上の親子関係を見るもの。しかし壊れる条件は字面の入れ子ではなく、**未到達の Fragment 配下ではその内側の Fragment がマウントされず登録もされない**というランタイムの包含関係にある。内側を別コンポーネントへ抽出すれば、外側の `<Fragment>` の子孫に `<Fragment>` タグは一つも現れなくなり、提案どおりの lint は検出できない。それでいてランタイムの壊れ方は直接入れ子と同一に再現する（レビュアーが実際に確認）。
- **なぜ問題か**: DR-0029 は「入れ子にしない」を決定し、その実効性を lint（#7）へ委ねると帰結に書いた。委ねた先の検査粒度が、決定が守ろうとしている不変条件より狭い。抜け道は「子を1つコンポーネントへ切り出す」だけで、意図せず踏む書き方でもある。
- **失敗シナリオ**: `function LaterReveal({children}) { return <Fragment index={2}>{children}</Fragment> }` を定義し、`<Fragment index={1}><li><LaterReveal><span>長いテキスト</span></LaterReveal></li></Fragment>` と書く。段階 0 で `Fragment(index=1)` が `null` を返すので `LaterReveal` はマウントされず、`data-step-count` は 1 のまま。lint は `<Fragment>` の子孫に `<Fragment>` を見つけられず通す。measure が巡回開始時に `data-step-count` を一度読む実装なら、段階 2 で初めて出る `<span>` のはみ出しが検出されない。
- **提案**: DR-0029 の決定へ「コンポーネントへ抽出して間接的に入れ子にすることも含めて禁止する」を明記し、Issue #7 へ間接入れ子の invalid ケースを完了条件として足す。加えて、静的検出には限界があるので Issue #8 側にも「`data-step-count` は各段階で読み直し、増えたら巡回を延長する」を歯止めとして残す。lint 側の禁止だけに頼らない二重構えにする。
