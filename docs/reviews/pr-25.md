## blocker

### `inspection/rule-has-bypass` — contrast の実測が半透明背景の alpha を握り潰し、不透明として扱っていた

- **場所**: `scripts/measure-slides.mjs`（旧 `effectiveBackgroundColor`。祖先の `backgroundColor` を alpha 判定だけで確定させ、合成前の値をそのまま返していた）
- **指摘した観点**: 検査ルールの実効性、コード品質（複数観点から指摘された）
- **累計**: 8回目
- **何が起きているか**: 祖先を遡って背景色を探す処理が、`alpha > 0` を満たした時点でその `rgba(...)` 文字列をそのまま「有効な背景色」として返していた。呼び出し側（`contrastRatioFromCss` 相当）は alpha を使わず RGB 成分だけをコントラスト計算に渡していたため、半透明な背景（例: `rgba(0,0,0,0.08)`）が実際にはほぼ白に近い色として描画されるのに、判定上は不透明な黒として扱われていた。
- **なぜ問題か**: DR-0011 が `contrast` に要求するのは「実測」であり、alpha を無視した合成前の値は実測ではない。ほぼ透明な背景の上に低コントラストな文字を置いても、この実装は「背景は不透明」と誤認して高いコントラスト比を算出し、`contrast` ルールを誤って通過させる。逆方向（半透明な明るいオーバーレイを暗い背景に重ねる通常のデザイン）では誤って fail させる方向にもズレる。
- **失敗シナリオ**: `background-color: rgba(0,0,0,0.08)` を持つ要素の上に白文字（`color: rgb(255,255,255)`）を置く。実際の描画背景は合成後 `rgb(235,235,235)` 相当でコントラスト比は 1.19:1（4.5:1 を大きく割る）だが、旧実装は alpha を無視して不透明な黒 `rgb(0,0,0)` として扱い、21:1 に近い比を返して `contrast` を pass させる。
- **対応**: 祖先の背景レイヤー（`[r,g,b,alpha]` の配列、alpha ≥ 1 で打ち切り）をブラウザ側で集めるだけにし、実際のアルファ合成は Node 側の `compositeBackgroundLayers`（純粋関数）で行うよう分離した。`scripts/measure-slides.test.mjs` に合成の単体テスト（不透明1枚・レイヤー無し・半透明1枚・半透明2枚重ね・不透明で打ち切り）と、`evaluateSlideMeasurements` レベルでの回帰テスト（`rgba(0,0,0,0.08)` を不透明として扱うと見逃す違反を検出できること）を追加した。

### `decisions/consequence-not-followed` — `pnpm measure` を `pnpm check` へ組み込まない判断が、DR-0028 が明示的に却下した代替案と一致するのに、DR として記録されていなかった

- **場所**: README.md（追加した注記のみ）、package.json（`measure` スクリプト追加、`check` の並びは不変）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 4回目
- **何が起きているか**: DR-0028 の「検討した他の選択肢」節は「`pnpm check` に measure まで含めず、measure は別コマンドにする」を挙げ、「Issue を終えてよいかの判定から、本命の検査（`no-overflow`）が外れる」という理由で明示的に却下している。この PR は `pnpm measure` を新設したが `pnpm check` へは組み込んでおらず、その判断の根拠が README の一文にしか無かった。
- **なぜ問題か**: DR-0028 の「決定」節と正面から矛盾する選択を、DR を更新せずに README だけで行うと、DR-0024 が想定する「決定は DR に残す」運用から外れる。次の Issue が進んだとき、`pnpm check` が緑であることを根拠に `no-overflow` が保証されていると誤解される可能性がある。
- **失敗シナリオ**: 該当なし（実行時の失敗ではなく、決定の記録場所の問題）。
- **対応**: [DR-0038](../decisions/0038-defer-measure-in-check.md) を新設し、動機（DR-0028 が却下した代替案とは異なり「本命の検査対象がまだ実データを持たない」という一時的事情であること）、却下した代替案（今すぐ組み込む／App.tsx へ先取りしてスタイルを適用する）、再開条件（`src/App.tsx` が設計契約を実際に消費するようになった Issue で `check` へ組み込む）を記録した。DR-0028 の「関連」行から前方参照を追加した。

## should

### `inspection/rule-id-mapping-incomplete` — measure 側のルールIDと実装の対応検査が、実装済みの3ルール分についても存在しなかった

- **場所**: `scripts/validate-design.mjs`（`checkLintRuleCoverage` は lint のみを対象にしていた）、`design/rules.json` の `$comment`（`deck-body-fidelity` の実装待ちを理由に measure 側の対応検査全体を先送りすると書いていた）
- **指摘した観点**: 検査ルールの実効性、決定記録（DR-0011 の帰結が要求する「実行されたルールIDの集合との差集合チェック」が実装されていない、という角度から。複数観点から指摘された）
- **累計**: 2回目
- **何が起きているか**: `design/rules.json` には measure ルールが4件（`no-overflow` / `min-font-size` / `contrast` / `deck-body-fidelity`）宣言されているが、対応検査は lint 側の `checkLintRuleCoverage` しかなく、measure 側は無かった。理由は「`deck-body-fidelity` が未実装なので、対応検査を入れると常に赤くなる」だった。
- **なぜ問題か**: DR-0011 の帰結は「lint / measure / review の1対1対応を検査する仕組みが要る。lint だけを対象にすると、本命である measure のルールが未実装のまま『全ルール pass』になる」と明記している。今回 measure 実装そのものは追加されたのに、この仕組みが無いままだと、将来 `evaluateSlideMeasurements` から特定ルールの判定が誤って削除されても、`design/rules.json` にはルールが残ったままサイレントに見逃される。
- **失敗シナリオ**: 該当なし（仕組みが無いことそのものの指摘）。
- **対応**: `scripts/validate-design.mjs` に `checkMeasureRuleCoverage(rules, implementedRuleIds, knownUnimplementedRuleIds)` を追加し、`pnpm design:check` へ組み込んだ。`deck-body-fidelity` は `knownUnimplementedRuleIds` へ明示することで missing 扱いから除外しつつ、実装済み3ルールの対応・契約に無いルールの実装・許容リストの陳腐化（実装済みなのに許容リストに残っている）はすべて検査する。実装ルールIDの一覧は `scripts/lib/measure-rules.mjs` に切り出し、`measure-slides.mjs`（Playwright 依存）を `validate-design.mjs`（静的検査）へ直接 import せずに共有した。`design/rules.json` の `$comment` を実態に合わせて更新した。

### `writing/inaccurate-rationale` — `relativeLuminance` の JSDoc が用途を「色域検査」と誤記していた

- **場所**: `scripts/lib/color.mjs`（`relativeLuminance` のJSDoc）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 3回目 — **ルール化候補**
- **何が起きているか**: 新設したJSDocに「DR-0008 の色域検査などが使う」とあったが、実際の呼び出し元は `scripts/validate-design.mjs` の `checkContrast`（コントラスト検査）であり、色域検査は別関数 `isInSrgbGamut` が独立に担っている。
- **なぜ問題か**: 削除・移動の影響範囲をこのコメントを根拠に判断すると、実際に壊れるコントラスト検査を見落として色域検査側だけを直してしまう。
- **失敗シナリオ**: 将来「色域検査だけを別ファイルへ切り出す」際、このJSDocを頼りに `relativeLuminance` / `contrastRatio` も一緒に移動すると `checkContrast` が壊れる。
- **対応**: JSDoc を実際の呼び出し元（`checkContrast`）と根拠DR（DR-0011 / DR-0033）に合わせて書き直した。

## consider

### `code/duplicate-hex-parsing-in-contrast-ratio` — `contrastRatio` が `relativeLuminance` を使わず hex→RGB のパースを重複して書いていた

- **場所**: `scripts/lib/color.mjs`（`contrastRatio`）
- **指摘した観点**: コード品質
- **累計**: 1回目
- **何が起きているか**: `contrastRatioFromRgb` を導入する際、`contrastRatio` が `relativeLuminance(foreground)` / `relativeLuminance(background)` を呼ぶだけだった以前の実装から、`oklchToHex(...).slice(...)` を前景・背景それぞれにインラインで書き直す形に変わっていた。
- **なぜ問題か**: 同じ hex→RGB 変換ロジックが3箇所に並ぶことになり、将来 `oklchToHex` の出力形式が変わったときに同期を崩しやすい。
- **失敗シナリオ**: 該当なし（設計上の重複であり、現在は誤った値を返さない）。
- **対応**: `contrastRatio` を `relativeLuminance` を呼ぶ形に戻した。

### `inspection/rule-coverage-partial` — `::before` / `::after` の疑似要素が判定対象に入らない

- **場所**: `scripts/measure-slides.mjs`（`collectElementRecords` が `querySelectorAll('*')` で対象を列挙）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 3回目 — **ルール化候補**
- **何が起きているか**: 判定対象はDOM要素のみで、`content:` で描画される疑似要素は対象外。現在の `design/layout.css` / `design/components/*.json` は `content:` を使っておらず、今は到達しないコードパス。
- **なぜ問題か**: 将来コンポーネント実装が `::before`/`::after` でテキストを描画するようになった場合、`no-overflow` / `min-font-size` / `contrast` のどれからも検査されず素通りする。
- **失敗シナリオ**: 該当なし（現在のコンポーネント契約では到達しない。将来 `content:` を使うコンポーネントが追加された場合にのみ顕在化する）。
- **対応**: コードコメントで制約を明示した（`scripts/measure-slides.mjs` 冒頭）。実装（疑似要素対応）は現時点でスコープ外と判断し、見送った。

### `phase/completion-criterion-not-verified-e2e` — 完了条件「意図的にはみ出させたスライドで no-overflow が落ちる」が、実ブラウザ経由の統合パスでは自動検証されていない

- **場所**: `scripts/measure-slides.test.mjs`（`evaluateSlideMeasurements` の単体テストのみで検証）
- **指摘した観点**: フェーズスコープ
- **累計**: 1回目
- **何が起きているか**: Issue #8 の完了条件2は、合否判定ロジック（`evaluateSlideMeasurements`）への単体テストでのみ検証されている。実際の `dist/` 配信・URL巡回・DOM収集を含む統合パスを、意図的にはみ出させたスライドで確認する自動テストは無い。
- **なぜ問題か**: 合否判定ロジック自体が正しくても、それを呼び出す統合パス（実DOMからのデータ収集、URL巡回、`.slide-canvas` セレクタの一致など）に不具合があれば、完了条件2は実際には満たされないまま単体テストは緑になりうる。
- **失敗シナリオ**: 該当なし（検証範囲の設計上の指摘）。
- **対応**: 実装中に `--dist` / `--out` オプションを使い、実際に意図的にはみ出す要素を持つ静的フィクスチャに対して `node scripts/measure-slides.mjs` を実際に実行し、`no-overflow` 違反が `measurements.json` に出力されること・収まる場合に `pass: true` になることを手動で確認済み（PR本文に記載）。Playwright を起動する統合テストを `pnpm test` の標準スイートへ常設することは、重い依存（Chromium バイナリ）を通常のテスト実行に持ち込むことになるため見送った。

## ルール化候補

- `writing/inaccurate-rationale` — 通算3回。「新設したコードのコメントが、実際の呼び出し元・使われ方と食い違う」を機械的に検出するのは難しい（意味的な整合性の判断が要る）ため、lint 化は現実的でない。次に出たら review 観点として運用を続けるのが妥当。
- `inspection/rule-coverage-partial` — 通算3回。「判定対象の列挙に穴がある」は個々の穴の性質が毎回異なる（今回は疑似要素、過去は別の対象漏れ）ため、単一の機械ルールに一般化しにくい。ただし `measure` 系の実装レビュー時に「対象の列挙が `querySelectorAll` 等でDOM要素のみに限定されていないか」を確認するチェックリスト項目にする価値はある。
