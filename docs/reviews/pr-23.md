## should

### inspection/rule-has-bypass — `keyMessage` / `title` が空白文字だけで必須チェックを通過する

- **場所**: `design/schemas/deck.schema.json:14`（title の `minLength: 1`）、`design/schemas/deck.schema.json:28`（keyMessage の `minLength: 1`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 6回目
- **何が起きているか**: `title` / `keyMessage` は `minLength: 1` の文字列としてのみ検証されており、`" "`（半角スペース1文字）のような空白のみの値も1文字以上として通ってしまう。実際に `keyMessage: " "` を含む deck.md を `checkDecks` に通すと、エラー0件で返ることを確認した。
- **なぜ問題か**: DR-0017 は `keyMessage` を「AI が判断の軸にする」ための必須項目としている。空白1文字で必須制約を満たせると、「`keyMessage` があれば AI が判断できる材料がある」という前提が崩れ、検査が意味的には機能しない。
- **失敗シナリオ**: `keyMessage: " "` とだけ書いた deck.md をコミットしても `pnpm check` は緑のまま通り、実質空の契約が「妥当な契約」として扱われ続ける。
- **提案**: `pattern: "\\S"` を追加するか、`checkDecks`（または `parseDeck`）側で `trim().length > 0` を確認してから正規化値を渡す。あわせて空白のみの値を invalid ケースとしてテストに追加する。

### code/dead-check-entry — `additionalProperties: false` が正規化コードにより迂回され、構造的に発火しない

- **場所**: `scripts/lib/deck.mjs:47-53`（`parseDeck`）、`scripts/lib/deck.mjs:100-111`（`parseSlide`）、`design/schemas/deck.schema.json:6`・`:17`（`additionalProperties: false`）
- **指摘した観点**: コード品質
- **累計**: 2回目
- **何が起きているか**: `parseDeck` / `parseSlide` は YAML マッピングから既知キー（`title` / `layout` / `keyMessage` / `body`）だけを明示的に取り出してオブジェクトを組み立てる。この結果、`checkDecks` が ajv に渡す正規化済みオブジェクトは、構造上未知のキーを一切持ち得ない。`author: "..."` や `speakerNotes: "..."` を deck.md に足しても、`checkDecks` が受け取る時点で既に消えているため、`additionalProperties: false` は絶対に違反として検出されない。実際に未知キーを含む deck.md で再現し、エラー0件を確認した。
- **なぜ問題か**: `additionalProperties: false` は想定外フィールドのタイプミスなどを検出する意図で書かれた制約（他の3スキーマと同じ形式）だが、実装のせいで死んだ設定になっている。`design/decks/*.md` が「機械が検証できる」ことが本 PR の目的であり、検査基盤の一部が構造的に無効なのは看過できない。
- **失敗シナリオ**: 上記の通り、未知キーを含む deck.md をコミットしても `pnpm design:check` は `ok` を返す。
- **提案**: 正規化時に既知キーだけを取り出すのをやめ、`meta` / `header` を（未知キーも含めて）そのままスキーマへ渡す。妥当性判定をスキーマ側に一本化するという `scripts/lib/deck.mjs` 冒頭のコメントの意図にも合う。

### contract/contract-structure-duplicated — `deck.schema.json` の layout enum が正本の一覧を4箇所目として複製している

- **場所**: `design/schemas/deck.schema.json:25`（新規）。既存の複製先: `design/schemas/layout.schema.json:14`、`design/schemas/component.schema.json:26`、`scripts/validate-design.mjs:36`（`LAYOUT_NAMES`）。正本: `design/layouts/`
- **指摘した観点**: 設計契約との整合
- **累計**: 4回目
- **何が起きているか**: 新規の `deck.schema.json` に `"enum": ["title", "bullets", "statement"]` を直書きした。この一覧は既に3箇所に存在しており、本PRで4箇所目になった。`scripts/validate-design.mjs:28-34` には「`layout.schema.json` と `component.schema.json` の enum は独立に更新が要る」という既存の注記があるが、この注記は `deck.schema.json` を含めて更新されていない。
- **なぜ問題か**: `contract/contract-structure-duplicated` は PR #13・#19・#21 で指摘済みでルール化候補（累計3）に達していたカテゴリ。本PRはこの複製を1箇所増やしながら、対応する注記を更新しておらず、既存問題を悪化させている。
- **失敗シナリオ**: Phase 1.5 で新しい layout（例: `section`）を追加したとき、`scripts/validate-design.mjs` の注記が2スキーマしか挙げていないため `deck.schema.json` の enum 更新が忘れられやすい。その場合、新しい layout を使った deck.md が `checkDecks` に「契約外の layout」として弾かれ続け、契約が実装に追随できていないことに気づきにくい。
- **提案**: `scripts/validate-design.mjs:28-34` の注記に `deck.schema.json` の `slides[].layout` も更新対象として追記する。根本対応としては、許容 layout 一覧を `LAYOUT_NAMES` から導出し、スキーマ側は型チェックのみに留める案もあるが、これは本PRの範囲を超える可能性がある。

### writing/notation-inconsistency — 新規コメントの「Ajv」表記が既存の「ajv」表記と割れている

### writing/notation-inconsistency — 「JSON Schema」「スキーマ」「Schema」が3通り併存している

- **場所**: `scripts/validate-design.mjs:375`（`name: 'deck 契約が構文・Schema を満たす'`）、`scripts/README.md:8`（「deck 契約の構文と Schema」）。比較対象: `scripts/validate-design.mjs:373`（既存、隣接する `'契約が JSON Schema を満たす'`）
- **指摘した観点**: 日本語ドキュメント
- **何が起きているか**: 既存コードは標準名を指すときはフルスペルの「JSON Schema」、具体的なファイルを指すときは片仮名の「スキーマ」を使い分けている。本PRの `checks` 配列の新規要素と `scripts/README.md` は、そのどちらでもない「Schema」単体の表記を持ち込んだ。同じ `checks` 配列内で373行目と375行目が隣接しているため、命名の不統一が特に目立つ。
- **なぜ問題か**: `checks` 配列の `name` は `pnpm design:check` の実行結果としてそのまま人に見える文字列であり、表記が不統一だと今後この配列に項目を足す人が迷う。

### code/redundant-type-only-devdependency — `@types/js-yaml` が js-yaml 自身の同梱型と重複し、実質未使用

- **場所**: `package.json`（`"@types/js-yaml": "^4.0.9"`）、`docs/decisions/0036-js-yaml-for-deck-frontmatter.md:20`
- **指摘した観点**: コード品質
- **何が起きているか**: 追加された `js-yaml@5.4.1` は `dist/js-yaml.d.ts` を自ら同梱し、`exports` の `types` 条件でも同じ宣言を持つ。`tsc --traceResolution` で確認したところ、`scripts/lib/deck.mjs` の `import { load } from 'js-yaml'` は js-yaml 自身の型に解決されており、`@types/js-yaml@4.0.9`（js-yaml **4系**向けの型）はこの import には使われていない。
- **なぜ問題か**: 効果の無い devDependency が増えている。加えて、将来 js-yaml が同梱型の `exports` 宣言を外す・壊すなどした場合、無関係な4系の型へ静かにフォールバックし、実際の5系 API とずれた型情報を出す潜在的なリスクがある。
- **失敗シナリオ**: 現時点では `pnpm typecheck` はエラー無く通る。実害が顕在化するのは、将来 js-yaml が同梱型の `exports` 宣言を外した場合。
- **提案**: `package.json` / `pnpm-lock.yaml` から `@types/js-yaml` を削除し、DR-0036 の該当記述も修正する。

### writing/test-title-ambiguous — 空スライドのテストタイトルが、固定している不変条件を示していない

- **場所**: `scripts/lib/deck.test.mjs:83-89`（「スライドが1枚も無くても空配列にはせず、そのまま返す」）
- **指摘した観点**: 日本語ドキュメント
- **何が起きているか**: このテストは、`---` 区切りが一度も現れない入力に対し `parseDeck(source).slides` が `[{ layout: undefined, keyMessage: undefined }]` になることを検証しているが、タイトルの「そのまま返す」だけでは、これが今後も保証すべき不変条件なのか、実装の副作用を確認しているだけなのかが読み取れない。
- **なぜ問題か**: DR-0016 の帰結に「パーサの挙動変更は契約の変更として扱う」とあり、このテストは契約を固定する記述として機能する。タイトルが不変条件と理由（schema側の `minItems`/必須項目で捕まえるため空チャンクをあえて残す）を示していないと、後で変更する人が「壊してよい実装詳細」と誤読しうる。
- **失敗シナリオ**: 該当なし（テスト説明文の明確さの問題）。
- **提案**: タイトルを「スライド区切りが一度も現れなくても slides は空にならず、`layout`/`keyMessage` が `undefined` の1件を持つ（schema の必須項目違反として検出させるため）」のように、不変条件と理由を明示する形に直す。

### should

#### inspection/rule-has-bypass — `pattern: "\S"` は ECMAScript の空白定義にしか反応せず、ゼロ幅スペースなどの不可視文字だけの値を素通りさせる

- **場所**: `design/schemas/deck.schema.json`（修正前: `title`/`keyMessage`/`body` の `pattern: "\\S"`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 6回目（1周目の `inspection/rule-has-bypass` と同一カテゴリ。1周目時点で既に今回のPR番号が計上済みのため、`docs/review_log.md` の回数はここでは増やさない）
- **何が起きているか**: 1周目で追加した `pattern: "\\S"` は半角スペース等の ECMAScript 空白は正しく弾くが、`\S`/`\s` は Unicode の不可視文字（U+200B ゼロ幅スペース等）を空白として扱わない。`keyMessage: "​"`（ゼロ幅スペース1文字のみ）を含む deck.md が `checkDecks` を通過することを確認した。
- **なぜ問題か**: 1周目の修正意図（「空白のみの文字列を弾く」）を、見た目が空でも別種の不可視文字なら通ってしまう形で部分的にしか達成できていなかった。
- **失敗シナリオ**: `keyMessage` にゼロ幅スペースだけが入った deck.md がコミットされても `pnpm check` は緑のまま通る。
- **対応**: `pattern` を `[^\s\u200B\u200C\u200D\uFEFF]`（ECMAScript空白 + ZWSP/ZWNJ/ZWJ/BOM を除外）に変更。Unicode の不可視文字（Cf カテゴリ）を網羅する意図はなく、実際に遭遇した種類だけを塞ぐものとして description に明記した。ゼロ幅スペースのみの `keyMessage` を invalid ケースとして `scripts/validate-design.test.mjs` に追加した。
