### `contract/source-of-truth-ambiguous` — 「正本」がレイアウトについて2箇所を指し、README の正本表も不完全

- **指摘した観点**: 設計契約との整合 / 日本語ドキュメント（**2観点**）

### `inspection/rule-scope-inconsistent` — `deck-conformance` の守備範囲が DR-0011 と DR-0017 で食い違う

- **場所**: `docs/decisions/0011-lint-and-measure.md`:21, `docs/decisions/0017-key-message-required-body-optional.md`:25, :43
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: DR-0011 は `deck-conformance` を「deck 契約の枚数・順序・layout 割当と一致する」と定義し、lint（静的）系に置いている。DR-0017 は同じルールについて「`body` がある場合は素材の欠落・改変も検出できる」「`body` の有無でモードを切り替える実装になる」と、本文文字列の照合まで含めている。
- **なぜ問題か**: 枚数・順序・layout 割当は JSX の AST から確実に取れるが、本文文字列の一致判定は取れない。ルール ID は1つなので `design/rules.json` に書くときにどちらの定義を採るかが割れる。広い方を採ると「実装したが検出できないケースが大量に残るルール」になり、狭い方を採ると DR-0017 が Phase 2 の根拠として挙げている検出力が実在しないことになる。
- **失敗シナリオ**: 次のどれも ESLint の静的解析では元の文字列を復元できず、素材の改変を検出できない。

  ```jsx
  const points = source.split("\n");
  <BulletList items={points} />

  <Statement>{`${subject}は${verb}`}</Statement>

  {items.map((t) => <BulletList key={t} items={[t]} />)}
  ```

  AI は普通に配列や変数を経由して JSX を書く。意地の悪い回避ではなく既定の書き方で起きる。
- **提案**: `deck-conformance` の定義を DR-0011 の「枚数・順序・layout 割当」に統一し、素材の欠落・改変は**別 ID の measure 系検査**として立てる（レンダリング後の DOM テキストと deck 契約の `body` を照合すれば変数経由もテンプレートリテラルも貫通できる）。あるいは DR-0017 側に「静的に照合できる範囲に限る」と限界を明記する。

### `inspection/rule-has-bypass` — `no-raw-scale` が px 限定で、rem / em / % が素通りする

- **場所**: `docs/decisions/0011-lint-and-measure.md`:18, 関連 `docs/decisions/0018-plain-css-with-tokens.md`:17
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: ルール定義が「生の px（余白・文字サイズ）を書かない」と単位を px に限定している。DR-0018 は Tailwind を却下した理由として「`text-[18px]` などがトークン契約を素通りする抜け道になる」を挙げており、抜け道を塞ぐ意図は明確だが、px 以外の長さ単位にはどの DR も触れていない。
- **なぜ問題か**: 素の CSS を選んだ以上、AI が書く CSS には任意の長さ単位が書ける。px だけを禁じると、**Tailwind を却下してまで塞いだ抜け道が、単位を変えただけで復活する。**
- **失敗シナリオ**:

  ```css
  .slide-bullets { gap: 1.75rem; padding: 3%; }
  .slide-statement { font-size: 1.125rem; margin-block: 2em; }
  ```

  px を一文字も含まないので `no-raw-scale` は通る。1.125rem は 18px 相当なので `min-font-size` も通る。トークン契約が効いていない状態で全検査 pass になる。
- **提案**: ルールの定義を「トークン変数（`--dh-*`）以外の長さリテラルを書かない」に変え、単位ではなく**リテラルか変数参照か**で判定する。例外的に許す値（`0`、`100%`、ヘアラインの `1px` など）があるなら DR に列挙しておく。

### `inspection/rule-id-mapping-incomplete` — ルール ID と実装の対応検査が lint 限定

- **場所**: `docs/decisions/0011-lint-and-measure.md`:54（帰結）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: 帰結に「`design/rules.json` のルール ID と **lint 実装**の1対1対応を検査する仕組みが要る」とある。しかし `rules.json` は lint / measure / review の3系統すべてを持つ。measure（`no-overflow` / `min-font-size` / `contrast`）と review は対応検査の対象外になっている。
- **なぜ問題か**: measure は DR-0011 自身が「本命」と呼ぶ系統。rules.json に ID があるのに Playwright 側に実装が無い、あるいは実装が例外で落ちて無言でスキップされる状態が生まれても、対応検査に引っかからない。**「検査していると思っていたが実はしていなかった」という、この観点で最も重い失敗そのもの。**
- **失敗シナリオ**: `rules.json` に `contrast` を追加し、measure 側の実装を後回しにする。採点はそのルールについて何も報告しないか「fail 0件」として pass 扱いになる。lint 側の対応検査は通るのでどこにも警告が出ない。以後の Run はコントラスト未検査のまま「全ルール pass」として保存される。
- **提案**: 帰結を「lint 実装 / measure 実装 / review チェックリストの1対1対応を検査する」に広げる。あわせて採点結果に「実行されたルール ID の集合」を残し、rules.json との差集合が空でないときは採点を fail にする（**未実行を pass と区別する**）。

### `inspection/measure-state-unspecified` — measure が Fragment の未表示段階を検査対象から落とす

- **場所**: `docs/decisions/0011-lint-and-measure.md`:23-26, `docs/decisions/0004-phase-1-runtime-scope.md`:13
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: DR-0004 で Phase 1 のランタイムに `Fragment`（段階表示）が入るが、URL に同期されるのは「現在位置」とだけ書かれ、段階が含まれるかは規定されていない。DR-0011 の measure ルールも、どの表示状態で測るかを規定していない。
- **なぜ問題か**: 段階表示は**最終段階が最も要素が多く、最も詰まった状態**になる。そこがはみ出しの起きる状態そのものであり、`no-overflow` を本命と位置づけている以上、この状態を測らない実装は中核の検査が空振りすることを意味する。未表示要素が `display: none` の場合、実測矩形は 0 になり、はみ出しもフォントサイズも検出できない。
- **失敗シナリオ**: 1枚のスライドが Fragment を3段階持ち、3段階目まで出すとキャンバス下端を超える。measure が各スライドを初期状態で1回だけ開いて測ると、はみ出しは検出されず pass。実際の発表では3段階目で文字が枠外へ出る。**DR-0011 が「プレゼンで最も多い事故」と呼んでいる事故が、検査を通ったまま起きる。**
- **提案**: DR-0011 の帰結に「measure は各スライドの全 Fragment 段階について測る」を明記する。あわせて DR-0004 の URL 同期に段階を含める（`#/3/2` 形式など）と、Playwright から段階を直接指定して巡回できるので実装も素直になる。

### `code/gitignore-hides-tracked-artifacts` — `.gitignore` の無名パターンが保存 Run の成果物を巻き込む

- **場所**: `.gitignore`:9（`*.log`）、:11-12（`playwright-report/` / `test-results/`）
- **指摘した観点**: コード品質 / 決定記録との整合（**2観点**）
- **累計**: 1回目
- **何が起きているか**: `.gitignore` の各パターンは先頭に `/` が無いため、リポジトリ配下の**任意の深さ**にマッチする。一方 DR-0023 は保存 Run に「生成ソース、`changes.diff`、`events.jsonl`、各種検証ログ、プロンプト全文」が含まれ、それを sanitize / audit のうえ public リポジトリへコミットする方針だと明記している。却下案「public のまま Run を `.gitignore`」は、まさに却下された選択肢。
- **なぜ問題か**: 検査ログを `.log` という名前で、あるいは Playwright の既定の出力先名を Run ディレクトリ配下でそのまま使うと、**コミットしたい成果物が無言で除外される**。エラーも警告も出ない。`audit-public-data.mjs` は文字列検査であり「あるべきファイルが無い」ことは検出しない。

- **提案**: いずれか。
  1. パターンをルートおよび生成物の出る場所へ限定する（`/dist/`、`/playwright-report/` など）
  2. Run 配下だけ無視を打ち消す（`!experiments/**/runs/**`）
  3. Run 保存側で成果物名を `.gitignore` と衝突しない形（`verify.txt` / `measure/`）に固定し、その規約を Issue #10 に明記する

### `writing/ambiguous-criterion` — 「色相差が十分」に判断基準が無い

- **場所**: `docs/decisions/0008-accent-hue-purple.md`:34（関連 :18, :20）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 1回目
- **何が起きているか**: DR-0008 の帰結はコントラストについて「本文 4.5:1、UI 境界とフォーカス 3:1」と数値基準を置くが、色相については「`accent` と `danger` の色相差が十分であることを確認する」とだけ書かれている。
- **なぜ問題か**: この帰結は Issue #4 の作業指示として読まれる。同じ帰結の中でコントラストだけ数値があるため、色相差にも同格の合否基準があるかのように読めるが実際には無い。二通りに割れる: (a) oklch の色相角で一定度数以上離れていることを実測して記録する（数値検査。だが閾値が無いので実行できない）、(b) `danger` と見分けがつけば足りる目視確認（「確認する」が何も担保しない）。

### `writing/term-inconsistency` — 「契約」の呼称と外延が揺れ、検査の系統数も文書間で食い違う

- **場所**: `README.md`:3, :5, :29, :37-45, `docs/decisions/0021-starter-contains-runtime-only.md`:22, :27, :36, `docs/decisions/0011-lint-and-measure.md`:1, :14, :28

- **累計**: 1回目
- **何が起きているか**: 2つの揺れがある。

  **(1) 「契約」の呼称と外延。** 同じ README 内で「デザイン契約」（:3）と「設計契約」（:5）が混在する。より問題なのは DR-0021 の内部で外延が揺れていること: 決定（:22）は「トークン・layout 契約・components・rules・Skill は Harness 条件にのみ渡す」と Skill を並列に挙げるが、理由（:27）は同じ差分を「デザイン契約の有無」と要約し、却下案（:36）は「契約と Skill の有無」と Skill を契約の外に置く。

  **(2) 検査の系統数。** DR-0011 はタイトル・決定ともに「lint と measure の2系統」とし `review` を系統の外に置くが、README の「検査」表は `review` を lint / measure と同じ列に並べ、`rules.json` の説明も「lint / measure / review」と3つを挙げる。
- **なぜ問題か**: (1) は DR-0021 の帰結「baseline のワークスペースに契約や Skill が混入していないことを検査する仕組みを持つ」の**検査対象が決まらない**。契約が Skill を含むなら対象は1つ、含まないなら2種類を別々に列挙する必要がある。(2) は「検査を通過した Run」という表現が review 未実施を含むかどうかで割れ、比較表の母数定義が揺れる。
- **失敗シナリオ**: 該当なし（設計上の問題であり実行時の失敗ではない）。
- **提案**: (1) 呼称を「設計契約」に固定し、DR-0021 の決定文に「本 DR で『契約』と呼ぶのは DR-0009 の5層を指し、Agent Skill は含まない」の一文を置く。(2) DR-0011 の決定文に「`review` も `rules.json` の `method` の1つだが、自動判定を持たないため本 DR の『2系統』には数えない」を足すか、README の表見出しを「系統」から「method」に変える。

### `contract/contract-structure-duplicated` — 正本を宣言した DR が、その正本の中身を一覧として抱えている

### `inspection/measure-viewport-unspecified` — measure の測定条件（ビューポート / スケール倍率）が未規定

- **場所**: `docs/decisions/0011-lint-and-measure.md`:23-24, :53, `docs/decisions/0004-phase-1-runtime-scope.md`:18
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: measure は `dist/` に対して Playwright で実行すると決まっているが、どのビューポートサイズで開くかは書かれていない。ランタイムはキャンバスをビューポートに合わせてスケーリングするため、ビューポートが変わればスケール倍率が変わり、実測矩形の値も変わる。
- **なぜ問題か**: DR-0020 は「採点は何度でも再実行できる」「保存済み Run へ遡ってルールの効き目を確認できる」ことを実験装置の価値の根拠にしている。測定条件が固定されていないと、同じ Run を別環境で採点し直したときに結果が変わりうるため、その根拠が崩れる。
- **失敗シナリオ**: CI と手元でスケール倍率が 1.0 と 0.83 になる。キャンバス下端を 0.5px 超えるだけの要素が、片方では fail、もう片方では pass になる。
- **提案**: DR-0011 の帰結に「measure はビューポートを 1280x720（スケール倍率 1.0）に固定して実行する」と書く。判定はキャンバス座標系で行い、許容誤差を `rules.json` 側の値として持つところまで決めておくと実装時に解釈が割れない。

### `decisions/undocumented-decision` — 開発運用の方針が PR 説明にしか書かれていない

- **場所**: PR #13 の説明本文。`docs/decisions/` に対応する DR は無い
- **指摘した観点**: 決定記録との整合
- **累計**: 1回目
- **何が起きているか**: PR 説明は「コードより先に置いている。DR が以降の Issue の根拠になり、Issue がブランチの単位になるためで、逆順だと実装中に『なぜこうしたか』が失われて方針がぶれる」と、理由つきで開発運用の方針を述べている。DR にはこの決定が無い。
- **なぜ問題か**: PR 説明はマージ後に読まれないが DR は残る。この方針には実在の代替案がある（実装しながら DR を起こす、Issue を跨ぐブランチを切る、DR を Phase 単位でまとめる）ため「後から理由を聞かれうる決定」に該当する。DR-0004 / DR-0010 / DR-0023 は帰結で「Issue を起こす」と書いており、Issue 粒度の前提が複数の DR の帰結に依存しているのに、その前提自体が記録されていない。
