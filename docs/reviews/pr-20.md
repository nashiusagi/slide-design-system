## blocker

### `code/check-false-negative-on-empty-output` — `--check` は `design/theme.css` が空ファイルのとき乖離を見逃して成功する

- **場所**: `scripts/generate-theme.mjs:183,186,190`
- **指摘した観点**: 検査ルールの実効性 / コード品質（2観点）
- **累計**: 1回目
- **何が起きているか**: `current` を `''` で初期化し、読み込み失敗時だけ「theme.css が無い」を積む。突き合わせは `if (current !== '' && current !== theme)` で行っており、空文字を「読めなかった」ことの番兵としても使っている。ファイルが存在して中身が空のときは読み込みに成功して `current === ''` となり、比較そのものが飛ぶ。
- **なぜ問題か**: この `--check` は DR-0033 の決定「生成し直した結果と現物を突き合わせて、違えば落とす」の唯一の実装であり、`pnpm check` の2段目に載っている。ここが偽陰性を出すと、`--dh-*` が1つも定義されていない CSS のままパイプライン全体が緑になる。検査基盤としては致命的な向き（失敗を成功と報告する側）に倒れている。Issue #4 の完了条件「`pnpm theme:check` が乖離を検出できる」も、この形では満たされていない。
- **失敗シナリオ**: スクラッチ領域へ `design/` `scripts/` `src/` を複製し、`: > design/theme.css` で 0 バイトに切り詰めてから `node scripts/generate-theme.mjs --check` を実行 → `design/theme.css と実測値は design/tokens.json と一致している。` を出力して終了コード 0（統合時に再現を確認）。同じ状態でファイルを削除した場合は正しく終了コード 1 になる。生成が途中で落ちる、リベースやマージで空ファイルが残る、といった経路で到達する。
- **提案**: 「読めたか」と「中身」を分ける。`let current = null` とし、`catch` では `null` のままにして、`if (current === null) { drifts.push('design/theme.css が無い。') } else if (current !== theme) { drifts.push('食い違っている。') }` とする。あわせて、この形を守る回帰テストを `generate-theme.test.mjs` へ置く（下の `inspection/invalid-case-untested` と同じ）。

### `contract/value-outside-source-of-truth` — コントラスト閾値と用途対応表が、正本と決めた `design/rules.json` ではなくスクリプト内にある

- **場所**: `scripts/validate-design.mjs:29-53`（`CONTRAST_REQUIREMENTS`）
- **指摘した観点**: 設計契約との整合 / 決定記録との整合（2観点）
- **累計**: 2回目
- **何が起きているか**: 閾値（4.5 / 3）と「どの色ペアがどの水準を要求されるか」の対応が、スクリプトにリテラルで入っている。`design/rules.json` はまだ存在しない。DR-0008 の帰結は「コントラストの基準は `design/rules.json` の `contrast` を正本とする」、DR-0011 は `**正本**: design/rules.json` と書いており、本 PR が追加した DR-0033 自身も理由節で「判定は `design/rules.json` の閾値が持つ（DR-0011）」と書いている。撤去の約束はコードコメントの「#7 / #8 で読み込みへ置き換えて消すこと」1箇所だけにある。
- **なぜ問題か**: 契約がまだ無い段階で暫定を持つこと自体は許容できるが、担保がコードコメントしか無い。マージ後にコメントは読まれない。#7 / #8 で `rules.json` に `contrast` が入った時点で同じ値が二箇所になり、片方だけ閾値を上げても `pnpm check` は緑を返す。しかもこの静的コントラスト検査は DR-0011 のルールID体系（`contrast` は measure 系）の外にあるため、「ルールIDと実装の1対1対応」の検査でも捕まらない。
- **失敗シナリオ**: #7 / #8 で `design/rules.json` に `contrast: { body: 4.5, ui: 3 }` を置き、後に本文基準を 7:1 へ上げる。`CONTRAST_REQUIREMENTS` は 4.5 のままなので `design:validate` は 4.5 で通す。measure 側だけが 7 で判定し、「契約は 7 なのに静的検査は 4.5 で合格を出す」状態になる。

### `inspection/rule-coverage-partial` — コントラスト検査は手書きの列挙で、現在の値ですでに基準を割っている組み合わせを見逃している

- **場所**: `scripts/validate-design.mjs:36-53`、`design/tokens.json:112`（`accentSoft|success: 4.45`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: `CONTRAST_REQUIREMENTS` は14行の固定表で、背景として現れるのは `background` / `surface` / `accentSoft` の3つ。前景ごとの網羅がばらばらで、`textMuted` と `border` は `accentSoft` が無く、`danger` / `warning` / `success` は `background` に対してしか検査されない。一方 `$measured.contrast` は45ペア全部を記録しており、`accentSoft|success` は **4.45:1** と、状態色に課している 4.5:1 を既に割っている。この組み合わせは表に無いので `node scripts/validate-design.mjs` は `ok コントラストが水準を満たす` を返す。
- **なぜ問題か**: 全ペアを実測して記録しておきながら、判定は列挙した14ペアにしか掛からない。記録が並んでいることで「全ペアが検証済み」に見えるが、実際には検査されていない値が混ざっている。DR-0033 が警戒した「古い実測値は『検証済み』という誤った合図を出す」と同じ形の誤信号が、網羅していない判定表から生まれている。
- **失敗シナリオ**: `color.danger` を `oklch(0.59 0.2 27)` に変えると、`background` に対して 4.53:1 なので状態色 4.5:1 の行を通り、スキーマ・色域・キャンバスも通って `validate-design.mjs` は終了コード 0。だが `surface` 上では 4.16:1、`accentSoft` 上では 3.90:1 でいずれも本文水準を割る。`pnpm theme:generate` を掛ければ `$measured` も追随するので `theme:check` も緑になり、`pnpm check` 全体が通る。
- **提案**: (a) 表を「前景の役割 × 許可された背景の集合」で持ち、背景側を展開して前景ごとの取りこぼしを構造的に無くす。(b) 少なくとも `danger` / `warning` / `success` / `textMuted` / `border` に `surface` と `accentSoft` の行を足す。(c) `accentSoft|success` が現状 4.45:1 である事実の扱い（`success` の L を下げる、あるいは `accentSoft` 上に状態色を置かないと契約で明示する）を決める。この表は `rules.json` へ移す前提なので、移すときに網羅の形も一緒に決めるのが自然。

- **場所**: `scripts/generate-theme.test.mjs`（`--check` のテストが無い）、`scripts/validate-design.mjs`（対応するテストファイルが存在しない）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目
- **何が起きているか**: `generate-theme.test.mjs` が触るのは `flatten` と `measure` だけで、`--check` の突き合わせロジックにテストは無い。`validate-design.mjs` にはテストファイル自体が無く、`checkSchemas` / `checkGamut` / `checkContrast` / `checkCanvasMatchesRuntime` のいずれも「違反を入れたら NG になる」ことを確認していない。
- **なぜ問題か**: 上の blocker（空 theme.css の素通り）と `rule-coverage-partial`（表の穴）は、どちらも invalid ケースのテストがあれば書いた時点で気付ける類のもの。判定側にテストが無ければ「何も検出しないルール」でも緑になる。Issue #4 の完了条件が乖離検出を「意図的に壊して確認」という人手の手順に委ねているのも、この状態と対になっている。
- **失敗シナリオ**: `checkCanvasMatchesRuntime` の正規表現が `canvas.ts` の書き方変更で永久に `null` を返すようになる、あるいは `CONTRAST_REQUIREMENTS` の `minimum` を誤って `0` にする、といった変更が入っても、テストは全緑のまま通る。

### `code/test-misses-core-path` — color.mjs の彩度のある経路が、テストで固定されていない

- **場所**: `scripts/lib/color.test.mjs:23-77`
- **指摘した観点**: コード品質
- **累計**: 1回目
- **何が起きているか**: `oklchToHex` のテストは白・黒・無彩色のみ、`relativeLuminance` と `contrastRatio` のテストも入力が全て C=0 の無彩色。彩度のある色で期待 hex を固定したアサーションが1つも無い。行列の彩度側を通る検証は `isInSrgbGamut` の true/false 2件だけで、これは境界の粗い符号判定にすぎない。
- **なぜ問題か**: このモジュールの存在理由は oklch→sRGB 変換そのもの。その中核が回帰テストで固定されていない。`theme:check` は生成物との突き合わせなので保険にはなるが、係数を変えた人が自然な手順（`pnpm theme:generate` で生成し直す）を踏むと生成物側も一緒に更新され、`pnpm check` は緑のまま通る。最後の防波堤が無い。
- **失敗シナリオ**: `oklchToLinearRgb` の戻り値の R 行と B 行を入れ替える（アクセントの紫が青緑へ転ぶ改変）と、`scripts/lib/color.test.mjs` の11件が**すべて PASS** する（統合時に実行して確認）。無彩色では3行の係数和が等しいため、無彩色だけのテストはこの入れ替えを検出できない。
- **提案**: 彩度のある色1〜2点の期待 hex を固定する。現在の実装で `accent` は `#791fba`、`danger` は `#c51e21`、`success` は `#1d7d3e` になることを確認済みなので、これらを `oklchToHex` のテストへ直接書けば足りる。あわせて彩度のある色でのコントラスト比を1件固定すると `relativeLuminance` 側も締まる。

### `writing/contradictory-instruction` — 契約検証の実行口が `design:check` と `design:validate` の二つの名前で書かれている / `$` キーの所有権が全称で書かれている

- **場所**: `README.md:29,37`、`docs/decisions/0032-ajv-for-contract-validation.md:14`（対 `docs/decisions/0009-five-layer-contract.md:48`、`docs/decisions/0030-slide-class-derived-from-layout.md:18`）、`docs/decisions/0033-derived-values-are-generated-and-checked.md:19`（対 `design/tokens.json:3`）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 2回目
- **何が起きているか**: 2箇所ある。(1) 既存の DR は契約検証の口を `pnpm design:check` と名指ししている（DR-0009 帰結、DR-0030）。この PR は同じ役割の口を `design:validate` として導入したが、DR-0032 も既存 DR も名前が変わったことに触れていない。(2) DR-0033 の決定は「`$` で始まるキーは生成側が所有し、人は編集しない」と全称で書いているが、`design/tokens.json` は「`$measured` **だけは** 人が編集しない」と書いており、`$schema` と各階層の `$comment` は明らかに人が書いた説明文である。
- **なぜ問題か**: DR は AI と人の判断の根拠になる。(1) では、DR-0030 が名指しする #5 を担当する側が存在しない `design:check` を探し、二つ目の口を新設する経路が開く。契約検証の口が2本になると DR-0028 の「実行口の一本化」が崩れる。(2) では、DR-0033 をそのまま読むと `$comment` は生成器の所有物なので手で直してはいけないと読め、tokens.json を読むと `$measured` 以外は自由に書けると読める。同じ状況に二通りの指示がある。
- **失敗シナリオ**: (1) Issue #5 を担当する AI が DR-0030 を読み、`package.json` に `design:check` が無いのを見て新規に追加し、`layout.css` の照合をそちらへ書く。`design:validate` と並立し、どちらが正本かが決まらなくなる。(2) トークンを追加する Issue で AI が DR-0033 に従い、意味の説明（`$comment`）を書き足さずにキーだけ足す。`flatten` は `$` を素通りし、スキーマも `$comment` を必須にしていないため `pnpm check` は緑のまま通る。
- **提案**: (1) スクリプト名を `design:check` に戻して DR-0009 / DR-0030 と一致させるか、`design:validate` を採るなら DR-0032 に「DR-0009 が `pnpm design:check` と書いた口は `design:validate` として実装する」と明記し、DR-0009 / DR-0030 も追随させる。(2) DR-0033 の該当文を「`$measured` は生成側が所有し、人は編集しない。`$schema` / `$comment` は人が書く説明であり生成器は保存する」に限定する。

### `writing/term-inconsistency` — 「実測」が「トークンから計算した値」と「ビルド出力を測った値」の両方を指している

- **場所**: `README.md:33`、`scripts/README.md:9`、`scripts/lib/color.mjs:2`、`scripts/generate-theme.mjs:11,73`、`design/tokens.json:69`、`design/schemas/tokens.schema.json:145`
- **指摘した観点**: 日本語ドキュメント
- **累計**: 5回目
- **何が起きているか**: このリポジトリで「実測」は measure 系統の固有語として使われてきた（DR-0011「measure（Playwright / ビルド出力に対して実測）」、DR-0028 帰結「実測系は build より後段」）。この PR は、トークンの数値から純粋計算で求めたコントラスト比・色相差にも一貫して「実測」「実測値」を当てている。同じ PR の `README.md:37` は「measure はビルド出力に対して実測するため `build` より後段へ置く」と書きつつ、33行目では `theme:check`（先頭段）が「コントラスト実測値」を見ると書いている。
- **なぜ問題か**: 「実測」は検査系統を分ける定義語である。DR-0028 帰結の「lint 系は lint 段、実測系は build より後段」に従うと、この PR で足した「コントラストの実測」は build より後段に置くべきものと読める。実際は先頭段にあり、規則がそのままでは適用できない。揺れの源は DR-0008 の「コントラストを実測して」にあるが、この PR で語がスクリプト・スキーマ・README へ広がったことで、後続の検査を足すときの配置判断が割れる状態になった。
- **失敗シナリオ**: #7 / #8 でコントラスト閾値を実装するとき、DR-0028 の「実測系は build より後段」に従い、トークン値から計算するだけの判定を Playwright 側へ置いてしまう。ビルドとブラウザ起動が要らない検査が最後段に来て、速く落ちる順序という DR-0028 の理由が失われる。
- **提案**: トークンから計算する値には別語を当てる（DR-0033 のタイトルが既に使っている「導かれる値」に揃えるのが自然）。「実測 / measure」はビルド出力に対する測定に限る。DR-0008 の「実測して記録する」も同じ語へ寄せる。

### `writing/ambiguous-criterion` — `space` の「4px 刻みの等比寄りスケール」が実際の値と一致せず、追加時の基準にならない

- **場所**: `design/tokens.json:18`
- **指摘した観点**: 日本語ドキュメント
- **累計**: 5回目
- **何が起きているか**: `space` の値は 4, 8, 12, 16, 24, 32, 48, 64, 96。「4px 刻み」は (a)「隣り合う値の差が 4px」とも (b)「すべて 4 の倍数」とも読めるが、16→24→32 の差は 8、48→64 は 16 なので (a) は成立しない。「等比寄り」も比が一定でない（2, 1.5, 1.33, 1.5, 1.33, 1.5, 1.5）ため、どちらの読み方でも次の値を決められない。
- **なぜ問題か**: この `$comment` は「レイアウトが使う余白はここからしか取らない（DR-0018 / no-raw-scale）」と対になっており、スケールに値を足すときの唯一の基準として置かれている。基準が値と食い違っていると、AI は「4px 刻み」を根拠に 20px や 28px を足してよいと判断でき、段階を粗く保つという意図が守られない。
- **失敗シナリオ**: 余白が足りない場面で AI が `space` に `"md2": 20` を足す。(a) の読みでは規則に合致し、スキーマは `additionalProperties: false` で弾くものの、弾かれた側は「コメント通りなのになぜ落ちるか」を判断できず、スキーマの `required` 側を書き換える方向へ流れる。
- **提案**: 実際の構成を書く。例:「4 の倍数のみ。小さい側は 4px 刻み（4/8/12/16）、大きい側はおよそ 1.5 倍ずつ（24/32/48/64/96）。値の追加は契約変更として扱う」。

### `decisions/undocumented-decision` — コントラストの測り方そのものが、どの DR にも記録されていない

- **場所**: `scripts/lib/color.mjs:66-120`、`scripts/validate-design.mjs:74-86`（`checkGamut`）、`design/tokens.json`（`color.$comment` / `$measured.$comment`）
- **指摘した観点**: 決定記録との整合
- **累計**: 5回目
- **何が起きているか**: この PR は「コントラストの指標は WCAG 2.1 の相対輝度」「輝度は 8bit へ丸めた sRGB 値から求める」「比は小数第2位で切り捨てる」「トークンの色は sRGB 色域内に限り、外れたら落とす」という4つの判断を実装している。理由はコード内コメントと `$comment` にあるが、`docs/decisions/` 配下には `sRGB` `色域` `WCAG` `切り捨て` のいずれの語も出てこない。DR-0033 は「導かれる値は生成して突き合わせる」という手順だけを決めており、何をどう測るかには触れていない。
- **なぜ問題か**: いずれも他の選択肢が実在する判断である（APCA / WCAG 3 ドラフト、oklch の L で判定、丸めか切り捨てか、Display-P3 を許すか）。特に sRGB 色域への限定は、トークン契約が将来持てる色の範囲を縛る制約であり、DR に無いまま `checkGamut` が落とすと、色を広げたい人には根拠の見えない拒否になる。「切り捨て」の選択（4.495 を 4.5 に上げない）は合否そのものを動かす。
- **失敗シナリオ**: 後日 P3 のアクセント色を試そうとした人が `checkGamut` で落とされ、根拠を探しても DR に無いため、コメントを消して検査を緩める方向に倒れる。あるいは APCA へ移す議論が起きたとき、WCAG 2.1 を選んだ理由が残っておらず、同じ検討をやり直すことになる。
- **提案**: DR-0033 に節を足すか、独立した DR（例:「コントラストの指標は WCAG 2.1 とし、sRGB 8bit 丸め後の値で測る」）を1本立てる。値そのもの（4.5 など）は書かず、指標の選択と却下した選択肢、および sRGB 色域限定の理由だけを書けば DR-0024 の方針に反しない。索引は「検査」節が妥当。
