## blocker

### `inspection/rule-has-bypass` — 大文字表記の `VAR(` / `16PX` が素通りする。宣言した `alternate-notation` 軸の内側

- **場所**: `packages/eslint-plugin-slide/src/lib/jsx-style.mjs`:184（`expandVarFallbacks` の `/\bvar\(/`）、:222（`varReferenceNames` の `/\bvar\(\s*(--[\w-]+)/g`）、`packages/eslint-plugin-slide/src/rules/no-raw-scale.mjs`:42（`NUMERIC_LENGTH`）。いずれも本 PR の新規・変更コード
- **指摘した観点**: 検査ルールの実効性
- **累計**: 14回目
- **何が起きているか**: 実測で確認した。

  ```
  PASS                     const el = <div style={{ color: "VAR(--my-red)" }} />
  CAUGHT nonTokenVariable  const el = <div style={{ color: "var(--my-red)" }} />
  PASS                     const el = <div style={{ padding: "16PX" }} />
  CAUGHT rawScale          const el = <div style={{ padding: "16px" }} />
  ```

  CSS の関数名と単位は ASCII 大小を区別しないため、`VAR(--my-red)` も `16PX` も実際に描画される。本 PR が新設した `varReferenceNames` / `expandVarFallbacks` は `i` フラグを持たず、`NUMERIC_LENGTH` も単位を小文字でしか受けない。
- **なぜ問題か**: `design/rules.json` は両ルールに `bypassAxes: ["alternate-notation", ...]` を宣言しており、その軸は「同じ値を別の記法で書けるなら、どの記法でも同じ結果にする」と定義されている。`no-raw-color.bypass.mjs` は hex について「大文字の hex。色の表記は大小を区別しない」という事例を持っており、書き手はこの軸で大小の違いを認識している。それなのに同じ理屈が `var(` と単位には適用されていない。**軸を宣言し、事例で埋め、検査が緑になり、それでもその軸の抜け道が残っている** — DR-0044 が塞ごうとした形そのものが、DR-0044 を導入する PR の中で再現している。
- **失敗シナリオ**: 生成されたスライドが `<div style={{ color: "VAR(--my-red)" }} />` を含む。契約外のカスタムプロパティを参照しているのに `pnpm lint` は無言で通る。`<div style={{ padding: "16PX" }} />` も同様に、生の長さリテラルがトークンを経由せずに通る。どちらもブラウザでは通常どおり描画される。
- **提案**: `expandVarFallbacks` の `/\bvar\(/` と `varReferenceNames` の正規表現に `i` を足す。`NUMERIC_LENGTH` の単位部分も `i` を付けるか、比較前に単位を小文字化する。あわせて両フィクスチャの `alternate-notation` に「大文字の `VAR(`」「大文字の単位」の事例を足し、回帰として固定する。

### `code/dead-check-entry` — `descriptionOf` の import 時 throw で検査が全滅し、`checkLintRuleCoverage` の「実装はあるが正本に無い」分岐が到達不能になった

- **場所**: `packages/eslint-plugin-slide/src/lib/design-contracts.mjs`:71（未登録IDで throw）、`packages/eslint-plugin-slide/src/rules/no-raw-color.mjs`:42（および他4ルールの同じ箇所）、`scripts/validate-design.mjs`:23, 251-255
- **指摘した観点**: コード品質
- **累計**: 3回目（**ルール化候補へ昇格**）
- **何が起きているか**: 各ルールの `meta.docs.description` が `descriptionOf('<id>')` になり、これはモジュール評価時に実行される。`descriptionOf` は `design/rules.json` に該当IDが無いと `Error` を投げる。`scripts/validate-design.mjs` は冒頭で `slidePlugin` を静的 import するため、この throw は `main()` より前に起きる。実測で確認した — `design/rules.json` から `no-raw-color` のエントリだけを消して `node scripts/validate-design.mjs` を走らせると、`ok`/`NG` の行が**1行も出ないまま** `Error: design/rules.json に 'no-raw-color' が無い` で終了する。
- **なぜ問題か**: `checkLintRuleCoverage` の `extra`（「ルール '<id>' を実装しているが、design/rules.json に method: "lint" として無い」）は、まさにその状態を報告するために置かれている。今は同じ状態が import 時例外になるので、この分岐に到達する経路が無い。加えて、契約と実装がずれた瞬間に `pnpm design:check` は「どこが壊れているかの一覧」を一切出さずに死ぬ。検査基盤としての退行であり、`code/parse-error-crashes-validator`（PR #39）で一度直した形の再発でもある。
- **失敗シナリオ**: 上記のとおり実測済み。同じ理由で `eslint.config.js` 経由の lint も起動しない。
- **提案**: (a) `descriptionOf` を遅延評価にする（`meta.docs.description` を getter にする、または未登録時は throw せず空文字を返し `checkLintRuleDescriptionsMatch` 側で不一致として報告させる）。(b) `validate-design.mjs` 側で `slidePlugin` を動的 import し、失敗を検査結果の1件として並べる（`loadBypassFixtures` が読み込み失敗を例外にせず `error` として返しているのと同じ扱い）。**(b) が既存の設計と揃う。**

## should

### `inspection/bypass-case-trivially-satisfiable` — `expect: 'ok'` の事例に下限が無く、中身が空でも軸と除外を「埋めた」ことになる

- **場所**: `scripts/validate-design.mjs`:425-436（`hasExpectedReport` の適用が `expect === 'violation'` に限られる）、`scripts/measure-bypass.test.mjs`:59-72、`packages/eslint-plugin-slide/src/rules/bypass.test.mjs`:65-73
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目（新規）
- **何が起きているか**: `checkBypassFixtureCoverage` は `expect: 'violation'` の事例にだけ「どの報告になるか」（lint: `messageId`、measure: `records`）を要求する。`expect: 'ok'` の事例には、中身が検査対象を通っていることを要求する条件が一つも無い。実測で確認した — `{ exclusion: 'keyword-color', name: 'b', code: '', expect: 'ok' }`（コードが空文字）を渡しても `checkBypassFixtureCoverage` は `[]`（問題なし）を返す。measure 側も `records: () => []` で同様に通る。
- **なぜ問題か**: `scopeExclusions` は「意図的に見ない領域」の正本で、その一つひとつが本当に見ないままであることを固定するのが事例の役目なのに、その固定が効かない。違反側は runner（RuleTester の invalid / `expect(violations.length).toBeGreaterThan(0)`）が実質の下限になっているので、穴は ok 側だけに開いている。
- **失敗シナリオ**: `contrast` の除外 `no-direct-text` を消して「直接テキストを持たない要素も判定する」実装へ変えても、除外の事例が `records: () => []` であれば緑のまま通る。
- **提案**: ok 側にも下限を課す。measure は `records(context)` が空配列でないことを runner で検査する。lint は `code` が非空文字列であることを `checkBypassFixtureCoverage` で検査する。より強くするなら、除外の事例は「除外を外したら違反になる」ことまで固定する。

### `contract/requirement-contradicts-review-method` — スキーマが `method: "review"` のルールにも `bypassAxes` とフィクスチャを必須にし、「review は人が判断する」と衝突する

- **場所**: `design/schemas/rules.schema.json`:18（`required` に `bypassAxes`）、:31-38（`minItems: 1`）、`scripts/lib/bypass-fixtures.mjs`:46（lint 以外をすべて `measure-bypass/` へ写す）、`scripts/validate-design.mjs`:887（method で絞らない）、`README.md`:79、`docs/decisions/0011-lint-and-measure.md`:29
- **指摘した観点**: 設計契約との整合 / 決定記録（DR）との整合（**2観点から独立に挙がった**）
- **累計**: 1回目（新規）
- **何が起きているか**: スキーマの `method` enum は `lint | measure | review` のままで、新しい `required` は**すべての**ルールに `bypassAxes`（1つ以上）と `scopeExclusions` を要求する。`checkBypassFixtureCoverage` も method で絞らない。免除は `UNIMPLEMENTED_RULE_IDS` の1件だけ。一方 DR-0011:29 は「`review` も `method` の一つだが、自動判定を持たない」と述べ、README:79 も「`review` とされた項目は自動合否にせず、画面を見て人が判断する」と書く。現在 `design/rules.json` に review ルールが無いため今日は落ちない。
- **なぜ問題か**: 契約どうしの衝突であり、かつ「review にフィクスチャを要求するか」という実在する判断が DR に無いまま実装へ埋まっている。DR-0044 の適用範囲は `eslint.config.js` の汎用ルールを対象外とすることしか述べていない。
- **失敗シナリオ**: DR-0011 が予定する review ルール（「1枚1メッセージか」等）を足すと、スキーマが `bypassAxes` 欠落で落ちる → 軸を宣言すると `checkBypassFixtureCoverage` が `scripts/lib/measure-bypass/<id>.bypass.mjs` を要求する → 置いても `measure-bypass.test.mjs` は `method === 'measure'` しか実行しないので、**宣言だけの飾りになる**（DR-0044 が「理由」節で塞ごうとした形そのもの）。
- **提案**: `checkBypassFixtureCoverage` と `fixturePathFor` を `method !== 'review'` に限定し、スキーマも `if/then` で review のときは `bypassAxes` を不要にする。あわせて DR-0044 の帰結に「review は対象外（自動判定を持たないため）」を1行加える。

### `inspection/rule-scope-inconsistent` — 守備範囲の宣言に、正本の description が約束した範囲と DR-0037 が決めた除外の両方が入っていない

- **場所**: `design/rules.json`:9, 11-15（no-raw-color）、:21, 23-27（no-raw-scale）、`packages/eslint-plugin-slide/src/rules/no-raw-color.mjs`:55（`'JSXAttribute[name.name="style"]'`）、`docs/decisions/0037-eslint-plugin-slide-rule-scope.md`:22
- **指摘した観点**: 設計契約との整合 / 決定記録（DR）との整合（**2観点から独立に挙がった**）
- **累計**: 5回目
- **何が起きているか**: 2つある。(1) description は「JSX の style・**色系 props**」「JSX の style・**長さ系 props**」と述べるが、実装は `JSXAttribute[name.name="style"]` だけを訪問し、`<Foo color="#ff0000" />` のような属性は一切見ない。`scopeExclusions` にもその項目が無い。(2) DR-0037:22 は「CSS ファイル（`design/layout.css` 等）は対象にしない」と明示的に決定しているが、両ルールの `scopeExclusions` に CSS ファイルの除外が無い。
- **なぜ問題か**: DR-0044 が新たに置いた規範は「契約に挙がっていない素通りは、除外ではなく抜け道である」。この規範を当てると、DR-0037 が明示的に決定した除外がマージ後は「抜け道」に分類され、description が約束した props の範囲は「契約が約束したのに実装が果たしていない範囲」になる。しかもこの PR は `descriptionOf()` により、その description をルール実装の公式な説明へ昇格させている。**DR-0044 が潰そうとしたカテゴリと同じ構造が、その DR を起こす PR の中で再生産されている。** `docs/review_log.md` はこの PR でこのカテゴリの状態を「仕組み化済み」に書き換えているが、実際に機械化されたのは lint 実装の description 1経路だけである。
- **失敗シナリオ**: `<SlideTitle color="#ff0000" />` も `design/layout.css` の `color: #fff` も、`pnpm lint` / `pnpm design:check` は緑のまま通す。ESLint が表示するルール説明は「色系 props に生の色値を書かない」なので、読み手は props も検査されていると信じる。
- **提案**: description を実装に合わせて「JSX の `style`」に限定し、props を見ないことを `scopeExclusions`（例: `attribute-value`）へ、CSS ファイルを見ないことを `css-file`（「ESLint に CSS AST パーサが配線されていない。DR-0037」）へ足す。それぞれ `expect: 'ok'` の事例を置く。あわせて DR-0037 側にも `scopeExclusions` を指す追記を入れ、無言で置き去りにしない。`review_log.md` の「仕組み化済み」も、どこまで機械化されたかが分かる書き方に留める。

### `inspection/rule-coverage-partial` — `enumeration-tail` 軸が、列挙の内側にある値だけで満たせる

- **場所**: `packages/eslint-plugin-slide/src/rules/no-raw-color.bypass.mjs`:54-65、`no-raw-scale.bypass.mjs`:64-76、`design/rules.json`:11, 21
- **指摘した観点**: 検査ルールの実効性
- **累計**: 6回目
- **何が起きているか**: `enumeration-tail` の事例は、`no-raw-color` では `COLOR_PROPERTIES` の末尾（`stopColor` / `accentColor`）、`no-raw-scale` では単位一覧の末尾（`vmax` / `ch`）を使っている。いずれも「一覧に載っている値」で、一覧の外は誰も見ていない。実測で確認した素通り: `color: "hwb(210 20% 30%)"`、`padding: "1cm"`、`width: "50dvw"` はすべて無警告。
- **なぜ問題か**: `enumeration-tail` という名前は列挙の末端まで塞いだことを示すと読めるが、検査が要求するのは「その軸のラベルが付いた違反事例が1つ以上あること」だけなので、一覧の内側から末尾っぽい値を選べば満たせる。宣言が緑になっても列挙の外の抜け道は残る。DR-0044 は「網羅性の保証ではなく、一覧を増やしたときに事例へ手が伸びる形を作るところまで」と正しく限定しているが、軸の**名前と事例の書き方**がその限定を裏切っている。
- **失敗シナリオ**: 生成されたスライドが `style={{ color: "hwb(210 20% 30%)" }}` を含んでいても lint は緑。`pnpm design:check` は `enumeration-tail` 軸が埋まっていることを確認して通す。
- **提案**: (a) 実装側の列挙を現行 CSS に寄せる（色関数に `hwb` / `color-mix` / `light-dark`、単位に `cm` / `dvh` / `dvw` 等）。(b) 軸の定義を「一覧の**外**の値」と明示し、フィクスチャがその外側の事例を持つようにする。(c) より根本的には、判定を許可リスト方式へ反転させる（`var(--dh-*)` と `allowedLiterals` 以外の、数値+英字に見える値はすべて違反）と列挙の末尾という概念自体が消える。

### `inspection/fixture-skips-collection-stage` — measure の bypass フィクスチャは評価段しか通らず、収集段の抜け道は原理的に扱えない

- **場所**: `scripts/measure-bypass.test.mjs`:59-72、`scripts/measure-slides.mjs`:134-282（`collectElementRecords`）、`design/rules.json`:87-90（`no-overflow` の `scopeExclusions: []`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 1回目（新規）
- **何が起きているか**: measure 側の runner は `evaluateSlideMeasurements(one.records(context), context)` しか呼ばない。`records` はフィクスチャが手で組み立てた配列であり、実際にブラウザで矩形・フォントサイズ・色・背景レイヤを集める `collectElementRecords` はこの経路に入らない（非 export、どのテストからも参照されていない）。
- **なぜ問題か**: measure 系の抜け道の多くは収集段に住む — どの要素を records に入れるか（`width <= 0 || height <= 0` による除外）、`hasDirectText` が何を「直接のテキスト」と数えるか、`backgroundLayers` が祖先をどこまで遡るか。これらは判定結果を左右するのに事例を書く場所が無い。`no-overflow` の `scopeExclusions` は空（= 見ない領域は無い、という宣言）だが、実際には収集段の取りこぼしがそこに入らない。「軸と除外を全部埋めた」という緑が、measure については評価関数の緑でしかない。
- **失敗シナリオ**: `collectElementRecords` の `rect.width <= 0 || rect.height <= 0` は、`width: 0` でも `left: -400` の要素をキャンバス外に出したまま records から落とす。この挙動を壊しても bypass フィクスチャは1件も落ちない。
- **提案**: (a) `collectElementRecords` の中身をブラウザ非依存の純関数として切り出し、フィクスチャが「DOM → records」も通れるようにする。(b) 重いなら、measure ルールの `scopeExclusions` へ「収集段は事例で固定していない」と明示し、緑が何を保証していないかを契約に残す。

### `decisions/dr-restates-canonical-value` — DR-0044 が、自分で「正本はスキーマの enum」と書いた軸の語彙4値を本文に書き写している

- **場所**: `docs/decisions/0044-bypass-fixtures-required.md`:5（`**正本**:` 行）、:26（「語彙は4つ——…」）、:62（「軸の語彙（4つ）は `design/schemas/rules.schema.json` の enum が正本」）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 6回目
- **何が起きているか**: 「決定」節が軸の語彙4つを id 付きで列挙し意味を定義する一方、「帰結」節は語彙の正本をスキーマの enum だと宣言している。冒頭の `**正本**:` 行はスキーマに触れていない。
- **なぜ問題か**: DR-0024 の帰結は「値を含む決定は `**正本**:` 行を持ち、値そのものは書かない」と定めている。列挙を2箇所に持つと、軸を1つ足したときに DR の「4つ」と列挙が取り残される。DR-0044 の帰結が書く「軸を増やすときの手順」にも、DR 本文の更新は含まれていない。
- **失敗シナリオ**: 5つ目の軸を enum に足す。スキーマ・`design/rules.json`・フィクスチャは `design:check` が整合を強制するが、DR-0044 の「語彙は4つ」は誰にも検査されず古いまま残る。
- **提案**: 「決定」節は軸の役割だけを述べ、語彙の列挙と各軸の定義はスキーマの enum とその `description` に寄せてリンクで指す。`**正本**:` 行にもスキーマを併記する。

### `writing/ambiguous-criterion` — 軸の語彙の定義が、実際の使い分けを決められない

- **場所**: `docs/decisions/0044-bypass-fixtures-required.md`:26、`design/rules.json`:22, 57、`packages/eslint-plugin-slide/src/rules/no-raw-scale.bypass.mjs`:49-65。あわせて `design/rules.json`:25（`calc-composition` の説明）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 8回目
- **何が起きているか**: 2つある。(1) DR-0044 は `boundary` を「閾値の両側」、`enumeration-tail` を「列挙で定義した対象の、先頭以外の要素」と定義するが、`no-raw-scale` の `boundary` 事例は閾値ではなく `allowedLiterals` という**列挙の内外**で書かれており（事例名自身が「1px が通るのは値が小さいからではなく、列挙されているから」と述べる）、`enumeration-tail` が指す「列挙」は実装側の単位一覧である。同じ性質の抜け道がルールごとに違う軸へ分類されうる。(2) `calc-composition` の説明は「calc() による**トークンの合成**」と書くが、実装は `calc(...)` 全体を1トークンとして扱うため中身を種類問わず見ない。事例のコードは `calc(100% - 8px)`（トークンを含まない生リテラルの式）で、説明と外延が合っていない。
- **なぜ問題か**: 書き手はまず `bypassAxes` を宣言してから事例を書く。その時点で「許容リストの内外は `boundary` か `enumeration-tail` か」が定義から決まらない。また「どこまでが除外として挙がっているか」が一意でないと、「契約に挙がっていない素通りは抜け道」という線引きが機能しない。
- **失敗シナリオ**: 書き手Aは許容リストの内外を `boundary` と読んで通る側の事例も書く。書き手Bは `enumeration-tail` だけを宣言し、通る側を要求されない。Bのルールでは、判定を一段厳しくする変更（リスト先頭の値まで落とす変更）が誰にも気付かれずに入る。`calc` については、レビュアーが `width: "calc(100% - 13px)"` を抜け道として立て、書き手が「calc は除外済み」と返す — 契約が決めるはずの論点が人の解釈に戻る。
- **提案**: 定義を「何の両側／何の末尾か」まで書く。`boundary` =「数値の閾値と、`design/rules.json` に列挙した許容値の内側と外側」、`enumeration-tail` =「ルールが判定対象を決めるために持つ一覧（プロパティ名・単位など）の、先頭以外の要素」。`calc-composition` は「`calc()` の内側。トークンの合成か生の長さかを問わず見ない」と実挙動に合わせる。

- **場所**: `design/rules.json`（no-raw-color / no-raw-scale の `attribute-value`）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 11回目
- **何が起きていたか**: 説明に「どの属性がその値を運ぶかは component 契約が決める範囲であり、lint 側に一覧を持つと正本が2つになる（DR-0037）」と書いていたが、DR-0037 を通読しても `no-raw-color` / `no-raw-scale` について書かれているのは「検査対象を JSX の `style={{ ... }}` オブジェクトに絞る」ことだけで、この理由付けはどこにも無い。DR-0035 も明示的には述べていない。
- **なぜ問題か**: 「非-style 属性は component 契約の管轄だから lint は持たない」は他の選択肢がありえた実在の判断であり、それが誤った参照付きで契約に居座っていた。読み手が根拠を確認しようと DR-0037 を開いても見つからない。
- **対応**: 理由付けを落とし、DR-0037 に実際にある記述だけを引く形にした（「検査対象を style オブジェクトに絞ったため見ない（DR-0037）」）。記録の無い判断を、記録があるかのように述べない方を選んだ。

#### `decisions/consequence-not-followed` — DR-0044 の「決定」節が、自分の「帰結」節が足した review の例外を反映していなかった

- **場所**: `docs/decisions/0044-bypass-fixtures-required.md`
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 8回目
- **何が起きていたか**: `method: "review"` の除外を「帰結」節にだけ足し、「決定」節の「検査ルールは、次の2つを伴わなければ `pnpm check` を通らない」は無条件のまま残っていた。**DR-0044 自身が問題視した構造（守備範囲が複数箇所に別々に書かれ、片方だけ更新される）が、この DR 自身の中で起きていた。**
