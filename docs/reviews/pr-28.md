## should

### code/binary-extension-check-case-sensitive — 拡張子の大文字小文字を無視しているため、大文字拡張子のバイナリが sanitize で破損しうる

- **場所**: `scripts/sanitize-run-artifacts.mjs`、`scripts/audit-public-data.mjs`（いずれも `BINARY_EXTENSIONS.has(extname(...))` を大文字小文字を区別したまま使っていた）
- **指摘した観点**: コード品質
- **累計**: 1回目（新規カテゴリ）
- **何が起きているか**: `extname()` は拡張子をそのまま返す（`extname('Screenshot.PNG')` は `'.PNG'`）。`BINARY_EXTENSIONS` は小文字のみの `Set` だったため、大文字拡張子のファイルは「バイナリではない」と誤判定されていた。レビュアーが実際に疑似バイナリ（不正バイトを含む25バイト）を大文字拡張子で保存し、`sanitizeDirectory` に通したところ、`writeFileSync` の UTF-8 再エンコードで内容が変わり、元のバイト列と一致しなくなることを確認した。
- **なぜ問題か**: 保存 Run を安全に公開用へ整形するという本PRの目的そのものに反する。画像を書き換えて壊してしまっては、audit が緑でも公開できるデータにならない。
- **対応**: `extname(path).toLowerCase()` で比較する `isBinaryPath` を `scripts/lib/fs-walk.mjs` へ切り出し、両スクリプトから使うようにした。大文字拡張子（`Screenshot.PNG`）で書き込まれないことを固定する回帰テストを追加した。

### inspection/rule-coverage-partial — audit が `PUBLICATION_POLICY.md` 自身の挙げる脅威の一部（一時ディレクトリのパス、単独のユーザー名）を検査していない

- **場所**: `scripts/audit-public-data.mjs`（`LEAK_PATTERNS` が `/home/` と `/Users/` の接頭辞、および秘密鍵形式しか持たない）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 5回目
- **何が起きているか**:
  1. `docs/PUBLICATION_POLICY.md` は絶対パス漏洩の例として「隔離ワークスペースの絶対パス（`/home/<user>/...` **や一時ディレクトリのパス**）」を挙げているが、`prepare-workspace.mjs` の既定の出力先は `os.tmpdir()`（Linux では通常 `/tmp`）配下であるにもかかわらず、`LEAK_PATTERNS` には `/tmp/` を拾うパターンが無かった。実際に `/tmp/...` を含む文字列が検知されないことを確認した。
  2. 同ポリシーは「OS ユーザー名。...単独の文字列として混ざることがある」とも書くが、`LEAK_PATTERNS` にはパス形状・秘密鍵形状しか無く、単独文字列としてのユーザー名を拾う手段が無かった。sanitize 側は単語境界つきの置換をすでに実装しているのに、audit 側にそれと対になる検査が無い状態だった。
- **なぜ問題か**: `pnpm public:audit`（`pnpm check` 経由）が緑でも、ポリシー文書が明示する脅威の半分が素通りする。「audit が通る＝既知パターンは無い」という前提が、文書に書かれた既知パターンの全部をカバーしていなかった。
- **対応**: `tmp-path` / `macos-tmp-path` の静的パターンを追加した（一時ディレクトリの接頭辞は環境に依存しない一般的な形なので、sanitize 側と同様に固定パターンで拾える）。ユーザー名は `buildLeakPatterns({ username })` を新設し、既定で現在の OS ユーザー名を単語境界つきで検査対象へ加えた。ただし audit を実行しているマシンのユーザー名しか分からないため、別マシンで生成し sanitize しなかった Run のユーザー名までは検出できないという限界を `docs/PUBLICATION_POLICY.md` に明記した。

### decisions/undocumented-decision — audit の API キー/token 検査対象パターンの選定が DR に無い

- **場所**: `scripts/audit-public-data.mjs`（`LEAK_PATTERNS` に OpenAI/Anthropic/GitHub/AWS/Slack の5形式 + 汎用代入パターン）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 9回目
- **何が起きているか**: DR-0023 の「決定」節は audit の役割を「置換漏れの文字列検査」とだけ定め、API キー・token には一言も触れていない。Issue #11 の完了条件がこれを要求してはいるが、どの形式を選ぶか・閾値をどう置くかという実装判断は DR に無いまま実装された。
- **なぜ問題か**: 「他の選択肢がありえて、選んだ理由を後から聞かれうる判断」（命名・閾値・対象範囲の選定）が記録されずに既成事実化していた。半年後に「なぜこの5形式か」を再検討する材料が無い。
- **対応**: [DR-0040](../decisions/0040-audit-secret-pattern-selection.md) を新設し、対象形式の選定理由・却下した代替（外部secret-scanningツール導入、汎用パターンのみに絞る案、有効性の外部確認）を記録した。DR-0023 の「決定」節からも DR-0040 へリンクした。

### contract/design-data-duplicated — `README.md` が `docs/PUBLICATION_POLICY.md` の内容を複製している

- **場所**: `README.md`「公開時の注意」節
- **指摘した観点**: 設計契約との整合
- **累計**: 6回目
- **何が起きているか**: 本PRは `README.md` の「正本の在り処」表に `docs/PUBLICATION_POLICY.md` を正本として追加する一方、同じ README の「公開時の注意」節に、保存 Run の内容・sanitize/audit の役割・「audit は公開承認ではない」「最終判断は人」といった、正本であるはずの内容をほぼそのまま書き写していた。
- **なぜ問題か**: 「設計データは正本にのみ置く。Skill やドキュメントへ複製しない」という README 自身の既存ルールに反する。将来 `PUBLICATION_POLICY.md` を改訂しても README 側は自動的に追随せず、どちらが最新かを読者が判断できなくなる。
- **対応**: 「公開時の注意」節を `docs/PUBLICATION_POLICY.md` への参照一文に絞り、具体的な基準文言は正本側だけに残した。

### writing/contradictory-instruction — 保存 Run に含まれるものの説明が DR-0023 と実際の保存形式で食い違う

- **場所**: `README.md`、`docs/PUBLICATION_POLICY.md` vs `docs/decisions/0023-public-repo-with-audit.md`（変更前）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 3回目（ルール化候補入り）
- **何が起きているか**: 本PRの README/POLICY は「生成ソース、採点結果、実測結果」と書くが、両方が根拠として引く DR-0023 は変更前の時点で「生成ソース、`changes.diff`、`events.jsonl`（AI の行動ログ）、各種検証ログ、プロンプト全文」と書いており、列挙が一致していなかった（DR-0023 は #10 の実装確定前に書かれた Atlas 由来の想定を引きずっていた）。
- **なぜ問題か**: 同じ決定記録を権威として指す3文書が、この PR の主題（何を sanitize/audit で守るべきか）について異なる事実を述べており、読み手によって解釈が割れる。
- **対応**: DR-0023 の文脈節を、実際の保存形式（#10 で確定した `run.schema.json`）に合わせて修正し、当初の Atlas 由来の想定（`changes.diff` / `events.jsonl`）は実装しなかった旨を明記した。README/POLICY 側の記述はそのまま維持し、3文書の記述を揃えた。

### writing/inaccurate-rationale — sanitize の「バックアップを取らない理由」が、同じPRが定める運用手順と矛盾する

- **場所**: `scripts/sanitize-run-artifacts.mjs` の JSDoc、`docs/PUBLICATION_POLICY.md`「使い方」節
- **指摘した観点**: 日本語ドキュメント
- **累計**: 5回目
- **何が起きているか**: sanitize のコメントは「バックアップは取らない（git 管理下にあるため、必要なら差分を戻せる）」と書いていたが、同じPRの `PUBLICATION_POLICY.md` は「Run を保存したら、**コミットする前に** sanitize → audit の順で実行する」と定めている。この主要な使用場面では対象はまだ未追跡ファイルで、戻せる差分が存在しない。
- **なぜ問題か**: コメントを信じて「まずければ git で戻せる」と考えたまま実行すると、コミット前の Run データを失いうる。
- **対応**: コメントを実態に合わせ、「疑いが残るときは実行前に `git add -N` するか、コミット後に実行する」旨に書き直した。
