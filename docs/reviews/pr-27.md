### inspection/rule-has-bypass — 採点用 ESLint 設定に `noInlineConfig` が無く、`eslint-disable` コメントで契約違反が消える

- **場所**: `scripts/evaluate-run.mjs`（`scoreLint` 内の `ESLint` インスタンス化）。比較対象は `eslint.config.js` の `src/**/*.{ts,tsx}` ブロック（`linterOptions: { noInlineConfig: true, ... }`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 9回目
- **何が起きているか**: `scoreLint` は独自の `overrideConfig` で ESLint インスタンスを組み立てており、本番の `eslint.config.js` が持つ `noInlineConfig: true` を引き継いでいなかった。実際に `/* eslint-disable slide/no-raw-color */` を付けたファイルを `scoreLint` に通すと、違反数が0件になることを確認した。
- **なぜ問題か**: `evaluate-run.mjs` の目的は「AI を起動せず、保存済みの生成結果を契約検査ルールで採点する」こと（DR-0020）。生成AIが typecheck/build を通すために抑止コメントを書くことは実際に起こり得る。その場合、実際には契約違反があるのに `scoring.json` / `compare-runs.mjs` の比較表は「pass」と報告し、baseline / harness のどちらが契約に沿っているかという実験結果の信頼性そのものを損なう。
- **失敗シナリオ**: harness 条件の生成コードに抑止コメントが混ざる → `evaluate-run.mjs score` を実行 → `no-raw-color` 等が計上されない → 比較表がそのセルを `pass` と表示 → 実際には契約違反があるのに harness の優位性の証拠として誤用される。
- **対応**: `scoreLint` の `overrideConfig` に `linterOptions: { noInlineConfig: true, reportUnusedDisableDirectives: 'error' }` を追加。回帰テスト（`scripts/evaluate-run.test.mjs` の「eslint-disable コメントでは違反が消えない」）を追加し、`no-raw-color` が引き続き1件計上されることを固定した。ruleId が無いメッセージのバケット名も `(parse error)` から `(no rule id)` に直した（noInlineConfig 通知は構文エラーではないため）。

### code/measure-failure-swallowed（新規） — `scoreMeasure` が measure-slides.mjs の実失敗を握り潰し、無関係な ENOENT で落ちる

- **場所**: `scripts/evaluate-run.mjs`（`scoreMeasure`）
- **指摘した観点**: コード品質
- **累計**: 1回目（新規カテゴリ）
- **何が起きているか**: `scoreMeasure` は子プロセスの失敗を無条件に `catch {}` で握り潰し、`measurements.json` を読みに行く前提だった。しかし `measure-slides.mjs` はビルド出力が壊れている場合（`.slide-canvas` が無い等）、`measurements.json` を書き出す前に例外で終了する。この場合 `readFileSync(outPath)` が ENOENT を投げ、本来の原因（ビルド出力の何が壊れているか）が失われる。実際に `.slide-canvas` を欠いた `dist/` を渡して再現を確認した。
- **なぜ問題か**: 採点基盤の失敗理由が実際の原因から無関係なメッセージにすり替わり、`stdio: 'pipe'` で握った stderr も表示されないため原因調査ができない。
- **失敗シナリオ**: ビルドが壊れた Run を `evaluate-run.mjs score` にかけると、素の `ENOENT: ... measurements.json` だけが出て、何が壊れているか分からない。
- **対応**: `catch` 節で `outPath` の存在を見て分岐するよう修正。`measurements.json` が無ければ子プロセスの stderr（またはエラーメッセージ）を含めた明示的なエラーを投げるようにした。あわせて `score` サブコマンドにも `save` と同様の try/catch を追加し、素の Node スタックトレースではなく一貫したエラー表示にした。回帰テスト2件（健全なビルドで `measured` を返すケース、`.slide-canvas` を欠くビルドで本来のエラーを伝えるケース）を追加した。

### phase/completion-criterion-not-verified-e2e — Run の実測採点パス（`scoreMeasure` の measured 分岐）が一切検証されないまま完了条件に含まれていた

- **場所**: `scripts/evaluate-run.test.mjs`（`scoreMeasure` / `scoreRun` のテストが `skipped` 分岐のみだった）
- **指摘した観点**: フェーズスコープ
- **累計**: 3回目（ルール化候補）
- **何が起きているか**: Issue #10 の完了条件「保存済み Run に対して採点と比較を何度でも再実行できる」のうち、`scoreLint` は実 ESLint による統合テストがあった一方、`scoreMeasure` は `dist` が無い `skipped` 分岐しかテストされておらず、実際に `measure-slides.mjs` を子プロセス起動して `measurements.json` を読み戻す本来の経路が一度も実行されていなかった。
- **なぜ問題か**: この経路はこの実験装置の主目的（Baseline/Harness の実測比較）が機能するかどうかを左右する中心的なコードパス。単体テストで一度も踏まれないまま完了条件のチェックが付くと、`--dist=`/`--out=` の受け渡しや `measurements.json` のマージが壊れていても `pnpm test` は緑のまま気付けない。
- **失敗シナリオ**: `measure-slides.mjs` 側の呼び出し規約に前提のズレがあった場合、実際に人が `dist` 付きの Run を保存してスコアリングを実行するまで（＝実験を1回走らせるまで）発覚しない。
- **対応**: 静的な `dist/index.html`（`.slide-deck` / `.slide-canvas` を持つ最小構成）を使った統合テストを2件追加。健全なビルドで `status: 'measured'` かつ `pass: true` を返すこと、壊れたビルドで正しくエラーになること（上の `code/measure-failure-swallowed` の回帰テストと兼用）の両方を実 Playwright 実行で固定した。
