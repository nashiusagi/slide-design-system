### `code/check-skips-workspace-packages` — `pnpm check` が workspace パッケージを型検査もテストもしない

- **場所**: `package.json`:17（`check` / `test`）、`tsconfig.json`:3-6、`vite.config.ts`:11、`pnpm-workspace.yaml`:2
- **指摘した観点**: コード品質、検査ルールの実効性（2観点から独立に挙がった）
- **累計**: 1回目
- **何が起きているか**: `pnpm-workspace.yaml` に `packages/*` を宣言し、`eslint.config.js` のコメントが契約検査プラグインを `packages/eslint-plugin-slide` に置くと明記している。一方 `tsc -b` の references は app / node の2つのみ、vitest の `include` は `src/**/*.test.{ts,tsx}`、`test` は `vitest run`（`-r` なし）。検査レビュアーが `packages/probe/probe.test.ts` に必ず失敗するテストを置いて `vitest run` した結果、`Test Files 1 passed (1)` で exit 0 だった。`packages/` を見るのは `eslint .` だけ。
- **なぜ問題か**: DR-0011 の lint 5 ルールの実効性を担保するのは RuleTester の invalid ケースだけであり、その置き場所が丸ごとテストランナーと型検査の視界の外にある。README は「`pnpm check` が受け入れの入口になる」と宣言しているのに、検査基盤そのものが入口を通らない。
- **失敗シナリオ**: 後続 Issue で `packages/eslint-plugin-slide/src/rules/no-raw-color.ts` と invalid ケース付きのテストを追加する → 実装をミスして何も報告しないルールになっても、テストは実行されず型エラーも見られないので `pnpm check` は緑 → 生の色値が素通りしたまま「全ルール pass」で採点される。
- **提案**: vitest の `include` を `{src,packages}/**/*.test.{ts,tsx}` へ広げる（または `pnpm -r --if-present test`）、`tsconfig.json` の references にパッケージを足す運用を明記する。今回閉じないなら「今の `check` は `packages/` を型検査・テストしない」ことを残す。

### `inspection/rule-has-bypass` — インライン `eslint-disable` で契約ルールを一行ずつ無効化できる

- **場所**: `eslint.config.js`:9-30
- **指摘した観点**: 検査ルールの実効性
- **累計**: 2回目
- **何が起きているか**: flat config に `linterOptions.noInlineConfig` も `reportUnusedDisableDirectives` も無い。`src/__probe.tsx` に `/* eslint-disable @typescript-eslint/no-unused-vars */` を付けた違反コードを置いて `eslint` を実行した結果、報告 0 件・exit 0 だった。
- **なぜ問題か**: 検査対象は AI が生成したスライドソースであり、生成物に抑止コメントが混ざりうる。抑止が効くなら `no-raw-color` / `layout-approved` / `deck-conformance` はいずれも「書き方を変えると素通りする」ルールになる。さらに disable された行は報告に残らないため、DR-0011 の帰結にある「実行されたルール ID の集合を残す」方式でも検出できない（ルール自体は実行済み扱いになる）。
- **失敗シナリオ**: 生成された `src/decks/foo/Slide03.tsx` に `// eslint-disable-next-line slide/no-raw-color` と `color: '#ff0000'` が入る → `pnpm lint` 通過 → 契約外の色を持つスライドが pass として採点される。
- **提案**: スライドソースに当たるファイル群へ `linterOptions: { noInlineConfig: true, reportUnusedDisableDirectives: 'error' }` を設定する。

### `writing/ambiguous-criterion` — 判断基準が曖昧で、契約として実行できない（2箇所）

- **場所**: `docs/decisions/0026-typescript-5-for-eslint-ast.md`:37、`README.md`:31
- **指摘した観点**: 日本語ドキュメント
- **累計**: 3回目（ルール化候補）
- **何が起きているか**:
  1. DR-0026 の帰結が「バージョンの上げ下げを検討するときは、まず `pnpm lint` が動くかを基準にする」と書いている。「動くか」は (A)「`eslint .` が exit 0 を返す」とも (B)「自作ルールが違反を実際に検出できる」とも読める。同じ DR の却下理由は (A) の状態こそ危険だと述べているので、読み方が割れると DR が実効を失う。
  2. README の「契約に基づく検査（lint / measure）は、この枠の中へ後から足していく」の「枠」が、`pnpm check` のコマンド列とも pnpm スクリプト群とも読める。measure は `dist/` に対して実行する（DR-0011 / DR-0022 の帰結）ため、現在の並び（build が最後）では前者の読みで実装すると空振りする。
- **なぜ問題か**: どちらも後続 Issue の実装方針を直接左右する一文である。
- **失敗シナリオ**: TypeScript を上げる Issue で `pnpm lint` の exit 0 だけを見て「基準を満たした」と判断し、パーサ変更で自作ルールが1件も発火しなくなっていることを見逃す。measure 実装の Issue で `check` の途中に measure を挿入し、`dist/` が無い状態で常に fail または空振りする。
- **提案**: DR-0026 は検出側で基準を書く（プラグイン実装前の現時点では「`pnpm lint` が正常終了し、かつ `typescript-eslint` の peer 範囲を満たすこと」に限定する）。README は「lint は `check` の lint 段へ、measure は build 後に走る段として足す」と実行位置を明示する。

### `decisions/undocumented-decision` — 足場の技術選定と `pnpm check` の設計が DR に無い

- **場所**: `package.json`:6-8,20-35、`pnpm-workspace.yaml`、`packages/.gitkeep`、`README.md`:22,28,31
- **指摘した観点**: 決定記録（DR）
- **累計**: 3回目（ルール化候補）
- **何が起きているか**: pnpm workspace（`packages/*` に ESLint プラグインを置く）、テストスタック（Vitest + jsdom + Testing Library）、Node.js 22 下限、そして「受け入れの入口を `pnpm check` 単一コマンドに集約し、typecheck → lint → test → build の順で直列に繋ぐ」という判断が、どの DR にも無い。理由が残っているのは Issue #2 の一行と README だけ。DR-0026（TypeScript のバージョン）という細かめの決定は DR にした一方でこれらを落としているため、記録の粒度も不揃いになっている。あわせて、直下の足場と DR-0021 の共通 starter（`experiments/`）の関係——再利用か、コピーか、生成か——も未記録のまま先送りされている。
- **なぜ問題か**: いずれも他の選択肢が実在する判断である（単一パッケージ / Jest / Node 20 / 検査ごとに別コマンド）。`pnpm check` は DR-0011 の帰結（実行ルール ID の集合、measure はビルド出力に対して実行）が実装される土台そのものであり、根拠が README にしか無いと、後続の変更が突き合わせなしに起きる。starter との関係は、複製になった場合に DR-0021 の公平性の根拠（starter は完全に同一）を静かに壊す。
- **失敗シナリオ**: 半年後に「なぜ workspace か」「なぜ Vitest か」を再議論する。`experiments/starter/` にビルド設定をコピーして作り、直下だけ更新した結果、Baseline と Harness が異なるビルド条件で走る。
- **提案**: (1) 足場の構成（workspace / テストスタック / Node 下限）、(2) 検査の実行口を `pnpm check` に一本化する決定、の 2 本を DR に起こし、却下案と順序の理由を書く。starter との関係は (1) の帰結に一文残す。

### `phase/out-of-scope-addition` — 足場の CSS が #4 の持つデザイン値とクラス名を先取りしている

- **場所**: `src/index.css`:5-8、`src/App.tsx`:3
- **指摘した観点**: フェーズスコープ、設計契約（2観点から挙がった）
- **累計**: 3回目（ルール化候補）
- **何が起きているか**: `:root` に `font-family: system-ui, sans-serif` と `line-height: 1.5` を直接書いている。これらは Issue #4 の `design/tokens.json` の `type` トークンが正本になる値で、Issue #2 の非スコープに「デザイントークン・契約（#4, #5）」が明記されている。`App.tsx` の `className="app"` に対応する CSS 規則も無く、DR-0018 は「クラス名は契約が定める」としている。

### `writing/term-inconsistency` — 「受け入れの入口」という新しい語が、issue-workflow の「完了条件」と別語のまま置かれている

- **累計**: 3回目（ルール化候補）

## ルール化候補

このレビューで累計3回に達したカテゴリ。**いずれもドキュメント・運用の問題であり、`design/rules.json`（スライド生成物の検査）へそのまま載る性質のものではない。** 機械化するならリポジトリ側の検査（DR とドキュメントの整合を見るスクリプト）になる。判断は人が行う。

- `writing/ambiguous-criterion` — 通算3回。「動く」「枠」のような多義語を基準の位置で使わない、という規約は自動判定が難しい。判定できるとすれば、DR の「帰結」節に検証手段（コマンドまたはテスト）が書かれているかの検査。
- `decisions/undocumented-decision` — 通算3回。PR 差分に新しい依存関係や新しい npm スクリプトが入ったとき、同じ PR で `docs/decisions/` に追加または更新があるかを見る検査にできる。
- `phase/out-of-scope-addition` — 通算3回。Issue の「非スコープ」節に挙がったパス・語が差分に現れていないかの検査にできるが、今回のように「値の種類」で違反する場合は捕まえにくい。
- `writing/term-inconsistency` — 通算3回。用語集を正本として持ち、新出の語を検出する形なら機械化できる。
- `writing/notation-inconsistency` — 通算3回。`DR-\d{4}` がリンクになっているかの検査は容易で、これが5件の中では最も機械化しやすい。
