## blocker

### inspection/rule-has-bypass — 生の値の書き方を変えるだけで no-raw-scale / layout-approved / component-approved を完全に迂回できる

- **場所**: `packages/eslint-plugin-slide/src/rules/no-raw-scale.mjs:38`、`packages/eslint-plugin-slide/src/rules/layout-approved.mjs:43`、`packages/eslint-plugin-slide/src/rules/component-approved.mjs:43`
- **指摘した観点**: 検査ルールの実効性
- **累計**: 7回目
- **何が起きているか**:
  - `no-raw-scale.mjs:38` の `NUMERIC_LENGTH = /^-?\d+(\.\d+)?(px|rem|em|vh|vw|vmin|vmax|pt|ch|%)?$/` は文字列全体が単一の数値＋単位であることを要求する。`style={{ margin: "8px 16px" }}` のようなショートハンド複合値は正規表現全体に一致せず、`continue` されて一切報告されない。`Linter` で実行し `0` 件になることを確認した（対照として `margin: "16px"` 単独では正しく1件検出されることも確認済み）。
  - `layout-approved.mjs:41-43` と `component-approved.mjs:41-43` はどちらも `layoutAttribute.value` の型が `Literal` であることだけを条件に値を取り出す（`value?.type === 'Literal' && typeof value.value === 'string' ? value.value : undefined`）。`<Slide layout={"bogus-layout"}>` のように文字列リテラルを波括弧（`JSXExpressionContainer`）で包むだけで `value.type` は `'JSXExpressionContainer'` になり、両ルールとも「静的に判定できない値」として扱われ検査自体をスキップする。`Linter` で実行し、`layout-approved` は契約に無い `bogus-layout` を報告せず、`component-approved` も `allowedIn` 違反を報告しないことを確認した（`layout="bogus-layout"`と波括弧無しで書いた場合は正しく検出されることも確認済み）。
- **なぜ問題か**: `design/rules.json` の契約は「生の長さリテラルを書かない」「契約外の layout 名を使わない」であり、値の構文をわずかに変えるだけで契約違反が `pnpm lint` を素通りするなら、この3ルールは実質的に検査として機能しない。特に `margin` / `padding` / `border` のショートハンド記法や、JSX で値を波括弧で包む書き方はどちらも一般的な書き方であり、意図的な回避でなくても自然に発生しうる。
- **失敗シナリオ**: 生成ループ、あるいは開発者が `style={{ padding: "8px 16px" }}` や `<Slide layout={"bogus-layout"}>` と書いても `pnpm lint` はエラーを出さずに通過し、`pnpm check` も緑になる。契約外の値が実装に紛れ込んだまま検出されない。
- **提案**:
  - `no-raw-scale`: 値をトリムした後に空白で分割し、各トークンを個別に `NUMERIC_LENGTH` へ通す（キーワード値・`var(...)` トークンはそもそも数値パターンに一致しないため誤検出は増えない）。
  - `layout-approved` / `component-approved`: `value.type === 'JSXExpressionContainer' && value.expression.type === 'Literal'` の場合も同じロジックで文字列を取り出す（テンプレートリテラルまで広げるかは別途判断）。

### inspection/rule-has-bypass — `var()` フォールバック・対象プロパティの不足・テンプレートリテラルが未検出

- **場所**: `packages/eslint-plugin-slide/src/rules/no-raw-color.mjs:15-30,32-33`、`packages/eslint-plugin-slide/src/rules/no-raw-scale.mjs:38`、`packages/eslint-plugin-slide/src/lib/jsx-style.mjs:58-66`
- **指摘した観点**: 検査ルールの実効性、コード品質（2つの観点から独立に指摘）
- **累計**: 7回目（同一PR内の blocker 指摘と同カテゴリのため、集計上は+1のみ）
- **何が起きているか**:
  - `TOKEN_REFERENCE = /^var\(--dh-[\w-]+\)$/` は完全一致のみを許可トークンとして扱う。`style={{ color: "var(--dh-color-text, #ff0000)" }}` はトークン参照にもRAW_COLORにも一致せず、フォールバックの生値がそのまま素通りすることを `Linter` で確認した（`no-raw-scale` の `var(--dh-space-md, 16px)` も同様）。
  - `COLOR_PROPERTIES` は `backgroundImage` / `boxShadow` / `textShadow` を含まず、また CSS カスタムプロパティ経由の間接参照（`--leak: '#ff0000'` → `var(--leak)`）も対象外。
  - `jsx-style.mjs` の `literalText` は `Literal` ノードのみを扱い、テンプレートリテラル（`` `#ff0000` `` / `` `16px` ``）は `null` を返すため両ルールとも無条件でスキップする。`Linter` で実際に0件になることを確認した。
- **なぜ問題か**: いずれも「トークン変数の参照だけを許す」契約の抜け道であり、書き方を変えるだけで検査を回避できる。
- **失敗シナリオ**: `var(--dh-color-text, #ff0000)` や `` `#ff0000` `` のような書き方が `pnpm lint` を通過する。
- **提案**: `var()` のフォールバック部分にも同じ検査を再帰適用する。`COLOR_PROPERTIES` に不足プロパティを追加する。`literalText` に `TemplateLiteral`（式を含まないもの）を対応させる。
