## blocker

### `writing/inaccurate-rationale` — 「契約検査5ルールはいずれも判定の基準値を自分の中に持たない」が `no-raw-color` の実装と食い違う

- **場所**: `docs/decisions/0045-stay-on-eslint-not-biome.md`:20（突き合わせ先: `packages/eslint-plugin-slide/src/rules/no-raw-color.mjs`:12-35、`no-raw-scale.mjs`:24-40,94-95）
- **指摘した観点**: コード品質 / 検査ルールの実効性 / 決定記録との整合 / 日本語ドキュメント（4観点）
- **累計**: 10回目
- **何が起きているか**: DR は「契約検査 5 ルールはいずれも、判定の基準値を自分の中に持たず、`design/` 配下の契約をその場で読んで判定する（`design-contracts.mjs`）」と書いている。実装を読むと、判定の基準値を `design/` から読んでいるのは `layout-approved`（`listLayouts`）/ `component-approved`（`listComponents`）/ `deck-conformance`（`parseDeck`）の3ルール。`no-raw-scale` は `readRules().noRawScale.allowedLiterals` だけを読み、`UNITLESS_PROPERTIES` と `NUMERIC_LENGTH` は実装内にある。`no-raw-color` に至っては `design-contracts.mjs` から取るのが `descriptionOf` だけで、判定に使う `COLOR_PROPERTIES` / `RAW_COLOR` / `TOKEN_PREFIX` はすべてルール本体の定数である。しかもこれは DR-0037 が意図して決めた形（「色を運ぶプロパティを固定の一覧で持ち」）。
- **なぜ問題か**: この全称が、却下理由（「GritQL はパターンへ値を書き写すので正本の複製になる」）と再検討条件（「外部ファイルを読めるようになったら」）の両方を支えている。実際に外部ファイル読み取りが移行可否を決めるのは3ルールで、残り2つは別の理由（判定ロジックの再実装、DR-0044 のフィクスチャ）で移せない。DR-0044 が `descriptionOf` のコメントで名指しした「同じルールの守備範囲を述べる場所が増える」状態を、DR 本文という3つ目の場所で作ってもいる。
- **失敗シナリオ**: 再検討の場で「`no-raw-color` は契約を読んでいないから GritQL で書けるのでは」と指摘された瞬間、DR の記述だけを根拠に論拠が崩れ、判断がやり直しになる。逆向きの誤りも起きる——この記述を信じた人が「色検査の対象プロパティは契約側で増やせる」と読み、`design/` に `borderInlineColor` を足す。`COLOR_PROPERTIES` は変わらないので検出は増えず、`pnpm check` は緑のまま生の色値が素通りする。
- **提案**: ルールごとの実態に分けて書く。「`layout-approved` / `component-approved` / `deck-conformance` は判定の基準値を `design/` 配下から読む。`no-raw-scale` は許容リテラルを `design/rules.json` から読む。`no-raw-color` は判定パターンを実装に持つが、説明文と意図的に見ない領域の正本は `design/rules.json` にある（DR-0044 / DR-0037）」。そのうえで「この一点が 2 を直撃する」を該当するルール数に合わせて落とす（決定そのものは3ルールが該当する時点で変わらない）。

## should

### `decisions/unsatisfiable-reexamination-criterion` — 再検討の合否判定「既存テストがそのまま通る」が字義どおりには満たせない

- **場所**: `docs/decisions/0045-stay-on-eslint-not-biome.md`:63（突き合わせ先: `packages/eslint-plugin-slide/src/rules/bypass.test.mjs`:11）
- **指摘した観点**: フェーズスコープ / 検査ルールの実効性 / 決定記録との整合（3観点）
- **累計**: 1回目（新規）
- **何が起きているか**: 合否判定を「DR-0044 の bypass フィクスチャを含む既存テストが、移行後の実装に対してそのまま通ること」とし、「移行先で書き直したテストが通ることは条件にならない」と閉じている。しかし実行の入口である `bypass.test.mjs` は `import { RuleTester } from 'eslint'` で、ESLint の `RuleTester` に `plugin.rules[rule.id]` を渡し、期待値を ESLint の `messageId` で書いている。ESLint を外した実装をこのテストに載せる経路は無い。フィクスチャ側（`*.bypass.mjs` の `code` / `expect`）は宣言データなので移植可能だが、ランナーは「そのまま」動かない。
- **なぜ問題か**: 字義どおり読むと、どんな移行案も判定に掛ける前に不合格が確定する（条件ではなく恒久的な否になる）。緩く読めば「事例は据え置き、入口だけ書き直す」だが、DR が禁じた「書き直したテスト」との線引きが無い。どちらに転んでも、再検討の場で基準がその場の解釈に置き換わる。DR-0026 の同種の条件はフィクスチャに軸を置いており、この DR はそこから一段厳しい方へずれている。
- **失敗シナリオ**: 将来 Biome が条件を満たし移行 PR が出る。作者は「事例は1件も変えていない、実行スクリプトだけ差し替えた」と言い、レビュアーは「テストを書き直したので条件不成立」と言う。どちらも DR を正しく引用しており、議論は速度と好みに戻る。
- **提案**: 据え置く対象と書き直してよい対象を分ける。「`design/rules.json` の `bypassAxes` / `scopeExclusions` の宣言と、各 `*.bypass.mjs` の事例・期待結果を1件も変えずに移行先の実装へ与え、すべてが期待どおり violation / pass になること。実行の入口は移行先向けに書き直してよいが、事例の追加・削除・書き換えは条件を満たさない」。禁じたいのは「テストごと作り直して違反が消える」ことであって、ランナーの再実装そのものではない。

### `decisions/context-broader-than-decision` — 再検討条件から、ビルドエントリ境界の import 禁止（文脈3のもう半分）が落ちている

- **場所**: `docs/decisions/0045-stay-on-eslint-not-biome.md`:16, :22, :60-62（突き合わせ先: `eslint.config.js`:12-48）
- **指摘した観点**: 検査ルールの実効性 / 決定記録との整合（2観点）
- **累計**: 2回目
- **何が起きているか**: 文脈の 3「構造の禁止」は (a) ビルドエントリ境界の静的 / 動的 import 禁止（DR-0042）と (b) `src/**` の `noInlineConfig` の二つで定義されている。しかし「3 も同様に埋まらない」（:22）は (b) しか論じず、再検討条件（:60-62）も (b) 相当しか要求していない。(a) が条件に現れない。Issue #48 の棚卸し表では動的 import について「代替が不明。`ImportExpression:not([source.type='Literal'])` のような否定条件を GritQL で表現できるか未確認」と明記されており、その未確認事項が DR に落ちていない。
- **なぜ問題か**: 条件が2つ揃った時点で「再検討してよい」と読まれるが、そこに (a) の判定が入っていない。しかも (a) は `design/rules.json` に ID を持たないため DR-0044 の bypass フィクスチャの対象外で、`forbidCrossEntryImports` に対するテストはリポジトリ内に存在しない。つまり合否判定（既存テストが通ること）を通しても、(a) が消えたことは検出されない。
- **失敗シナリオ**: Biome が JS ルール記述と `noInlineConfig` 相当を備える → 条件成立と判断して移行 → 契約検査は移植され bypass フィクスチャも通る → `forbidCrossEntryImports` だけ移植漏れ → `src/App.tsx` から組み立てたパスの `import()` が入ってもどの検査も落ちず、カタログのコードがスライドのバンドルへ混ざる。ビルドは通るので気づけない（DR-0042 / DR-0022）。
- **提案**: 再検討条件を3つにし、「ビルドエントリ境界の禁止を、静的 import のパス glob・リテラル引数の動的 import・リテラルでない `import()` そのものの禁止まで含めて同じ守備範囲で表現できること」を加える。あわせて :22 では (a) について「未確認」であることを書く（「見当たらない」と断定しない）。

### `writing/contradictory-instruction` — 「整形は決めない」と、却下した選択肢の見出しが整形まで含めていることが食い違う

### `writing/unsourced-external-claim` — Biome 側の事実に出典とバージョンが無く、根拠が不在の証明になっている
