## should

### `inspection/rule-has-bypass` — `backgroundLayers()` が oklch() を読めず、未知の記法を黙って無視する

- **場所**: scripts/measure-slides.mjs:213-247（修正前）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 11回目
- **何が起きているか**: `scripts/lib/color.mjs` の `parseCssRgb` はすでに oklch() の計算値を読めるよう修正済みだったが（Issue #12 の実験中に発見・修正）、`measure-slides.mjs` 側の `backgroundLayers()` は Playwright の `page.evaluate()` クロージャ内で独立した正規表現を持っており、そちらには oklch() 対応が入っていなかった。しかも一致しない値が来ても例外を投げず、単に何も push せず次の祖先へ進んでいた。
- **なぜ問題か**: `design/theme.css` の `--dh-color-*` を `background-color` に直接当てた要素があると、その背景レイヤーが「無い」ものとして扱われ、実際より薄い（あるいは無い）背景に対してコントラストを判定する。判定結果が実測とズレていることに誰も気付けない。
- **失敗シナリオ**: 背景に oklch() の暗い色を使い、前景に白文字を置いたスライドで、本来は基準を満たすコントラストが「背景なし＝白地」として計算され、逆に基準未達のケースを見逃す（またはその逆）。
- **提案**: `color.mjs` と同じ oklch() 読み取りを `backgroundLayers()` にも追加し、認識できない記法は例外にする。
- **対応**: 修正済み。`oklchToRgb255(l, c, h)` をクロージャ内に複製し（Node 側モジュールを import できないため）、`rgbMatch` → `oklchMatch` → 例外、の順で判定するよう書き換えた（コミット `5ad8337`）。手動ビルドした smoke test dist（背景に oklch()、alpha 付きも含む）と、実際の `harness-corrected-1/dist` の両方で `pnpm exec node scripts/measure-slides.mjs` が正しく pass することを確認した。

- **場所**: docs/decisions/0038-defer-measure-in-check.md（帰結節）、experiments/harness-intro/RESULTS.md
- **指摘した観点**: 決定記録（DR）との整合

- **失敗シナリオ**: 別の Issue で「DR-0038 の帰結通り #12 で対応済みのはず」として `pnpm measure` の組み込み漏れを見逃す。

### `writing/dangling-quote-reference` — RESULTS.md の DR-0038 引用が実在しない

- **指摘した観点**: 日本語ドキュメント
- **累計**: 3回目（ルール化候補の閾値に到達）
- **何が起きているか**: 「DR-0038 が『App.tsx が design/theme.css を実消費するまでは分からない』と予告していた」という引用符付きの記述があったが、DR-0038 の実際の文言はこれと一致せず、しかも DR-0038 が予告していた問題（プレースホルダの `src/App.tsx` のまま実測すると `no-overflow` / `min-font-size` が実データ不在で誤って落ちる）と、今回実際に起きた問題（`getComputedStyle` が oklch() の計算値を返し、色の変換コードが例外で落ちる）は別の原因によるものだった。
- **なぜ問題か**: 存在しない引用は読み手がその文言で DR-0038 を検索しても見つからず、しかも「同じ種類の問題が的中した」という誤った理解を招く。実際には無関係な2つの問題を同一視している。

- **提案**: 引用符を外し、実際に起きたことと DR-0038 の懸念が別物である旨を正確に書き直す。
- **対応**: 修正済み。引用を削除し、両者が別原因であることを明記した上で、DR-0038 の完了条件が未達であることも同じ段落に追記した（上の指摘と合わせて1箇所で対応）。

### `contract/design-data-duplicated` — テストコメントが `design/tokens.json` の実値を前提にしていた

- **場所**: scripts/lib/color.test.mjs:118（修正前）
- **指摘した観点**: 設計契約との整合
- **累計**: 7回目
- **何が起きているか**: `parseCssRgb('oklch(0.21 0 0)')` のテストに「design/tokens.json の text（oklch(0.21 0 0)）は #181818 相当」というコメントが付いており、テストの入力値が実際のトークン値と一致することを前提にした説明になっていた。
- **なぜ問題か**: `design/tokens.json` の `text` トークンの値が将来変わると、このコメントだけが古い値を主張し続ける。テストの合否には影響しないが、正本の値がテストフィクスチャへ複製された形になっている。
- **失敗シナリオ**: `text` トークンの値を変更した際、このコメントを更新し忘れても検査は何も落とさない（テストは無関係な値でも通る）ため、古い記述がそのまま残り続ける。
- **提案**: コメントから正本の値への言及を外し、単なる無彩色の一例として書き直す。
- **対応**: 修正済み。「design/tokens.json の特定のトークン値との一致を意図したものではない」と書き直した。
