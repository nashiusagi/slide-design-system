## should

### inspection/rule-has-bypass — 疑似クラス引数の一律除外が `:not()` には正しいが `:where()` / `:is()` には成り立たず、新しい誤判定と抜け道を生んでいた

- **場所**: `scripts/validate-design.mjs`（`classesTargetedBySelector`、修正前の `insidePseudoArgument` 判定）、`docs/decisions/0041-postcss-for-layout-class-check.md`（決定・理由節）
- **指摘した観点**: 設計契約との整合、検査ルールの実効性、決定記録（DR）との整合、日本語ドキュメント（4観点から独立に指摘）
- **累計**: 12回目 → ルール化候補（継続）
- **何が起きているか**: 修正前の実装は、クラスノードの祖先を `parent` チェーンで辿り `pseudo` 型のノードに行き着けば、疑似クラスの種類を区別せず一律に除外していた。しかし `:not(.x)` は「`.x` を持つ要素を除外する」条件で `.x` 自身へスタイルを与えないのに対し、`:where(.x)` / `:is(.x)` は引数の要素そのものを選択する（詳細度が変わるだけ）ため実際にスタイルを与える。手元で実行して次を確認した。
  - `:where(.slide--bullets) { display: flex; }` だけで実装 → 「`.slide--bullets` を実装していない」と誤って missing 報告
  - `.slide--title {}` `.slide--bullets {}` を実装した上で `:is(.slide--rogue) { display: none }` を追加 → 契約に無い `.slide--rogue` の実装が extra として報告されない（削除された旧正規表現版はこれを拾えていたため、本 PR での回帰）
- **なぜ問題か**: `checkLayoutClasses` の目的は「`design/layout.css` がレイアウト契約の `classes` をちょうど実装しているか」を過不足なく検査すること（DR-0018 / DR-0030）。`:where()` / `:is()` は詳細度制御の実務上ごく普通の書き方で、DR-0011 が前提とする「AI が無人で生成ループを回す」状況では書かれ得る。誤判定の方向が両方向（実装しているのに未実装と出る／実装していないのに緑になる）にまたがっており、検査としての信頼性を損なう。
- **失敗シナリオ**: `design/layout.css` で共通の箱の性質を `:where(.slide--title, .slide--bullets, .slide--statement) { height: 100%; }` のようにまとめて書くと、契約どおり実装しているのに `pnpm design:check` が「`.slide--title` を実装していない」等で赤くなる。逆に `design/layouts/` から古いレイアウトの契約を削除した後も `design/layout.css` に `:is(.slide--old) { ... }` という形の実装が残っていると、`pnpm design:check` は緑のまま通る。
- **対応**: 除外対象を「引数のクラスが選択対象そのものにならない疑似クラス」（`:not` / `:has`）に限定した。`:where()` / `:is()` の引数内クラスは実装として数える。DR-0041 の決定・理由・帰結を新しい挙動に合わせて書き直し、`scripts/validate-design.test.mjs` に `:where()` / `:is()` を実装として正しく認めるケースと、`:is()` 越しの extra 検出ケースを追加した。

### decisions/citation-overclaims-source-scope — DR-0041 の帰結が、DR-0018 の「帰結」節に無い内容を「帰結が既に想定している」と引用していた

- **場所**: `docs/decisions/0041-postcss-for-layout-class-check.md`（帰結節）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 2回目
- **何が起きているか**: 「[DR-0018] の帰結が既にこの可能性を想定している」とあったが、DR-0018 の帰結節（2項目）は検査の仕組みの必要性と記述量の増加にしか触れておらず、CSS AST にも #7 での再利用にも触れていない。CSS AST への言及は DR-0018 の「理由」節（「素の CSS なら生の px や色値の検出を CSS AST で素直に行える」）にあり、しかも採用理由であって将来の再利用を想定した記述ではなかった。
- **なぜ問題か**: このプロジェクトは DR の帰結節を「実装されているか追跡する足場」として使っている。存在しない帰結を根拠にすると、#7 の担当者が DR-0018 を開いても裏付けを見つけられず、「DR-0018 が postcss 再利用を承認済み」という誤った既成事実だけが DR-0041 経由で残る。

### code/parse-error-crashes-validator（新規） — `postcss.parse` が不正な CSS で例外を投げ、以降の検査が一度も走らずに落ちる

- **場所**: `scripts/validate-design.mjs`（`checkLayoutClasses` 内の `postcss.parse` 呼び出し）、`main()` の `checks.flatMap`
- **指摘した観点**: 検査ルールの実効性、コード品質（2観点から指摘）
- **累計**: 1回目
- **何が起きているか**: `postcss.parse` は不正な CSS（例: `}` の閉じ忘れ）に対して `CssSyntaxError` を投げる。`checkLayoutClasses` はこれを捕まえておらず、`main()` の `checks.flatMap` にも try/catch が無いため、例外が未捕捉のまま抜け、`checkLayoutClasses` より後ろの5つの検査（layout/component 整合、lint/measure ルール対応、SKILL.md の複製検査、resolve スモーク）が一度も走らない。旧実装（正規表現）はどんな入力でも例外を投げなかったため、この失敗モードは本 PR で新たに入った。既存の `checkDecks` は構文エラーを try/catch し問題文字列として返しており、この検査だけ作法が揃っていなかった。
- **なぜ問題か**: 1つの構文エラーが他の検査結果を隠す。終了コードは非ゼロなので偽の緑にはならないが、`design/layout.css` 以外の問題（SKILL.md の設計データ複製等）が同時にあっても報告されない。

- **対応**: `checkLayoutClasses` 内で `postcss.parse` を try/catch し、`design/layout.css: CSS として解析できない: ...` という問題文字列を1件返して他の検査を継続させるよう修正した。回帰テストを追加した。
