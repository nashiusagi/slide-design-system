### `inspection/bundle-boundary-unchecked` — 「スライドのバンドルへカタログのコードが入らない」を保証する検査が無い

- **場所**: `vite.config.ts`:9-21 / `docs/decisions/0042-design-catalog-as-separate-build-entry.md`:24
- **指摘した観点**: 検査ルールの実効性、フェーズスコープ
- **累計**: 1回目
- **何が起きているか**: DR-0042 の決定1は「`src/docs/` から `src/App.tsx` や `src/runtime/` を参照せず、逆向きの参照も作らない」と規定するが、これを強制するものが無い。`eslint.config.js` に import 境界のルールは無く、`scripts/` にも `src/docs` を見る検査は無い。実ビルドでは現在、分離は成立している（`dist/index.html` は `assets/index-*.js` と共有の `jsx-runtime-*.js` のみを参照し、`docs-shell` / `docs-root` はカタログ側のアセットにしか現れない）。
- **なぜ問題か**: DR-0042 の理由節は「カタログのコードが混ざると measure が実測する物が本番と一致しなくなる」（DR-0011 / DR-0022）をこの決定の根拠に置いている。その根拠を支える性質が規約の遵守だけに依存し、破れたときに何も落ちない。

### `writing/inaccurate-rationale` — 「書式が違うので流用しない」という根拠が、実際の書式と食い違う

- **場所**: `src/docs/hash.ts`:7-8 / `docs/decisions/0042-design-catalog-as-separate-build-entry.md`:22
- **指摘した観点**: 日本語ドキュメント
- **累計**: 7回目
- **何が起きているか**: カタログ側は「スライドの hash は `#/<番号>/<段階>` で書式も対象も違う」と書くが、`src/runtime/hash.ts` の `formatHash` は段階 0 のとき `#/3` を返す。カタログの `PAGE_ID_PATTERN`（`/^#\/([a-z0-9-]+)$/`）は `#/3` に一致するため、両者の書式は実際には重なっている。
- **なぜ問題か**: この一文は「独立して持つ」という決定の根拠として DR-0042 とソースの両方に置かれている。根拠が実態と食い違うため、後続 Issue でページ ID を足す人が「スライドの hash とは絶対に衝突しない」と読み、数字だけのページ ID を安全だと判断し得る。
- **失敗シナリオ**: 該当なし（設計上の問題であり実行時の失敗ではない）。将来 `#/3` というページ ID を足すと、スライド URL とカタログ URL が同一文字列になる。
- **提案**: 書式の重なりを認めた上で、分離の理由（対象が違う）を書く。あわせて数字のみのページ ID を使わないことを規約として書く。

### `decisions/undocumented-decision` — 履歴を積む判断と、未知 hash のフォールバックが DR に無い

- **場所**: `src/docs/DocsApp.tsx`:20-24,45-53 / `src/docs/pages.ts`:14-22 / `docs/decisions/0042-design-catalog-as-separate-build-entry.md`
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 10回目
- **何が起きているか**: カタログの移動は素の `<a href="#/...">` で、クリックのたびに履歴が積まれる。その理由はコードのコメントにしかない。DR-0031 は「ページ送りは履歴を積まない（`history.replaceState`）」と決め、`pushState` 案を明示的に却下している。カタログが逆を採る理由は DR に無い。未知・不正な hash を先頭ページへ落とす判断も同様にコメントだけにある。
- **なぜ問題か**: 同じリポジトリで反対の結論が出ている判断なので、DR に無いと「DR-0031 に反している」と読まれるか、逆にカタログ側の方針がスライド側へ逆輸入される。PR とコードコメントは DR ほど参照されない。
- **失敗シナリオ**: 該当なし（設計上の問題であり実行時の失敗ではない）。後続 Issue の実装者が DR-0031 だけを読み、カタログの `<a href>` を `replaceState` へ「修正」する。
- **提案**: DR-0042 の決定1へ「カタログのページ移動は履歴を積む。DR-0031 が履歴を積まないと決めたのはスライドのページ送りであり対象が異なる」「未知・不正な hash は先頭ページへ落とす（404 ページを持たない）」を足し、関連に DR-0029 / DR-0031 を加える。

## consider

### `code/unreachable-defensive-branch` — 到達しない「ページが無い」分岐と、型の事実と食い違う根拠コメント

- **場所**: `src/docs/DocsApp.tsx`:6-16,55-57
- **指摘した観点**: コード品質
- **累計**: 1回目
- **何が起きているか**: `resolvePage` は戻り値型を `DocsPage | undefined` と宣言し、`DocsApp` が `page === undefined` の分岐を持つ。`DOCS_PAGES` は非空のリテラル配列で、`tsconfig` に `noUncheckedIndexedAccess` は無い（確認済み）。`DOCS_PAGES[0]` の型は `DocsPage` なので `undefined` は混ざらず、JSDoc の「型の上では空配列を取れる」は成立しない。
- **なぜ問題か**: 実行もテストもできない分岐と、事実と異なる説明が残る。`page?.id` の optional chaining も連鎖して増えている。
- **失敗シナリオ**: 該当なし（設計上の問題であり実行時の失敗ではない）。
- **提案**: 戻り値を `DocsPage` にして分岐と `?` を落とす。非空を型で固定したいなら `DOCS_PAGES` を `[DocsPage, ...DocsPage[]]` にする。

### `code/unvalidated-id-format` — ページ ID が hash の許容書式に収まる保証が型にもテストにも無い

- **場所**: `src/docs/hash.ts`:11,26-28 / `src/docs/pages.ts`:6-8,20-22
- **指摘した観点**: コード品質
- **累計**: 1回目
- **何が起きているか**: `parseDocsHash` は `^#\/([a-z0-9-]+)$` しか通さないが、`formatDocsHash` は受け取った文字列をそのまま連結する。`DocsPage.id` は素の `string` で、対応関係を検査する仕組みが無い。
