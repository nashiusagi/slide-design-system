## should

### contract/contract-structure-duplicated — layout / component 名の一覧が schema の enum とスクリプトの定数配列に複製されている

- **場所**: `design/schemas/layout.schema.json:14,51`、`design/schemas/component.schema.json:14,26`、`scripts/validate-design.mjs`（旧: `CONTRACTS` がファイル名を個別列挙）
- **指摘した観点**: 設計契約との整合
- **累計**: 2回目
- **何が起きているか**: 「有効な layout 名は title/bullets/statement」「有効な component 名は slide-title/bullet-list/statement/emphasis」という一覧が、2つのスキーマファイルの計4箇所の enum と、`validate-design.mjs` の `CONTRACTS` 配列（ファイルパスの個別列挙）に複製されていた。
- **なぜ問題か**: DR-0035 の帰結が「検査対象が増えたら `LAYOUT_NAMES` / `COMPONENT_NAMES` と `CONTRACTS` に1行ずつ足す」と書いており、複製を運用でカバーする前提になっていた。
- **失敗シナリオ**: Phase 1.5 で新しい layout を追加する際、`LAYOUT_NAMES` への追加を忘れると、`checkLayoutClasses` / `checkLayoutComponentConsistency` がその layout を検査対象に含めないまま `pnpm design:check` が緑になる。
- **対応**: `CONTRACTS` を `LAYOUT_NAMES` / `COMPONENT_NAMES` から `.map()` で導出するよう変更し、この2つの定数が唯一の名前の一覧になるようにした。スキーマの enum は JSON Schema の静的な列挙という性質上、完全な単一化はできないため、DR-0035 の帰結に「両方のスキーマの enum も合わせて更新すること」という注記を追加して残存する複製を明示した。

### contract/value-outside-source-of-truth — component の usage が、対応する layout の slots.max と同じ数値を平文で複製している

- **場所**: `design/components/slide-title.json`、`bullet-list.json`、`statement.json`、`emphasis.json` の各 `usage`。対応する `design/layouts/*.json` の `slots[].max`
- **指摘した観点**: 設計契約との整合
- **累計**: 3回目 → ルール化候補
- **何が起きているか**: 4つの component 契約すべてが、自分を使う layout の `slots.max` と同じ数値（すべて1）を `usage` の自然文としても独立に書いていた。DR-0035 は最大個数の正本を layout 側の `slots.max` と定めている。
- **なぜ問題か**: 現状は値が一致しているが、正本を参照できない場所に同じ値が独立して存在しており、layout 側の `slots.max` を変えても component 側の文言が自動追従しない。
- **失敗シナリオ**: Phase 1.5 で `bullet-list` を別の layout から `max: 2` として使うよう `slots` を変更しても、component 契約の「1 スライドにつき最大 1 つ」は追従しない。
- **対応**: 4つの component 契約すべての `usage` から個数の直書きを外し、「使ってよい個数は allowedIn の各 layout の slots が定める」という、正本を参照する記述に統一した。

### inspection/rule-coverage-partial — `checkLayoutComponentConsistency` が一方向（`slots` → `allowedIn`）しか検査していなかった

- **場所**: `scripts/validate-design.mjs`（旧実装）、`DESIGN.md`（「対応が崩れていないことは `pnpm design:check` が検査する」という記述）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 2回目
- **何が起きているか**: `component.allowedIn` に、実際にはその layout の `slots` から使われていない layout 名を書いても検出されなかった。手元で `bullet-list.json` の `allowedIn` に存在しない参照を混ぜて確認し、`[]`（問題なし）が返ることを確認した。
- **なぜ問題か**: 同じ diff で追加された `DESIGN.md` 自身が「対応が崩れていないことは `pnpm design:check` が検査する」と双方向であるかのように書いていたが、実装は DR-0035 に明記された2パターンしか見ていなかった。
- **失敗シナリオ**: `design/components/emphasis.json` の `allowedIn` に `"bullets"` を書き足しても、`design/layouts/bullets.json` の `slots` に `emphasis` を追加し忘れると `pnpm design:check` が緑のまま通る。
- **対応**: `checkLayoutComponentConsistency` に `allowedIn` → `slots` 方向の検査を追加し、双方向で矛盾を検出するようにした。DR-0035 の該当記述も両方向の検査内容に更新した。

### inspection/rule-has-bypass — `checkLayoutClasses` の正規表現が、宣言ブロック内の文字列もセレクタとして拾ってしまう

- **場所**: `scripts/validate-design.mjs`（旧実装の `matchAll(/\.([a-zA-Z0-9_-]+)/g)`）
- **指摘した観点**: 検査ルールの実効性
- **累計**: 5回目 → ルール化候補（継続）
- **何が起きているか**: コメント除去後の CSS 全体に対して `.` 始まりのトークンを拾っていたため、`:root { --debug-note: ".slide--bullets is not implemented yet"; }` のようなカスタムプロパティの値に含まれる文字列も「実装済み」と誤判定していた。実際にこの入力で `checkLayoutClasses` を呼び、`[]` が返ることを確認した。
- **なぜ問題か**: このチェックの目的（「layout.css がレイアウト契約の classes をちょうど実装しているか」）に対して、実装せずに検査を通す具体的な書き方が存在していた。
- **失敗シナリオ**: 実装が追いついていない段階で、開発者がクラス名をコメント以外の場所（プロパティ値など）に書き残すと、実際には見た目が一切実装されていないスライドが `pnpm design:check` を通過してビルドされる。
- **対応**: クラス名の抽出を「次の `{` の直前までの部分（セレクタ）」だけに限定し、宣言ブロックの中身は見ないように変更した。回帰テストを追加し、宣言ブロック内の文字列が実装と見なされないことを固定した。

### decisions/undocumented-decision — `props.type` を `string` / `string[]` に絞った理由が DR-0035 に記録されていなかった

- **場所**: `design/schemas/component.schema.json`（`type` の enum）、`docs/decisions/0035-layout-component-contract-shape.md`（旧稿）
- **指摘した観点**: 決定記録（DR）との整合
- **累計**: 6回目 → ルール化候補（継続）
- **何が起きているか**: DR-0035 は `props` の形を定めていたが、`type` に取りうる値を2種類（`string` / `string[]`）に絞った理由や、他の選択肢（boolean / number 等）を却下した記述が無かった。
- **なぜ問題か**: DR-0035 はまさに「layout / component 契約の具体的な形」を定める DR であり、他の選択肢がありえて選んだ理由を後から問われうる判断がこの DR の対象範囲そのものだった。
- **失敗シナリオ**: Phase 1.5 で真偽値の prop が必要な component が出てきたとき、この制限が意図的だったのか単なる現状追従だったのかが DR から判断できない。
- **対応**: DR-0035 の「決定」「理由」「検討した他の選択肢」の各節に、Phase 1 の4 component がすべて文字列かその配列で表現できるためこの2値に絞ったこと、他の型を今回対象外にしたことを明記した。

### writing/term-inconsistency — DESIGN.md 内で「layout / レイアウト」「component / 部品」が同一文書内で揺れている

- **場所**: `DESIGN.md`（Do / Don't リスト、優先順位リスト、参照リスト）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 6回目 → ルール化候補（継続）
- **何が起きているか**: 同じ概念を指すのに、箇条書きによって「レイアウト」「layout」、「部品」「component」を使い分けており、1つの Don't 項目の中で前半が英語・後半が日本語になっている箇所もあった。
- **なぜ問題か**: DESIGN.md は AI が最初に読む契約文書であり、呼称が揺れると横断参照時に取りこぼす可能性がある。README の正本表は既に「部品」を使っており、統一先も既に決まっていた。
- **対応**: `design/layouts/` のような実際のパス・フィールド名（コード表記）は残しつつ、地の文の概念語を「レイアウト」「部品」に統一した。あわせて Don't の2項目（契約に無い名前を使わない／独自実装を作らない）が同じ内容の言い換えだった箇所を1文に整理した。

### writing/ambiguous-criterion — `bullet-list.json` の usage が順序の許容度について自己矛盾していた

- **場所**: `design/components/bullet-list.json`（usage 2番目の項目）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 6回目 → ルール化候補（継続）
- **何が起きているか**: 「項目どうしに強い時系列や手順を持たせない。順序を示したいときはこの部品を使わない」という1つの箇条書きが、前半で「強い」時系列のみを禁止し、後半で強弱を問わず順序を示す意図があれば使用不可としており、二通りに解釈が割れた。
- **なぜ問題か**: AI がどちらの解釈を取るかで、許可される入力の範囲が変わる。`pnpm design:check` はこの意味的な曖昧さを検査できない。
- **対応**: 「強い」という程度表現を削り、「項目のあいだに時系列や手順の意味を持たせない。順序を示したいときはこの部品を使わない」という、強弱を問わない一貫した基準に書き換えた。

## consider

### writing/do-dont-asymmetry — 北極星「白い紙面」の比喩の暴走（紙・帳票的な装飾）を止める Don't が無かった

- **場所**: `DESIGN.md`（北極星、Don't リスト）
- **指摘した観点**: 日本語ドキュメント
- **累計**: 1回目（新規カテゴリ）
- **何が起きているか**: 北極星「白い紙面と黒い文字」は紙のメタファを含むが、Don't リストのどの項目も、紙・帳票を模した罫線や枠線を禁止する記述を持たなかった。DR-0007 が旧システムの「整った業務台帳」という比喩から言い換えた経緯があり、同種の暴走が起こりうる。
- **対応**: Don't リストに「北極星の『紙面』を字義通りに取らない。罫線・枠線・仕切り線で紙や帳票を模す装飾は作らない」という一文を追加した。判断は人に委ねられる項目だったが、低コストで契約の明確さが上がるため反映した。

## ルール化候補

- `contract/value-outside-source-of-truth` — 通算3回。正本の値が別ファイルの自由文へ複製されていないかを検査するルール（値そのものの一致ではなく「自由文に数値・識別子が直書きされていないか」を検出する形）が候補になる。
- `inspection/rule-has-bypass` — 通算6回（2周目で継続）。検査スクリプトの追加・変更時に、意図的に細工した invalid 入力（境界ケース）でのテストをレビューチェックリスト化する、あるいは正規表現ベースの検査を避ける方針を rules.json 相当の場に明文化することが候補になる。
- `decisions/undocumented-decision` — 通算6回。DR 作成時に「この DR が定める値・形の範囲を絞った理由」を明記するテンプレート項目を DR のフォーマット自体に追加することが候補になる。
- `writing/term-inconsistency` — 通算7回（2周目で継続）。プロジェクト全体の用語対応表（英語表記と日本語表記の対応）を1箇所に持ち、レビューでその表と突き合わせる運用が候補になる。
- `writing/ambiguous-criterion` — 通算6回。契約の usage / whenToUse 等の文言に「強い」「なるべく」等の程度語が使われていないかを機械的に検出する軽量な lint（語彙ブラックリスト方式）が候補になる。
- `decisions/dr-restates-canonical-value` — 通算4回（2周目で新規計上）。DR に `**正本**:` 行があっても値そのものを書き写せてしまう。DR のレビュー・執筆時に「正本のリテラル値を本文に書いていないか」を機械的に検出する軽量チェック（正本ファイルの既知の値一覧との文字列突き合わせ）が候補になる。

### should

#### inspection/rule-has-bypass — `checkLayoutClasses` 修正後も、属性セレクタの引用符付き値経由で同種の抜け道が残っていた

- **場所**: `scripts/validate-design.mjs`（`checkLayoutClasses` のセレクタ抽出部分）
