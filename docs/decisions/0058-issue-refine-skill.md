# DR-0058: 大きい Issue は `issue-refine` で現状把握・分割・4節への書き直しを行い、承認後に反映する

- **状態**: 承認済み
- **日付**: 2026-09-25
- **関連**: [DR-0024](./0024-decision-records-not-adr.md), [DR-0025](./0025-issue-driven-development-flow.md), [DR-0052](./0052-review-loop-third-exit.md)
- **正本**: `.claude/skills/issue-refine/references/issue-body.md`（本文の書式）／`.claude/skills/issue-refine/references/proposal.md`（提示と退避コメントの書式）
- **実装**: `.claude/skills/issue-refine/SKILL.md`（手順2 の分割の判定・手順4 の承認・手順5 の反映の順序）

## 文脈

最近の Issue（[#70](https://github.com/nashiusagi/slide-design-system/issues/70), [#73](https://github.com/nashiusagi/slide-design-system/issues/73)）は、1本に論点・人の判断待ち・実装作業が詰め込まれ、本文も長い。#73 は「(a)(b)(c) のどれを採るかは人が決める」と書いたうえで、決めた後の実装3ファイルの修正と測定の前提の書き直しまでを同じ完了条件に並べている。

[DR-0025](./0025-issue-driven-development-flow.md) の `issue-workflow` は、Issue の完了条件をそのまま実装のスコープにする。**判断待ちが混ざった Issue を乗せると、判断が出るまで手が止まる。** 大きい Issue を乗せると、1 PR に収まらずレビューの上限周回に当たりやすい——上限まで回して収束しないのは前提の問題であることが多い、という見立てを [DR-0025](./0025-issue-driven-development-flow.md) と [DR-0052](./0052-review-loop-third-exit.md) が持っている。

分割や書き直しは毎回手作業で行われていて、やり方がぶれていた（[#74](https://github.com/nashiusagi/slide-design-system/issues/74)）。

## 決定

### 1. `issue-workflow` の手前に、Issue を整える Skill を別に置く

`.claude/skills/issue-refine/` に置く。[DR-0025](./0025-issue-driven-development-flow.md) の帰結どおり、開発プロセスの Skill の系統として扱う。

**`issue-workflow` からは呼ばない。** 手順0 に「大きければ `issue-refine` へ」と組み込むことはしない。組み込むかどうかは、この Skill を何本かの Issue に当ててから決める。

### 2. 本文は親・サブとも4節で書く

「背景 / 解決したい課題 / やること / ゴール（チェックリスト）」。やらないことは「やること」の末尾に置き、独立した節にしない。

**本文に残すかどうかは、`issue-workflow` が実装か完了判定に使うかで決める。** 使わない経緯・実測・議論はリンクで渡す。

### 3. 分割は2つの判定のどちらかに当たったときだけ行う

1. **判断待ちと実装が混ざっている** — 判断を1本のサブ Issue にし、そのゴールを「DR に記録されている」にする。判断待ちに数えるのは、Issue が「人が決める」と明示している項目と、選択肢を並べて結論を書いていない項目だけ
2. **独立にマージできるまとまりが2つ以上ある** — 「それだけを先に main へ入れても `pnpm check` が通り、かつ元の本文が挙げている問題のどれか1つをそれだけで解消する」単位で数える。突き合わせるのは元の本文の問題で、書き直しで起こす「解決したい課題」ではない

分けるのは1階層だけで、親は閉じずに全体の目的とサブの並びを持つ場所として残す。サブ Issue は GitHub のサブ Issue 機能で親に紐づける。

### 4. 承認の前に GitHub へ何も書かない

案を会話で提示し、明示的な了承を得てから反映する。提示の中身は `references/proposal.md` が持つ。**本文案は親・サブとも全文を出す。****修正を求められたら、直した案をもう一度提示する。** 承認は提示した版に対するものだ。

### 5. 元の完了条件の行き先を表にして提示する

元の完了条件を1件ずつ、書き直し後のどの Issue のどの項目になったか、外したならその理由を並べる。

### 6. 反映は「退避コメント → サブ作成 → 親の書き換え」の順で行う

元の本文は、書き換えより先に親 Issue のコメントへ `<details>` で退避する。途中で失敗しても元の本文が失われない。

**先に作ったサブ Issue が後のサブ Issue を仮の名前（`サブ2` など）で指しているなら、全部を作り終えてから、親の書き換えの前にそのサブ Issue の本文を置き換える。** 番号は作るまで発番されないので、前向きの参照は作った時点では埋められない。置き換えるのは仮の名前だけで、承認された内容は変えない。だから承認をやり直さない——やり直すと、承認者に見せるのは番号が埋まっただけの同じ案になる。

#73 への最初の適用で、#76 の本文に「サブ2」が残ったまま作られた。この段はそれを受けて足した。

## 理由

- **判断と実装を分けると、`issue-workflow` が止まらない。** 判断のサブ Issue は人が決めて DR を書けば閉じ、実装のサブ Issue は決まった前提の上で完了条件を持てる。判断待ちを抱えたまま実装に入ると、完了条件の一部が満たせないまま PR が上限周回に当たる
- **分割の判定を長さや項目数で決めない。** 長い Issue が1 PR で済むこともあり、短い Issue に判断待ちが混ざることもある。粒度の問題は長さではなく、**`issue-workflow` がそのまま完了させられるか**で決まる。判定1・2はその2つの止まり方にそれぞれ対応している
- **判定2を「`pnpm check` が通り、課題のどれか1つを解消する」で書いたのは、読んだ人が同じ判定に到達できるようにするためだ。** 「1 PR に収まる大きさ」や「単独で意味を持つ」と書くと、何をもって収まる・意味があるとするかが人によって割れる。採った書き方では、`pnpm check` の部分はコマンドで、問題の解消の部分は元の本文が挙げている問題と1件ずつ突き合わせて確かめられる
- **承認を反映の前に置くのは、反映が取り消しにくいからだ。** 作ったサブ Issue は購読者に通知が飛び、削除には管理権限が要る。書き換えた本文は履歴に残るが、履歴は目立たず、読み手が見に行かない
- **行き先表が無いと、承認は形だけになる。** 本文案を読み比べて「何も落ちていない」ことを確かめるのは、承認する人にとって重い。表があれば元の項目を1行ずつ追える
- **退避を先にするのは、失敗の途中状態で元の本文が消えないようにするためだ。** 本文を先に書き換えて退避に失敗すると、元の本文は GitHub の編集履歴にしか残らない

## 検討した他の選択肢

### `issue-workflow` の手順0 に分割を組み込む

Skill が1本で済み、着手の前に必ず整う。

**却下理由**: `issue-workflow` は着手と同時にブランチと Draft PR を立てる。分割が要る Issue でそこまで進むと、どのサブ Issue のブランチなのかが後から変わる。また #74 の非スコープに「分割後の実装」が挙がっており、整える仕事と実装する仕事を同じ呼び出しに入れない方針と合う。組み込むかは決定1のとおり後で決める。

### 判断待ちを親 Issue のゴールに残し、実装だけをサブ Issue にする

サブ Issue の数が1つ減る。

**却下理由**: 親が「判断」と「集約」の二役を持つ。判断が済んだかどうかが、GitHub のサブ Issue の進捗表示から読めなくなる。判断の完了を DR の記録で閉じる単位として独立させた方が、何を待っているかが一目で分かる。

### サブ Issue を本文のタスクリスト（`- [ ] #N`）だけで繋ぐ

GitHub の機能に依存しない。

**却下理由**: 親子関係が本文の文字列にしか無く、サブ Issue の側から親へ辿れない。GitHub のサブ Issue は両方向に辿れ、進捗も親に表示される。#74 もサブ Issue としての紐づけを完了条件に挙げている。

### 元の本文は GitHub の編集履歴に任せる

コメントが1本減る。

**却下理由**: 編集履歴は本文の見出しの小さな表示からしか開けず、`gh` からも取りにくい。書き直しで詳しい経緯をリンクへ移す（決定2）以上、そのリンク先として目に見える場所に元の本文が要る。

### サブ Issue 同士の前向きの参照を、案の段階で禁じる

作成後の編集が要らなくなり、反映が「退避 → 作成 → 親の書き換え」の3段で閉じる。

**却下理由**: 判断のサブと実装のサブのように、先に作るサブが後のサブを指すのが自然な組み合わせがある（「実装は #77 が受け持つ」）。禁じると、その関係は親の本文にしか書けず、サブだけを読んだ人が辿れない。

### 分割を多階層にする

大きい Issue をさらに細かく分けられる。

**却下理由**: 階層が深いと、全体を知るにはどこを見ればよいかが消える。サブ Issue がさらに大きいと分かったら、提示の中でユーザーに伝え、扱いは人が決める（`SKILL.md` は既にサブ Issue である Issue を分割しない）。

## 帰結

- `issue-refine` の手順・書式を変えるときは、この DR を読んでから行う。分割の判定（決定3）・承認の位置（決定4）・反映の順序（決定6）を変えるなら、この DR を置き換える
- `issue-workflow` から `issue-refine` を呼ぶかどうかは未決定のまま残る。決めるときは新しい DR を立て、[DR-0025](./0025-issue-driven-development-flow.md) との関係を書く
- 既存の Issue を一括で書き直すことはしない。`issue-refine` は1回に1本の Issue を扱う
