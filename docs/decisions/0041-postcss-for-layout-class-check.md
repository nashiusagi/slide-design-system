# DR-0041: `checkLayoutClasses` は postcss + postcss-selector-parser の構文木で判定する

- **状態**: 承認済み
- **日付**: 2026-09-10
- **関連**: [DR-0018](./0018-plain-css-with-tokens.md), [DR-0032](./0032-ajv-for-contract-validation.md)
- **実装**: `scripts/validate-design.mjs`（`checkLayoutClasses`）

## 文脈

`checkLayoutClasses`（`design/layout.css` がレイアウト契約の `classes` を実装しているかの検査）は、正規表現で「セレクタらしき部分」を判定していた。PR #21 のレビューで3周にわたり、同じ性質（実装ではない場所に書かれた文字列を実装済みと誤判定する）の抜け道が形を変えて見つかった。

1. コメント内の文字列（1周目、修正済み）
2. 属性セレクタの引用符付き値（2周目、修正済み）
3. 疑似クラスの引数（`:not()` / `:where()`）、属性値内に `]` を含む属性セレクタ（3周目、レビュー上限で未修正のまま打ち切り）

2回は直したがそのたびに別の構文経路が見つかり、3周目も同じ性質の指摘だった。個々のパッチの不備ではなく、**正規表現でセレクタの構造を判定するアプローチ自体**がこの種の不具合を構造的に生み続けていた（詳細: `docs/reviews/pr-21.md` の見立て）。

## 決定

CSS を `postcss` でパースして構文木を得たうえで、`root.walkRules()` で拾った各ルールのセレクタ文字列を `postcss-selector-parser` でさらに構造化し、クラスセレクタのノードだけを集める。両方を devDependency に追加する。

ただし、引数の中のクラスセレクタが要素自身を選択対象にしない疑似クラス（`:not(...)` / `:has(...)`）の関数引数の中にあるクラスセレクタは対象から除く。`:not(.x)` は「`.x` を持つ要素を除外する」条件であり、引数の `.x` そのものへスタイルを与えている（=実装している）ことを意味しない。`:has(.x)` も、実際に選択・スタイリングされるのは外側の要素であって引数の `.x` ではない点で同じ。除外は、対象ノードの祖先を `parent` チェーンで辿り、`pseudo` 型かつ引数がこの2つに該当するノードに行き着くかどうかで判定する。

一方 `:where(.x)` / `:is(.x)` は引数の要素そのものを選択する（詳細度が変わるだけ）ため対象から除かない。`:where(.x) { color: red }` は `.x` を実際に赤くする。ここまで除外に含めると、`:where()` / `:is()` で書かれた実装を「実装していない」と誤判定し、逆に契約に無いクラスを `:is()` の引数だけで実装しても検出されなくなる（レビューで実際にこの誤判定を確認した）。

## 理由

- **構文木を使えば、コメント・宣言ブロックの値・属性セレクタの値は、そもそもセレクタとして通る経路に存在しない。** 正規表現でこれらを個別に除外する条件を積み増す必要が無くなる。3周のレビューで見つかった4種の抜け道（コメント内の文字列・属性セレクタの引用符付き値・属性値内の `]`・疑似クラス引数）のうち、疑似クラス引数を除く3種は、構文木を使うだけで追加のコードを書かずに解消した
- 属性値内に `]` を含む属性セレクタ（`[data-x="].foo"]`）は、引用符付き文字列を正しくトークナイズできて初めて安全に扱える。自前の正規表現でこれを再現するのは、まさに3周にわたって割れ続けた前提であり、実績のあるパーサに委ねる方が確実
- `postcss` は、`theme.css` を生成する `scripts/generate-theme.mjs`（素の文字列操作のままで、今回変更しない）とは独立に、ここでは `checkLayoutClasses` の CSS 構文解析だけに使う軽量な依存で、ビルド成果物（`dist/`）には入らない（[DR-0022](./0022-plain-vite-build-output.md)と同じ整理）
- 検証の呼び出しは `scripts/validate-design.mjs` に集約する既存の方針（[DR-0032](./0032-ajv-for-contract-validation.md)）をそのまま踏襲できる

## 検討した他の選択肢

### 正規表現に抜け道潰しのパッチを追加し続ける

依存が増えない。

**却下理由**: 3周のレビューで実証済みの通り、正規表現でセレクタ構造を判定するアプローチ自体が同じ性質の不具合を繰り返し生む。個別のパッチは対症療法であり、次の構文経路（例: ネストしたセレクタ、コメントを含む複雑な属性値）が見つかるたびに同じサイクルを繰り返すことになる。

### 「クラス名がセレクタに現れるか」ではなく「そのクラスに実際に宣言を持つルールが存在するか」で判定する

Issue #22 が提示したもう一方の案。「実装済み」の定義を、セレクタの構文的な一致からスタイルの有無へ変える。

**却下理由**: この案でも、宣言が0件の空ルール（`.slide--x {}`）を「未実装」として弾くという副次効果はあるが、セレクタ自体をどう読むか（コメント・属性値・疑似クラス引数を除外する必要性）という3周分の抜け道は、結局セレクタの構文解析が要る。構文木を導入すればこちらの判定（宣言の有無）も同じ構文木の上に追加できるため、今回は範囲を広げず「セレクタの構文解析」だけを解決した。空ルールを弾く判定が必要になったら、既に導入した構文木の上に追加する。

### `postcss-selector-parser` を使わず、`postcss` が返すセレクタ文字列に対して独自の簡易パーサを書く

依存を1つ（`postcss` のみ）に抑えられる。

**却下理由**: セレクタ自体の構文（属性値の引用符、疑似クラスの引数の入れ子）を正しく読む部分こそが3周にわたって割れ続けた箇所であり、そこを自前実装に戻すと同じ不具合を再発させかねない。`postcss-selector-parser` は `postcss` エコシステムの標準的なセレクタパーサであり、ここを実績のある実装に委ねる。

## 帰結

- `packages/eslint-plugin-slide`（#7）の `no-raw-color` 等、生成されたスライドの CSS を検査するルールでも、同種の CSS 構文解析が要る場面があれば、ここで入れた `postcss` を再利用できる。[DR-0018](./0018-plain-css-with-tokens.md) の理由節が「素の CSS なら生の px や色値の検出を CSS AST で素直に行える」としており、同じ CSS 構文木への投資を #7 でも再利用できる可能性がある。ただし #7 でどのパーサを使うか・実際に再利用するかは、この DR では決めない
- `checkLayoutClasses` のテストに、`:not()` の引数・属性値内の `]` を使った invalid ケースと、`:where()` / `:is()` の引数を実装として正しく認める（かつ contract に無いクラスを `:is()` 越しに実装しても extra として検出する）ケースを追加し、3周目で見つかった抜け道とレビューで見つかった誤判定を回帰として固定した
- `design/layout.css` は、契約クラスを `:not()` / `:has()` の引数だけで書くと未実装として扱われる。`:where()` / `:is()` の引数であれば実装として認められる
- `postcss.parse` が構文エラーで例外を投げた場合は、他の検査（`design:check` の残りの項目）を止めずに進められるよう、`checkLayoutClasses` 内で捕まえて問題文字列に変換する（`checkDecks` が構文エラーを扱う形と揃える）
