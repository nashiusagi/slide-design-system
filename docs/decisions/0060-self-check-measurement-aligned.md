# DR-0060: `済` の定義は `self-check.md` だけが持ち、1周目の計上はレビュー記録からスクリプトで数える

- **状態**: 承認済み
- **日付**: 2026-10-11
- **関連**: [DR-0053](./0053-review-coverage-recorded.md), [DR-0057](./0057-self-check-before-ready.md), [DR-0059](./0059-self-check-done-covers-ready-diff.md)
- **正本**: `.claude/skills/issue-workflow/references/self-check.md`（`済` の定義と `読み返した head` 欄）／`docs/review_log.md`（数え直した基準値と、測定・再現の手順）／`.claude/skills/pr-review/references/review-file-format.md`（`対象コミット` 欄）
- **実装**: `scripts/count-first-round-findings.mjs`（1周目の切り出しと計上）

## 文脈

[DR-0059](./0059-self-check-done-covers-ready-diff.md) は、セルフチェックの `済` が保証する範囲を Ready 化時点の差分に限り、[DR-0057](./0057-self-check-before-ready.md) 決定7 の計上回数と基準値を1周目の指摘だけで数えると決めた。実装を揃える作業は [#77](https://github.com/nashiusagi/slide-design-system/issues/77) に渡された。

揃える前の状態には3つの穴があった。

- **`済` を説明する場所が3つあった。** `self-check.md` の「この段を通した PR の数え方」、`docs/review_log.md` のレビュー履歴表の「セルフチェック」列、`review-log-format.md` の「更新の手順」。DR-0059 決定2 の「何を保証するか」はどこにも書かれていなかった。どれか1つだけを直すと、[PR #72](https://github.com/nashiusagi/slide-design-system/pull/72) で繰り返し出た「正本と実体のずれ」を再生産する
- **1周目の計上回数を出す手順が無かった。** `docs/review_log.md` は全周の累計しか持たない。基準値も全周で数えた値のままで、DR-0059 の帰結により比較には使えない
- **1周目が Ready 化時点の差分を見たかを確かめる材料が無かった**（DR-0059 帰結）。レビュー記録の冒頭欄は `base...head` のブランチ名しか持たず、見たコミットが残らない

## 決定

### 1. `済` の定義は `self-check.md` の「この段を通した PR の数え方」だけが持つ

判定の条件（DR-0057 決定4・決定6）、`済` が保証する範囲（DR-0059 決定2）、内容が誤っていた PR を区別しないこと（DR-0059 決定5）を、すべてこの節に置く。

`docs/review_log.md` と `review-log-format.md` は、`済` / `—` の値と、定義がこの節にあることだけを書く。**定義の中身——条件も、保証する範囲も、内容が誤っていた PR の扱いも——を書き写さない。** 記録の手順（`review-log-format.md`）が持ってよいのは、いつ書き、いつ書き換えないかという記録の操作だけだ。

### 2. 1周目は、レビュー記録の先頭から最初の `## <N>周目` 見出しまで

`review-file-format.md` は、2周目以降を `## <N>周目（YYYY-MM-DD）` の節として末尾に追記すると定めている。その手前が1周目だ。PR #72 のマージ直前の記録28本で、この切り方が古い書式でも成り立つことを確かめた（カテゴリID形の見出しの取りこぼしは0件）。

計上は `scripts/count-first-round-findings.mjs` が行う。1つのカテゴリは1つの PR につき1回で、`docs/review_log.md` と同じ数え方になる。**人が記録を読んで数えない。** 根拠として挙げた集計が再現しないことは、`decisions/cited-tally-not-reproducible` として繰り返し指摘されている。

対象カテゴリは、**いまの** `docs/review_log.md` の候補表で状態が `セルフチェックで扱う` のものを読む。基準値を出す時点の表は使わない——その時点ではまだ状態が付いていないからだ。

### 3. 基準値は、PR #72 のマージ直前の履歴表の全 PR について、同じスクリプトで数え直す

母集団は DR-0059 決定4 のとおり。値と再現のコマンドは `docs/review_log.md` の候補表前書きが持つ。全周で数えた旧値は残すが、比較には使わない。

### 4. 1周目に観点が欠けたかは、`立った観点` 欄から機械的に判定する

`立った観点` 欄に、`pr-review` の観点表の観点がすべて並び、どれにも `（結果なし）` が付いていなければ欠けていない。欄の各要素は、観点表の名前そのものか、名前 + `（結果なし）` に完全一致しなければ読めないものとし、欠けた側に倒す——括弧を剥がして照合すると、書式外の注記（`（結果なし：タイムアウト）` など）が剥がれて「立った」と数えられる。**欄が無い記録は、欠けた側に倒す**——確かめられないなら母数に入れない（DR-0059 決定3）。スクリプトは測定のときだけこの除外を当てはめ、基準値には当てはめない（DR-0059 決定4）。

### 5. 読み返した地点と1周目が見た地点を SHA で残し、一致するかで確かめる

セルフチェックのコメントに `読み返した head` を、レビュー記録の冒頭欄に `対象コミット` を足す。どちらも **PR の head の SHA**（`gh pr view <N> --json headRefOid`）で取る。`対象コミット` は1周目の値を残し、再レビューでは書き換えない。2つが一致すれば、1周目はセルフチェックと同じ差分を見ている。

どちらの欄も `済` の条件にはしない。

**一致しないことを母数から除く条件にもしない。** DR-0059 決定3 は、記録が無いことを理由にこの条件を除外へ入れなかった。欄が入っても、欄を持たない PR（PR #75・#78・#79）が既に測定の母数にいる。除外に格上げするかは、最初の測定を経てから決める。それまでは DR-0059 の帰結のとおり、基準値を下回ったときに確かめる。

## 理由

**定義を1箇所に寄せるのは、PR #72 の3周がそこで壊れたからだ。** `済` の判定を具体化するたびに、列の説明と更新の手順のどちらかが古いまま残った。参照する側が「どこにあるか」だけを持てば、定義が動いても参照は外れない。

**置き場所に `self-check.md` を選ぶのは、判定の条件が既にそこにあるからだ。** 保証する範囲は判定の条件と対になっていて、離すと「条件を満たした＝内容が正しい」と読まれる余地が戻る。`docs/review_log.md` は数える場所で、定義する場所ではない。

**スクリプトにするのは、数える量が人手で再現できる量を超えているからだ。** 基準値だけで28本の記録を読み、見出しの書き方は2通りに割れている。既に `select-review-findings.mjs` が同じ記録を指摘単位へ分解しているので、それを使えば分解の規則も1箇所に保てる。

**2つの SHA を足すのは、DR-0059 が残した唯一の「確かめられない前提」を、等しいかどうかの比較だけで確かめられる形にできるからだ。** DR-0059 決定2 の「Ready 化の時点の差分」は、Ready 化の時刻からは決められない——その時点でリモートにあったコミットは、時刻からは分からない。`issue-workflow` 手順2 はセルフチェックのコメントを出してから Ready にするので、読み返した head を Ready 化時点の head の代わりに使う。間に push があれば2つは一致しなくなり、それも捕まる。

**PR の head で取るのは、1周目が読むのが `gh pr diff <N>` だからだ。** `pr-review` は番号さえあればどのブランチからでも呼べるので、ローカルの `HEAD` は見た差分と食い違いうる。

## 検討した他の選択肢

**`済` の定義を `review-log-format.md` に置く。** 列を書く手順と定義が隣り合う。採らないのは、判定の条件が `self-check.md` にあり、そちらを動かすと DR-0057 決定4・決定6 の正本が移るからだ。条件と保証範囲を離す理由もない。

**1周目の切り出しを手順の文章だけで定め、人が数える。** コードが増えない。採らないのは、28本を人が数えると、数えるたびに値がずれうるからだ。PR #72 では、根拠として書いた集計が翌日に再現しなかった。

**`対象コミット` を足さず、Ready 化後のコミットを git の履歴から推定する。** 書式が増えない。採らないのは、`issue-workflow` 手順4 がレビュー成果物と修正の順序を固定していないからだ。1周目の修正が記録より先にコミットされうるので、履歴だけでは1周目が見た地点を特定できない。

**`対象コミット` のコミット時刻を Ready 化イベントの時刻と比べる。** セルフチェック側に欄を足さずに済む。採らないのは、コミット時刻が push の時刻ではないからだ。Ready 化より前に作り、後で push したコミットを「足されていない」と判定する。

**`対象コミット` をローカルの `git rev-parse HEAD` で取る、または `issue-workflow` 手順3 が控えた HEAD を渡す。** 手順3 は呼ぶ直前に HEAD を控えるが、`pr-review` へ渡すのは2周目以降の前周コミットだけだ。1周目にも渡すよう手順を変えるより、`pr-review` が自分の読む差分と同じ出どころ（PR の head）から取る方が、食い違う経路が少ない。ローカルの `HEAD` を採らない理由は「理由」のとおり。

**Ready 化から1周目までにコミットが足された PR を、母数から除く。** 射程のずれを記録で閉じられる。採らないのは決定5 のとおりで、欄の無い PR が既に母数にいる。

## 帰結

- `self-check.md` の「この段を通した PR の数え方」に、`済` が保証する範囲と、内容が誤っていた PR の扱いが入る。`docs/review_log.md` と `review-log-format.md` は、そこを参照するだけになる
- `docs/review_log.md` の基準値が1周目だけで数えた値へ替わる。DR-0059 の帰結にある「揃うまでは基準値（全周）を比較に使わない」は、この DR で揃った
- `scripts/count-first-round-findings.mjs` は `select-review-findings.mjs` のパーサに依存する。あちらの書式の解釈が変われば、計上回数も動く。実在のレビュー記録すべての1周目が取りこぼしなく読めることを、テストが固定している
- セルフチェックのコメントに `読み返した head` が、レビュー記録の冒頭欄に `対象コミット` が増える。この DR より前の記録には無い
- 対象カテゴリはいまの候補表から読む（決定2）ので、**状態が `セルフチェックで扱う` に変わる・外れるたびに、`docs/review_log.md` の基準値を同じコマンドで数え直す。** DR-0057 決定7 の「対象8カテゴリ」の8は、この DR の時点の数だ。分子と基準値を別のカテゴリで数えると、DR-0059 が閉じた射程のずれが別の形で戻る
