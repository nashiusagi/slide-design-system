# DR-0056: スライドが keyMessage を伝えているかを、レイアウトの役割ごとの軸で判定する

- **状態**: 承認済み
- **日付**: 2026-09-24
- **関連**: [DR-0011](./0011-lint-and-measure.md), [DR-0028](./0028-single-check-entry-point.md), [DR-0038](./0038-defer-measure-in-check.md), [DR-0044](./0044-bypass-fixtures-required.md), [DR-0046](./0046-prose-checked-for-canonical-duplication.md)
- **正本**: `design/rules.json`
- **実装**: `scripts/score-slide-content.mjs`

## 文脈

measure は「はみ出したか」「文字が小さすぎないか」「コントラストが足りるか」を見る。lint は部品の使い方を見る。**そのスライドが伝えたいことを伝えられているかは、どちらも見ていない。**

判定の正解軸は既に契約にある。deck 契約の `keyMessage` は必須で、「そのスライドで伝える一文」と定義されている（`design/schemas/deck.schema.json`）。**書かれているのに、書かれたとおりになっているかを確かめる経路が無い。**

使い捨てのプロトタイプで [`experiments/harness-intro`](../../experiments/harness-intro/) の保存 Run を採点し、3つのことを確かめた。

**判定は本物の穴を当てる。** 1枚目は契約が `AI に契約を渡してスライドを書かせる仕組みを紹介する` と言うのに、表示文字に「契約」が一言も無く、低いスコアが付いた。

**既存の検査と独立している。** `harness-corrected-1` は lint / measure の違反を直した Run だが、中身のスコアはほぼ動かなかった。見た目の契約違反を直しても伝わり方は変わらない。この軸が既存の穴を埋めている。

**契約どうしが衝突した。** `design/layouts/title.json` は title の役割を「情報を足さず、これから何を話すかだけを示す」と定める。一方で「keyMessage が過不足なく伝わるか」を一律に問うと、**title は構造的に低スコアになる。**

## 決定

### 1. 判定は既存の契約から組み立てる

何を伝えるはずかは deck 契約の `keyMessage` から、どの役割を担うはずかとどのレイアウトが向くかは `design/layouts/*.json` の `role` / `whenToUse` / `whenNotToUse` から、実行時に読む。**実装へ書き写さない**（[DR-0046](./0046-prose-checked-for-canonical-duplication.md)）。

### 2. 「伝わる」の意味をレイアウトごとに変える

`role` を判定の指示へ流し込み、その役割が求めることを果たしているかを問う。title なら「次に何を話すかが分かるか」、statement なら「主張がそのまま伝わるか」。

**閾値を下げて回避しない。** title が低く出るのは軸が役割と噛み合っていないからで、合格線を動かしても「なぜ動かしたか」が残らない。

判定の**刻み**（4段階）は実装が持つ。刻みまで契約から取ろうとすると、全レイアウトの契約へ同じ4段階を書くことになり、正本が増える。

### 3. 閾値は `design/rules.json` に置く

`keyMessageConveyed` と `layoutFit` の2ブロックに分ける。他の閾値（`minFontSize` / `noOverflow` / `contrast`）と同じ扱いで、**ブロック名はルールIDから引ける形にする**——カタログ（`#/rules`）が閾値をルールの下に並べるとき、この対応で引いている。

**確信度の線はルールごとに別に持つ。** 一方は順序のある4段階の分布の集中度、もう一方は並列な選択肢の分布の集中度で、同じ値が同じ割れ方を指さない。値が偶然同じでも、片方を動かす理由がもう片方に及ぶとは限らない。

**現在の値は暫定で、根拠は段階の定義から導いた理屈だけだ。** サンプルが1つの deck・3枚・2 Run しかない。実測の分布を見て決め直す。その旨は正本側の `$comment` に書いてある。

### 4. `pnpm check` には組み込まない

外部 API（TypeSafe）を使うため、**ネットワークと API キーを `check` の必須依存にしない**。[DR-0038](./0038-defer-measure-in-check.md) が measure について同じ判断をした前例に倣う。[DR-0028](./0028-single-check-entry-point.md) の「検査の実行口は `pnpm check` に一本化する」からの意図的な例外で、`pnpm score:content` を単独の入口として持つ。

**キーが無ければこのコマンド自身が落ちる。** 無言で飛ばす経路は作らない。飛ばせるようにすると、緑が「検査を通った」を意味しなくなる。

判定ロジックのテストは `pnpm test`（つまり `check` の中）で走る。**テストは API を叩かない**——リクエストの組み立てと結果の畳み方だけを固定する。

### 5. 役割の判定とレイアウトの判定を、別のリクエストに分ける

「役割を果たしているか」には宣言済みのレイアウトが要る。「どのレイアウトが向くか」にそれを渡すと、宣言をなぞるだけになる。1つの入力に両方の質問を置くと、宣言が漏れていないことを確かめられない。

### 6. bypass フィクスチャを要求しない

`method: "content"` は `pnpm check` の中で機械に走らせる入口を持たない（決定4）。事例を要求しても実行できず、宣言だけの飾りになる。[DR-0044](./0044-bypass-fixtures-required.md) が `review` を外したのと同じ理由で外す。

**どの method が外れるかの正本は `scripts/lib/bypass-fixtures.mjs` に置く。** これまで `review` の判定が2箇所に複製されており、method が増えたときに片方だけが古くなる形だった。

### 7. 枚数が食い違う Run は採点しない

契約の枚数と描画された枚数が違うとき、位置で対応づけると別のスライドどうしを比べることになる。黙って続けず落とす。どの描画スライドがどの `keyMessage` に対応するかを当てる工程は、この検査の範囲外。

## 理由

**正解軸を新しく作らない。** `keyMessage` は既に必須の契約で、AI が判断の軸にすることになっている。その軸で生成させておいて、その軸で測らないのは片手落ちだ。

**役割ごとに軸を変えるのは、契約がそう書いてあるからだ。** `layouts/*.json` は各レイアウトが何をする場所かを既に定義している。一律の軸を当てるほうが、契約を無視していることになる。

**`check` へ入れないのは、緑の意味を守るためだ。** `check` が外部サービスの可用性に依存すると、落ちたときに「設計が壊れた」のか「ネットワークが切れた」のかを緑・赤から読めなくなる。DR-0038 が measure について同じことを言っている。

## 検討した他の選択肢

**閾値をレイアウトごとに変える（決定2 の代案）。** 問いは共通のまま、title は合格線を下げる。スコアがレイアウトをまたいで比較可能なまま残る利点がある。採らないのは、**合格線の差が「なぜその差なのか」を持たない数字になる**からだ。役割の違いは契約に書いてあるので、そちらを軸へ流し込むほうが根拠が残る。

**title を採点対象から外す（同上）。** 一番単純だが、title が崩れても検出できなくなる。「これから何を話すかを示す」ことにも失敗しうる。

**`pnpm check` へ入れる（決定4 の代案）。** 検査の単一入口（DR-0028）に揃う。採らない理由は上記。将来、判定をネットワーク無しで行えるようになれば再検討の余地がある。

**1リクエストにまとめる（決定5 の代案）。** 安く速い。採らないのは、同じ入力に宣言済みのレイアウトを置くと、レイアウト判定がそれを見ていないことを確かめられないからだ。**確かめられない設計は、確かめなくてよい設計とは違う。**

**プロトタイプのままリポジトリの外に置く。** 外部依存を持ち込まずに済む。採らないのは、実際に一度消えたからだ。再現できない検査は検査として使えない。

## 帰結

- `design/rules.json` に `method: "content"` のルールが2つ（`key-message-conveyed` / `layout-fit`）と、それぞれの閾値ブロックが入る。**ルールは契約の並びの末尾へ置く**——カタログは method ごとに束ねる際に契約の並びを保つので、同じ method が連続していないと一覧の順が崩れる。`design/schemas/rules.schema.json` が `content` を method の選択肢へ加える
- `pnpm score:content` が単独の入口になる。`pnpm check` の段には入らない
- `method: "content"` は bypass フィクスチャを要求しない。どの method が外れるかは `scripts/lib/bypass-fixtures.mjs` の `METHODS_WITHOUT_FIXTURES` が持ち、`scripts/validate-design.mjs` はそれを参照する
- ビルド出力を配信する静的サーバは `scripts/lib/static-server.mjs` に一本化する。measure と content の両方が同じ出力を開くため、それぞれが持つと配信できる拡張子の一覧が片方だけ古くなる
- **スコアはレイアウトをまたいで比較できない。** 同じ 2.5 が title と statement で違うことを意味する。レイアウト間の優劣を論じる用途には使えない
- 判定は外部サービスの応答に依存する。同じ入力でも値は完全には再現しない。閾値の近くに集まる判定は、確信度で人へ回す（決定3）
