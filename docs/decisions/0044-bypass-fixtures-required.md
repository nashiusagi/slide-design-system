# DR-0044: 検査ルールには bypass フィクスチャを伴わせ、守備範囲を契約で宣言する

- **状態**: 承認済み
- **日付**: 2026-09-11
- **関連**: [DR-0011](./0011-lint-and-measure.md), [DR-0033](./0033-derived-values-are-generated-and-checked.md), [DR-0037](./0037-eslint-plugin-slide-rule-scope.md)
- **正本**: `design/rules.json` の各ルールの `bypassAxes` / `scopeExclusions`（軸と除外の宣言）

## 文脈

[指摘ログ](../review_log.md)で単一カテゴリの最多は `inspection/rule-has-bypass` である。「検査ルールに抜け道があり、書き方を変えると素通りする」という指摘で、PR #13 から PR #40 まで通算13回出ている。周辺の `rule-coverage-partial` / `rule-scope-inconsistent` / `invalid-case-untested` を合わせると24回になる。

繰り返される構造は単純だ。検査ルールを書くとき、テストには「捕まえたい違反」を並べる。捕まえたい違反はルールを書いた本人が考えたものだから、当然捕まる。緑になる。素通りする書き方は、本人が思いつかなかった書き方であり、だからテストにも無い。レビュアーが別の頭で読んで初めて出てくる。13回それが起きたということは、レビュアーの頭を13回借りたということでもある。

守備範囲の食い違い（`rule-scope-inconsistent`、通算4回）も同じ根を持つ。「このルールは何を見ないか」がルール実装のコメントに散文で書かれ、正本（`design/rules.json` の description）や DR と別々に書き換わる。[PR #40 のレビュー](../reviews/pr-40.md)では、`no-raw-scale` の守備範囲を CSS ファイルまで含むかのように引用したコメントが指摘されている。

## 決定

自動判定を持つ検査ルール（`design/rules.json` の `method` が `lint` / `measure` のもの）は、次の2つを伴わなければ `pnpm check` を通らない。`method: "review"` は人が判断し自動判定を持たない（[DR-0011](./0011-lint-and-measure.md)）ため対象外で、理由は帰結に書く。

**1. 軸の宣言と、軸ごとの bypass フィクスチャ。** `design/rules.json` の各ルールは `bypassAxes` を持つ。軸は「同じ違反を別の書き方で表す種類」であり、語彙は4つ——`alternate-notation`（記法を変えた同値）、`value-composition`（複数の値が1つの値に同居する形）、`boundary`（閾値の両側）、`enumeration-tail`（列挙で定義した対象の、先頭以外の要素）。宣言した軸ごとに、違反として捕まる事例をフィクスチャへ置く。`boundary` だけは通る側の事例も要求する。

**2. 除外の宣言と、通ることを固定する事例。** 同じく `scopeExclusions` に「意図的に見ない領域」を id と説明で列挙し、id ごとに「通る」事例をフィクスチャへ置く。**ここに挙がっていない見落としは、除外ではなく抜け道である。**

フィクスチャの置き場所は method で決まる（`scripts/lib/bypass-fixtures.mjs` の `fixturePathFor` が唯一の定義）。実行の入口は method ごとに1つだけ置き、`design/rules.json` を端から回してすべての事例を走らせる。ルールごとにテストを書き足す形にはしない——書いたのに走らせ忘れる、という抜け方を作らないためである。

あわせて、**ルール実装の `meta.docs.description` は `design/rules.json` から引く**。実装側に書き下ろすと、同じルールの守備範囲を述べる場所が2つになる。

## 理由

- **軸を先に宣言させると、抜け道の探索が設計の一部になる。** 事例を書く手間より、「このルールにはどの軸があるか」を考える段が入ることに意味がある。13回の指摘は、その段が無いために外注されていた
- **除外を契約に置くと、見落としと意図的な除外が区別できる。** 今までどちらもコメントに書かれていて、読み手には区別が付かなかった。契約に無い素通りは、議論の余地なく抜け道になる
- **`boundary` で両側を要求するのは、片側だけでは判定を厳しくする変更を捕まえられないからだ。** 「閾値を割ったら落ちる」しか固定していないと、閾値ちょうどで落ちるようになっても誰も気付かない
- **実行の入口を1つにしたのは、フィクスチャが宣言だけの飾りになる経路を塞ぐため。** 検査（宣言を埋めているか）と実行（事例が実際に通る／落ちるか）の両方が無いと、どちらか片方をすり抜けられる
- **説明を正本から引くのは、一致させる努力より、複製しない方が確実だからだ**（[DR-0033](./0033-derived-values-are-generated-and-checked.md) と同じ形）

## 検討した他の選択肢

### 軸を宣言させず、フィクスチャの存在だけを必須にする

仕組みが小さく済む。

**却下理由**: 存在だけを問うと、既に捕まえている書き方をもう1つ書いて終わる。埋めるべき枠を先に決めないと、埋める側は自分が思いつく範囲から出ない。それは今のテストが既に持っている範囲であり、13回の指摘は正にその外側から来ている。

### 軸と除外を `design/rules.json` ではなく、テスト側の設定ファイルに置く

設計契約にテストの都合を持ち込まずに済む。

**却下理由**: 「このルールが何を見て何を見ないか」はテストの都合ではなく、ルールそのものの定義である。`design/rules.json` は既に閾値と許容リスト（`noRawScale.allowedLiterals`）を持っており、守備範囲だけを別ファイルへ追い出すと、ルールの定義が2箇所に割れる。

### 列挙（許容リスト・対象プロパティ一覧）の網羅性を機械的に証明する

`rule-coverage-partial` を根本から潰せる。

**却下理由**: 網羅性は証明できない。CSS プロパティや単位の全体集合を、このリポジトリが正本として持つことはできず、外部の一覧を引いても版によって動く。代わりに `enumeration-tail` の軸を置き、一覧の先頭以外の要素で事例を要求することにした。**これは網羅性の保証ではなく、一覧を増やしたときに事例へ手が伸びる形を作るところまで**である。

### レビューで見つけ続ける

仕組みを増やさずに済む。

**却下理由**: 見つけられてはいる。13回とも見つかっている。問題は、見つかるのがレビューの段だということだ。書く側が塞いだつもりでいる状態でレビューに出て、毎回そこで差し戻る。

## 帰結

- **ルールを1つ足すと、`design/rules.json` への宣言とフィクスチャがセットで要る。** どちらも無いと `pnpm design:check` が落ちる
- 軸の語彙（4つ）は `design/schemas/rules.schema.json` の enum が正本。増やすときはスキーマを変え、既存ルールが新しい軸を宣言すべきかを見直す
- 実装がまだ無いルール（`deck-body-fidelity`）はフィクスチャを免除する。免除リストは `scripts/validate-design.mjs` の `UNIMPLEMENTED_RULE_IDS` 一箇所で、実装との対応検査と共有する。実装された日に片方だけ外れて食い違う形を作らない
- **ルール実装のコメントに「何を見ないか」を書かない。** 書くべき場所は `design/rules.json` の `scopeExclusions` であり、コメントはそこを指す
- **`method: "review"` のルールは対象外。** 人が画面を見て判断し、自動判定を持たない（[DR-0011](./0011-lint-and-measure.md)）ため、機械で実行する事例を要求しても走らせる入口が無く、宣言だけの飾りになる。スキーマは review のとき `bypassAxes` / `scopeExclusions` を求めず、`checkBypassFixtureCoverage` と `fixturePathFor` も review を外す
- この DR は自動判定を持つ検査ルール（`design/rules.json` の `method` が `lint` / `measure` のもの）を対象とする。`eslint.config.js` が持つ汎用ルールの設定（`no-restricted-imports` の境界指定など）は対象外だが、同じ抜け道の指摘は PR #40 で出ている。適用範囲を広げるかどうかは、次に同種の指摘が出た時点で判断する
