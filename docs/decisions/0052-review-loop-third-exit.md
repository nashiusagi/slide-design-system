# DR-0052: レビューループの抜け方に「確認未了」を足す

- **状態**: 承認済み
- **日付**: 2026-09-22
- **関連**: [DR-0024](./0024-decision-records-not-adr.md), [DR-0025](./0025-issue-driven-development-flow.md), [DR-0044](./0044-bypass-fixtures-required.md)
- **実装**: `.claude/skills/issue-workflow/SKILL.md`（手順5・手順7）, `.claude/skills/issue-workflow/references/unconfirmed-comment.md`, `.claude/skills/issue-workflow/references/completion-comment.md`, `.claude/skills/issue-workflow/references/pending-comment.md`

上限の周回数と、レビューが返らなかった回をやり直せる回数は、どちらも値であり、正本は `.claude/skills/issue-workflow/SKILL.md` の手順5。上限を設けるという決定自体は [DR-0025](./0025-issue-driven-development-flow.md) が持ち、この DR はそこへ手を入れない。

この DR は [DR-0025](./0025-issue-driven-development-flow.md) の決定のうち、**レビューループの抜け条件だけ**を置き換える。ブランチ命名・Draft 先行・上限を設けること・再レビューの扱い・マージ不可は、あちらのまま有効である。

## 文脈

[DR-0025](./0025-issue-driven-development-flow.md) はレビューループの抜け方を2つだけ定めた。**収束**（指摘ゼロのレビューを1周通った）と**打ち切り**（上限を終えてもなお未対応の指摘が残る、または `should` を見送ると判断した）である。打ち切りでは残指摘を PR にコメントし、完了報告は出さない。

ところが、どちらにも当てはまらない抜け方が2度起きた。

**検査を新しく書く PR では、検査そのものが1周遅れでレビュー対象として現れる。** 実装のレビューが終わった周に検査が生まれ、その検査の抜け道は次の周でしか見つからない。実装だけの PR なら、レビュー対象は最初の周から出揃っている。この違いが、上限に当たる形を変える。

- [PR #53](../reviews/pr-53.md) — 同じ1行について、`inspection/rule-has-bypass` が上限まで毎周、形を変えて出た。毎周1段だけ穴が狭くなり、最後の周の修正を見るレビューを回せないまま上限に達した（#54 の発端）
- [PR #57](../reviews/pr-57.md) — 指摘は 18 → 6 → 3 と減り、最後の周は6観点のうち3観点が指摘ゼロだった。その周の指摘（検査の抜け道が1段残っていた）を反映して次の周を立てたが、**6観点ともレート制限で終了し、レビューが1件も返らなかった**。上限に達したのではなく、上限の次の周を走らせられなかった

どちらも**未対応の指摘はゼロ**である。前提が崩れたのでも、`should` を見送ったのでもない。2件は上限への当たり方が違う——[PR #53](../reviews/pr-53.md) は上限を使い切り、[PR #57](../reviews/pr-57.md) は最後のレビューを走らせられなかった。後者のような「周として成立しなかった回」の扱いには前例がある。[PR #55](../reviews/pr-55.md) は落ちた周を数えずにやり直した。それでも定義上は打ち切りしかなく、打ち切りとして扱うと「まだ直っていない指摘が残っている」という誤った合図が出る。[DR-0025](./0025-issue-driven-development-flow.md) が上限を設けた理由（収束しない指摘は前提の問題であることが多く、AI が粘るより人に渡す方が速い）は、この当たり方には当たらない。

## 決定

#54 が挙げた4案のうち **(c)** を採る。収束の定義は変えず、打ち切りの内訳を分ける。

### 1. 抜け方を3つにする

- **収束** — 指摘ゼロのレビューを1周通った。完了報告を出す
- **確認未了** — 上限を終え、未対応の `blocker` / `should` はゼロだが、最後の修正を見たレビューの周を回せていない。未確認コメントを出す。完了報告は出さない
- **打ち切り** — 上限を終えてもなお未対応の `blocker` / `should` が残っている、または `should` を見送ると判断した。残指摘コメントを出す。完了報告は出さない

収束の定義は変えない。「直した結果として未対応がゼロになった状態は収束ではない」も変えない。**確認未了は収束の緩和ではなく、打ち切りの内訳を分けたものである。**

収束が言う「指摘ゼロ」は、`blocker` / `should` がゼロで、かつ `consider` を直していないことを指す。**`consider` を理由つきで見送った周は収束を妨げない**——見送りは差分を変えないので、その周が見たものが最新のまま残る。`consider` を直したなら、その修正は誰も見ていないので収束ではない。`consider` を直しても収束扱いにする形は採らない。見た目の差分が変わっている以上、他の指摘と扱いを分ける理由が無いからだ。

**収束に使えるのは、観点が絞られずに立ち、そのすべてが結果を返した周だけだ。** 観点が絞られた周も、一部が落ちた周も、返った指摘がその周の結果になり上限も進むが、収束には使えない（落ちた回の扱いは決定4）。

**絞られたかどうかは、返ってきたレビュー結果で確かめる。確かめられないなら収束にしない。** 絞らないよう `pr-review` へ伝えることはできるが、あちらは呼ぶ側の要望を受け取る項目を持たず（[`pr-review/SKILL.md`](../../.claude/skills/pr-review/SKILL.md) の手順1・手順4。絞ってよいのは差分がドキュメント・契約・Skill に閉じているときだけ、という条件付きの規則である）、絞るかどうかは差分の性質から決まる。だから「伝えた」を判定の入力にすると、相手を何も拘束しない申告で収束を名乗れる。

### 2. 判定は「未対応の指摘が残っているか」だけで行う

上限に達したとき、未対応の `blocker` / `should` が1件でもあれば打ち切り、ゼロなら確認未了。**差分の性質（検査を含むか、実装だけか）を判定に使わない。**

### 3. 確認未了には専用の書式を持たせ、何が未確認かを名指しする

`references/unconfirmed-comment.md` を置く。未確認の範囲を**コミットの範囲**で示し、次に見る人がそこだけを1周回せばよい状態にする。

### 4. レビューが1件も返らなかった回は、周として数えずにやり直す。やり直しにも上限を置く

レビュアーが全滅した、外部の制約で走らせられない——**呼んだ観点のどれ一つとして結果が返らなかった**回は「指摘ゼロのレビュー」ではないので、収束には使わない。上限の周としても数えず、やり直す。

ただし**やり直せる回数にも上限を置く**（値は正本の `SKILL.md` 手順5 が持つ）。その上限を超えてもなお返らなければ、その回を1周として数える。数えた周は上限を進めるが、指摘の有無を判定できていないので収束には使えない。

一部の観点だけが落ちた回は、これに当たらない。返ってきた指摘がその周の結果になり、上限も進む。**ただしその周は収束には使えない**——収束に使える周の条件は決定1 が持つ。

上限に達する前に、レビューが落ちたことだけを理由に抜けてはいけない。

## 理由

- **打ち切りと確認未了では、次に人がやることが違う。** 打ち切りは「判断してほしい」——残った指摘を直すか、Issue の前提から見直すか。確認未了は「見てほしい」——直っているはずだが誰も確かめていない範囲がある。この2つを同じ合図で出すと、読み手はどちらなのかを PR の中身を読んで判別することになる
- **未対応がゼロなのに打ち切りと呼ぶのは、事実と違う。** [PR #53](../reviews/pr-53.md) / [PR #57](../reviews/pr-57.md) では、残指摘コメントの本文に「未対応の指摘は無い」と書く羽目になった。書式が想定していない状態を、本文で打ち消している
- **判定に差分の性質を持ち込むと、判定が揺れる。** #54 の (a) 案は「検査を追加した PR なら上限を1周増やす」だが、`scripts/` の検査・テスト・ESLint の設定・契約のスキーマのどこまでを「検査の追加」と数えるかに線を引く必要がある。`writing/ambiguous-criterion` は累計10回出ており、線引きの要る規則はこのリポジトリで繰り返し壊れている。「未対応がゼロか」なら、レビュー記録を見れば誰でも同じ結果になる
- **上限を増やしても、最後の修正が未レビューであることは変わらない。** 4周にすれば4周目の修正が、5周にすれば5周目の修正が未レビューになる。周を足すことでは解けない——解けるのは「最後の修正を見る周を必ず回す」ことだが、それは上限を無くすのと同じだ。だから**上限は保ったまま、未確認であることを申告する**形にする
- **落ちた回をやり直すのは、既にそうしていたからだ。** [PR #55](../reviews/pr-55.md) は成立しなかった周を数えずにやり直している。運用が先にあり、手順に書かれていなかっただけだ。落ちた回をそのまま1周と数えると、上限は「レビューを何周通したか」ではなく「何回呼び出したか」になり、外部の不調で上限を使い切れる
- **やり直しにも上限が要る。** 数えない回を無制限に許すと、上限（成立した周でしか進まない）へ到達する経路が消え、どの抜け方にも辿り着かない。[DR-0025](./0025-issue-driven-development-flow.md) が上限を設けた理由——上限が無ければ回り続ける——は、やり直しにもそのまま当たる。やり直せる回数は、**1つの周についての呼び出し（初回＋やり直し）が上限の周回数と同じ回数に収まる**ように決める——レビューの呼び出し回数が、通した周の数を超えて増え続けない値だ。あわせて「実行できなかった」を**1件も返らなかった**ことに限るのは、一部の観点が返した指摘ごと無かったことにする経路を塞ぐためだ。都合の悪い周を「失敗」と申告して消せるなら、上限は自己申告で回避できる。ただしそこを塞ぐだけでは足りない。**落とす単位が周から観点へ細かくなるだけ**だからだ。しかも観点は、落とすまでもなく**呼ばない**ことで外せる。だから収束に使える周は「観点が絞られなかった周」に限る
- **判定の入力は、申告ではなく結果に置く。** 「絞らないよう頼んだ」を入力にすると、相手を何も拘束しない申告で収束を名乗れる——[`pr-review`](../../.claude/skills/pr-review/SKILL.md) は呼ぶ側の要望を受け取る項目を持たない。この PR のレビューで、抜け方を回避できる経路が5周にわたって移動した（周ごと消す → 観点を落とす → 観点を呼ばない → 頼んで確かめない）。どれも「書き手がそう申告した」で通る形だったことが共通している。だから確かめられないなら収束にせず、確認未了へ倒す。**未確認であることを申告する**という、この DR の基本の形に合わせる
- **完了報告を出さないのは打ち切りと同じでよい。** 終わっていないものに完了報告を重ねると、通知だけを見た人が完了扱いでマージ判断に入る。確認未了はまさにその状態にある

## 検討した他の選択肢

### (a) 検査を新設した PR は上限を1周増やす

1周遅れで現れる検査の穴を、その周のうちに見られるようになる。#54 が挙げた案のひとつ。

**却下理由**: 「検査を追加した PR かどうか」に線を引く必要があり、その線が曖昧になる（上の理由を参照）。加えて、周を1つ足しても最後の修正が未レビューである構造は変わらない。#54 の完了条件が「判定が誰にでも同じ結果になる書き方」を求めているのは、まさにこの案の弱点を指している。

### (b) 検査を書く時点で、判定対象の別記法を列挙して事例で固定する

[DR-0044](./0044-bypass-fixtures-required.md) が `design/rules.json` の検査ルールに課していることを、リポジトリ側の検査（`scripts/` の検査、ESLint の設定、テスト）へも広げる。穴が1段ずつ狭まる形そのものを無くす。

**却下理由**: これが根本解であることには同意する。却下ではなく**別の Issue の仕事**として残す——#49 / #50 が同じ領域（軸の列挙、収集段の抜け道）を扱っており、3つを別々に設計すると同じ要求が3箇所に分かれる。#54 の本文も「(b) が根本解だが #49 / #50 と合わせて考える必要がある」と書いている。この DR が扱うのは、根本解が入るまでの抜け方であり、(b) が入っても確認未了という状態は無くならない（レビューが走らせられない場合が残る）。

### (e) 上限を無くし、指摘ゼロまで回す

#54 が挙げた案ではない（ラベルも #54 とは別系統になる）。収束の定義を扱う以上、ここで潰しておく。確認未了という状態が原理的に無くなる案である。

**却下理由**: [DR-0025](./0025-issue-driven-development-flow.md) が却下したのと同じ理由。前提の問題を実装で殴り続けることになる。上限は品質の妥協ではなく「実装で解ける問題は数周で解ける」という見立てで、これは変えない。

### レビューを実行できなかった回も1周として数える

判定が単純になる。呼び出した回数を数えるだけでよい。

**却下理由**: 外部の不調（レート制限、レビュアーの起動失敗）で上限を使い切れてしまう。レビューが1周も成立しないまま確認未了で抜ける経路ができ、上限を設けた意味が消える。[PR #55](../reviews/pr-55.md) の運用（数えずにやり直す）とも食い違う。

### (d) 何も変えず、人が判断する

運用で吸収する。#54 が挙げた案のひとつ。

**却下理由**: 2度起きており（[PR #53](../reviews/pr-53.md) / [PR #57](../reviews/pr-57.md)）、どちらも同じ形で「残指摘コメントの本文で書式を打ち消す」対処になった。同じ対処を人が毎回その場で考えるなら、それは手順が持つべきものだ。

### DR-0025 を全面的に置き換える

[DR-0025](./0025-issue-driven-development-flow.md) の帰結は「抜け条件を変えるときはこの DR を置き換える」と書いている。字義どおりなら、新しい DR があちらの5点すべてを引き取る。

**却下理由**: 抜け条件以外（[DR-0025](./0025-issue-driven-development-flow.md) の帰結が挙げる残りの項目）は変わっていない。引き取れば、変わっていない決定とその理由をここへ書き写すことになる——このリポジトリが最も避けている形（正本の複製）だ。置き換えるのは**抜け条件の決定だけ**にし、[DR-0025](./0025-issue-driven-development-flow.md) 側にはその1点が置き換わったことを書いて、双方向に辿れるようにする。

## 帰結

- 抜け方の判定を手順として書くのは `.claude/skills/issue-workflow/SKILL.md` の手順5・手順7 で、3つそれぞれの出力もあちらが持つ。上限の周回数と、やり直せる回数の正本は冒頭に書いたとおり（[DR-0024](./0024-decision-records-not-adr.md)）
- [DR-0025](./0025-issue-driven-development-flow.md) の「レビューは上限を決めて打ち切る」の決定は、抜け条件の部分だけこの DR が置き換えた。あちらの該当箇所にもその旨を書いてある。**抜け条件を次に変えるときは、この DR を置き換える**
- 確認未了で抜けた PR は、**マージ前に未確認の範囲を人が見るか、レビューをもう1周回すか**を選ぶことになる。どちらを選ぶかは Skill が決めない（マージの可否を人が持つ理由と同じ。[DR-0025](./0025-issue-driven-development-flow.md)）
- 確認未了が続くようなら、それは (b) の根本解が要るという信号になる。この DR は (b) を却下していない——#49 / #50 と合わせて設計する仕事として残している
- **`pr-review` に、呼ぶ側の「観点を絞らないでほしい」を受け取る口と、その周に立った観点を記録する項目を足すのは、あちら側の変更**であり #54 の非スコープ。#59 で扱う。それが入るまで、収束の判定は返ってきた結果を確かめることで行い、確かめられないなら確認未了へ倒す
- レビューを走らせられなかった回のことは、未確認コメントに書く。`docs/reviews/pr-<N>.md` へは書かない——あのファイルの書式は `pr-review` が持っており、実行できなかった周を書く節を持たない。書式を足すなら `pr-review` 側の変更であり、#54 の非スコープにあたる（別の Issue で扱う）
- 抜け方の判定に使った材料——各 `blocker` / `should` を直したか見送ったか、見送った `consider`、最後の周に呼んだ観点、やり直した回数——は、**3つの出力すべて**（完了報告・未確認コメント・残指摘コメント）が持つ。判定の入力が残らないと、「未対応がゼロ」は書き手の申告にしかならない。収束はマージ判断の材料として最も強い合図なので、そこだけ記録を緩くしない
