# DR-0052: レビューループの抜け方に「確認未了」を足す

- **状態**: 承認済み
- **日付**: 2026-09-22
- **関連**: [DR-0024](./0024-decision-records-not-adr.md), [DR-0025](./0025-issue-driven-development-flow.md), [DR-0044](./0044-bypass-fixtures-required.md)
- **正本**: `.claude/skills/issue-workflow/SKILL.md`（上限の周回数と、3つの抜け方の判定）
- **実装**: `.claude/skills/issue-workflow/SKILL.md`（手順5・手順7）, `.claude/skills/issue-workflow/references/unconfirmed-comment.md`

この DR は [DR-0025](./0025-issue-driven-development-flow.md) の決定のうち、**レビューループの抜け条件だけ**を置き換える。ブランチ命名・Draft 先行・上限を設けること・再レビューの扱い・マージ不可は、あちらのまま有効である。

## 文脈

[DR-0025](./0025-issue-driven-development-flow.md) はレビューループの抜け方を2つだけ定めた。**収束**（指摘ゼロのレビューを1周通った）と**打ち切り**（上限を終えてもなお未対応の指摘が残る、または `should` を見送ると判断した）である。打ち切りでは残指摘を PR にコメントし、完了報告は出さない。

ところが、どちらにも当てはまらない抜け方が2度起きた。

**検査を新しく書く PR では、検査そのものが1周遅れでレビュー対象として現れる。** 実装のレビューが終わった周に検査が生まれ、その検査の抜け道は次の周でしか見つからない。実装だけの PR なら、レビュー対象は最初の周から出揃っている。この違いが、上限に当たる形を変える。

- [PR #53](../reviews/pr-53.md) — 同じ1行について、`inspection/rule-has-bypass` が3周続けて形を変えて出た。毎周1段だけ穴が狭くなり、3周目の修正を見る周を回せないまま上限に達した（#54 の発端）
- [PR #57](../reviews/pr-57.md) — 指摘は 18 → 6 → 3 と減り、3周目は6観点のうち3観点が指摘ゼロだった。3周目の指摘（検査の抜け道が1段残っていた）を反映したところで上限に達し、その修正を見る周は回せていない

どちらも**未対応の指摘はゼロ**である。前提が崩れたのでも、`should` を見送ったのでもない。それでも定義上は打ち切りしかなく、打ち切りとして扱うと「まだ直っていない指摘が残っている」という誤った合図が出る。[DR-0025](./0025-issue-driven-development-flow.md) が上限を設けた理由（収束しない指摘は前提の問題であることが多く、AI が粘るより人に渡す方が速い）は、この当たり方には当たらない。

## 決定

### 1. 抜け方を3つにする

- **収束** — 指摘ゼロのレビューを1周通った。完了報告を出す
- **確認未了** — 上限を終え、未対応の `blocker` / `should` はゼロだが、最後の修正を見たレビューの周を回せていない。未確認コメントを出す。完了報告は出さない
- **打ち切り** — 上限を終えてもなお未対応の `blocker` / `should` が残っている、または `should` を見送ると判断した。残指摘コメントを出す。完了報告は出さない

収束の定義は変えない。「直した結果として未対応がゼロになった状態は収束ではない」も変えない。**確認未了は収束の緩和ではなく、打ち切りの内訳を分けたものである。**

### 2. 判定は「未対応の指摘が残っているか」だけで行う

上限に達したとき、未対応の `blocker` / `should` が1件でもあれば打ち切り、ゼロなら確認未了。**差分の性質（検査を含むか、実装だけか）を判定に使わない。**

### 3. 確認未了には専用の書式を持たせ、何が未確認かを名指しする

`references/unconfirmed-comment.md` を置く。未確認の範囲を**コミットの範囲**で示し、次に見る人がそこだけを1周回せばよい状態にする。

### 4. レビューの周が回せなかった場合も確認未了に含める

上限に達する前でも、レビュー自体を実行できなかった（レビュアーが落ちた、外部の制約で走らせられない）場合、その周は「指摘ゼロ」ではない。未対応がゼロなら確認未了として抜ける。

## 理由

- **打ち切りと確認未了では、次に人がやることが違う。** 打ち切りは「判断してほしい」——残った指摘を直すか、Issue の前提から見直すか。確認未了は「見てほしい」——直っているはずだが誰も確かめていない範囲がある。この2つを同じ合図で出すと、読み手はどちらなのかを PR の中身を読んで判別することになる
- **未対応がゼロなのに打ち切りと呼ぶのは、事実と違う。** [PR #53](../reviews/pr-53.md) / [PR #57](../reviews/pr-57.md) では、残指摘コメントの本文に「未対応の指摘は無い」と書く羽目になった。書式が想定していない状態を、本文で打ち消している
- **判定に差分の性質を持ち込むと、判定が揺れる。** #54 の (a) 案は「検査を追加した PR なら上限を1周増やす」だが、`scripts/` の検査・テスト・ESLint の設定・契約のスキーマのどこまでを「検査の追加」と数えるかに線を引く必要がある。`writing/ambiguous-criterion` は累計10回出ており、線引きの要る規則はこのリポジトリで最もよく壊れる形だ。「未対応がゼロか」なら、レビュー記録を見れば誰でも同じ結果になる
- **上限を増やしても、最後の修正が未レビューであることは変わらない。** 4周にすれば4周目の修正が、5周にすれば5周目の修正が未レビューになる。周を足すことでは解けない——解けるのは「最後の修正を見る周を必ず回す」ことだが、それは上限を無くすのと同じだ。だから**上限は保ったまま、未確認であることを申告する**形にする
- **完了報告を出さないのは打ち切りと同じでよい。** 終わっていないものに完了報告を重ねると、通知だけを見た人が完了扱いでマージ判断に入る。確認未了はまさにその状態にある

## 検討した他の選択肢

### (a) 検査を新設した PR は上限を1周増やす

1周遅れで現れる検査の穴を、その周のうちに見られるようになる。#54 が挙げた案のひとつ。

**却下理由**: 「検査を追加した PR かどうか」に線を引く必要があり、その線が曖昧になる（上の理由を参照）。加えて、周を1つ足しても最後の修正が未レビューである構造は変わらない。#54 の完了条件が「判定が誰にでも同じ結果になる書き方」を求めているのは、まさにこの案の弱点を指している。

### (b) 検査を書く時点で、判定対象の別記法を列挙して事例で固定する

[DR-0044](./0044-bypass-fixtures-required.md) が `design/rules.json` の検査ルールに課していることを、リポジトリ側の検査（`scripts/` の検査、ESLint の設定、テスト）へも広げる。穴が1段ずつ狭まる形そのものを無くす。

**却下理由**: これが根本解であることには同意する。却下ではなく**別の Issue の仕事**として残す——#49 / #50 が同じ領域（軸の列挙、収集段の抜け道）を扱っており、3つを別々に設計すると同じ要求が3箇所に分かれる。#54 の本文も「(b) が根本解だが #49 / #50 と合わせて考える必要がある」と書いている。この DR が扱うのは、根本解が入るまでの抜け方であり、(b) が入っても確認未了という状態は無くならない（レビューが走らせられない場合が残る）。

### (c') 上限を無くし、指摘ゼロまで回す

確認未了という状態が原理的に無くなる。

**却下理由**: [DR-0025](./0025-issue-driven-development-flow.md) が却下したのと同じ理由。前提の問題を実装で殴り続けることになる。上限は品質の妥協ではなく「実装で解ける問題は数周で解ける」という見立てで、これは変えない。

### (d) 何も変えず、人が判断する

運用で吸収する。#54 が挙げた案のひとつ。

**却下理由**: 2度起きており（[PR #53](../reviews/pr-53.md) / [PR #57](../reviews/pr-57.md)）、どちらも同じ形で「残指摘コメントの本文で書式を打ち消す」対処になった。同じ対処を人が毎回その場で考えるなら、それは手順が持つべきものだ。

### DR-0025 を全面的に置き換える

[DR-0025](./0025-issue-driven-development-flow.md) の帰結は「抜け条件を変えるときはこの DR を置き換える」と書いている。字義どおりなら、新しい DR があちらの5点すべてを引き取る。

**却下理由**: 5点のうち4点（ブランチ命名・Draft 先行・上限を設けること・再レビューの扱い・マージ不可）は変わっていない。引き取れば、変わっていない決定とその理由をここへ書き写すことになる——このリポジトリが最も避けている形（正本の複製）だ。置き換えるのは**抜け条件の決定だけ**にし、[DR-0025](./0025-issue-driven-development-flow.md) 側にはその1点が置き換わったことを書いて、双方向に辿れるようにする。

## 帰結

- 抜け方の判定と、3つそれぞれで何を出すかは `.claude/skills/issue-workflow/SKILL.md` の手順5・手順7 が正本。**周回数の値もあちらのまま**で、この DR には複製しない（[DR-0024](./0024-decision-records-not-adr.md)）
- [DR-0025](./0025-issue-driven-development-flow.md) の「レビューは上限を決めて打ち切る」の決定は、抜け条件の部分だけこの DR が置き換えた。あちらの該当箇所にもその旨を書いてある。**抜け条件を次に変えるときは、この DR を置き換える**
- 確認未了で抜けた PR は、**マージ前に未確認の範囲を人が見るか、レビューをもう1周回すか**を選ぶことになる。どちらを選ぶかは Skill が決めない（マージの可否を人が持つ理由と同じ。[DR-0025](./0025-issue-driven-development-flow.md)）
- 確認未了が続くようなら、それは (b) の根本解が要るという信号になる。この DR は (b) を却下していない——#49 / #50 と合わせて設計する仕事として残している
- レビューを走らせられずに抜けた回は、`docs/reviews/pr-<N>.md` にもその旨を残す。記録が無いと、次に見る人は「その周は指摘ゼロだった」と読む
