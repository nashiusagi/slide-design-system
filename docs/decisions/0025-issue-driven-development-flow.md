# DR-0025: Issue 起点の開発フローを Agent Skill として固定する

- **状態**: 承認済み
- **日付**: 2026-09-06
- **関連**: [DR-0013](./0013-agent-skill-and-resolver.md), [DR-0024](./0024-decision-records-not-adr.md)

## 文脈

このリポジトリは AI が実装を書くことを前提にしている。だが実装の前後——ブランチをどう切るか、いつ PR を立てるか、レビューをどこまで回すか、終わったことをどう示すか——は誰の担当でもなく、毎回その場の判断で行われていた。

結果として起きていたのは次のことである。ブランチ名がばらつく。PR が実装の後追いで作られ、走っている最中は誰にも見えない。レビューを受けたのに指摘が半分だけ反映される。PR 本文が着手時のまま実態と食い違う。終わったのかどうかが Issue からも PR からも読み取れない。

[PR #13 のレビュー](../reviews/pr-13.md)でも「意思決定 → Issue → ブランチの順序と粒度」が未記録であることが指摘され、保留になっていた。

## 決定

Issue 起点の開発フローを Agent Skill（`.claude/skills/issue-workflow/`）として固定する。決めたのは次の 4 点である。

**ブランチ名は `feature/<Issue番号>_<内容>` とする。** 内容は Issue タイトルから起こした短い英小文字スラグ。

**PR は Draft で先に立て、実装が済んだ時点で Ready にする。** 空コミットを push して着手と同時に PR を作る。Ready 化がレビューの開始線になる。

**レビューは最大 3 周で打ち切る。** `pr-review` を呼び、指摘を反映し、また呼ぶ。指摘が無くなるか 3 周を終えたら抜ける。打ち切った場合は残指摘を PR にコメントする。

**マージは人が行う。** Skill は PR を出して完了を報告するところまで。

あわせて、開発プロセスの Skill（`pr-review` / `issue-workflow`）は `.claude/skills/` に置き、設計契約を供給する Skill（[DR-0013](./0013-agent-skill-and-resolver.md) の `skills/slide-harness/`）とは別系統として扱う。前者はリポジトリの回し方を、後者は生成物の作り方を担う。

## 理由

- **順番と痕跡を固定すると、進行が読める。** Draft PR が着手の合図、Ready がレビュー可能の合図、完了コメントが終了の合図になる。どれも通知として届くので、リポジトリを見に行かなくても状態が分かる
- **ブランチ名に Issue 番号を入れると、どこからでも辿れる。** ブランチ・PR・Issue のどれか一つを持っていれば残りに到達できる
- **上限を 3 周にしたのは、収束しない指摘は前提の問題であることが多いからだ。** スコープが曖昧、契約と要求が矛盾している、別の作り方が要る。AI が粘るより人に渡す方が速い局面が必ず来る。上限が無いと、その局面が来ても回り続ける
- **マージを人に残すのは、統合の可否がコードの正しさとは別の判断だからだ。** 他の作業との兼ね合い、リリースの都合、そもそも今入れるべきか。Skill はその情報を持たない

## 検討した他の選択肢

### 実装が終わってから PR を作る

差分が揃った状態で PR が立つので、レビューの空振りが無い。

**却下理由**: 走っている最中が見えない。着手済みの Issue に別の人（または別のセッション）が手を出す事故を防げない。空コミットの PR は 1 行のコストで、これを防ぐ。

### レビューを指摘ゼロまで無制限に回す

品質の下限を上げられる。

**却下理由**: 収束しない指摘に上限が無いと、前提の問題を実装で殴り続けることになる。3 周は「実装で解ける問題は 3 周で解ける」という見立てであって、品質の妥協ではない。残った指摘は消さずに PR へ残すので、判断は人に渡る。

### 指摘ゼロになったら Skill がマージまで行う

完全自動化できる。

**却下理由**: 上記のとおり、統合の可否は Skill が持たない情報で決まる。

### 開発プロセスの Skill も `skills/` に置く

Skill の置き場所が 1 箇所で済む。

**却下理由**: [DR-0013](./0013-agent-skill-and-resolver.md) の `skills/slide-harness/` は実験の条件差として Harness 側にだけ渡されるものであり、リポジトリの回し方を担う Skill とは配布の単位が違う。同じ場所に置くと、実験のワークスペースへ開発プロセスの Skill が混入する経路ができる。

## 帰結

- ブランチ命名・Draft 先行・3 周上限・マージ不可を変えるときは、この DR を置き換える。`.claude/skills/issue-workflow/SKILL.md` を書き換えるだけで済ませない
- レビューの周回数の正本は `.claude/skills/issue-workflow/SKILL.md` にある。この DR は「上限を設ける」という決定を記録するもので、値を再掲しない（[DR-0024](./0024-decision-records-not-adr.md)）
- `.claude/skills/` 配下の Skill が増えたときは、README の「正本の在り処」に載せるのではなく、この DR の系統として扱う。設計データの正本ではないため、正本表と混ぜない
