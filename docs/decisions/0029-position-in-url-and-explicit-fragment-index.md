# DR-0029: 現在位置は URL の `#/<スライド>/<段階>` で表し、Fragment の段階は明示する

- **状態**: 承認済み
- **日付**: 2026-09-07
- **関連**: [DR-0004](./0004-phase-1-runtime-scope.md), [DR-0011](./0011-lint-and-measure.md), [DR-0016](./0016-deck-contract-markdown.md)

## 文脈

[DR-0004](./0004-phase-1-runtime-scope.md) は「URL には現在のスライドに加えて Fragment の段階も含める（`#/3/2` の形）」と決めたが、番号の基数と省略の規則は決めていない。measure（[DR-0011](./0011-lint-and-measure.md)）は URL を組み立てて全段階を巡回するので、規則が曖昧だと巡回する側とランタイムで解釈がずれる。しかも「1 つ足りない段階」は緑のまま通る。

同じ理由で、Fragment が自分の段階を**どこから得るか**も決める必要がある。出現順から自動採番するか、書き手が明示するか。

## 決定

- URL の書式は `#/<スライド番号>/<段階>`。**スライド番号は 1 始まり、段階は 0 始まり**で、段階 0 は Fragment を 1 つも表示していない状態を指す
- 段階が 0 のときは省略して `#/3` と書く。読む側は `#/3` と `#/3/0` の両方を受け付ける
- 書式に合わない hash は無視して先頭のスライドを表示する。範囲を超えるスライド番号は端へ丸める
- Fragment は段階を `index` props で**明示**する。出現順からの自動採番はしない

書式の実体は `src/runtime/hash.ts` にあり、この DR は規則と理由だけを持つ。

## 理由

- スライド番号を 1 始まりにするのは、URL が人の目に触れるものだから。「3 枚目」と `#/3` が一致する
- 段階を 0 始まりにするのは、0 が「まだ何も出していない」という実在の状態だから。1 始まりにすると初期状態を表す番号が無くなる。基数が揃わないのは承知の上で、両方に自然な向きを取った
- 段階 0 を省略できると、Fragment を持たないスライドの URL が `#/3` で済む。スライドの大半は Fragment を持たない
- Fragment の段階を明示させるのは、静的に読めるようにするため。lint（#7）は JSX を見て段階の連番や重複を検査でき、deck 契約（[DR-0016](./0016-deck-contract-markdown.md)）との突き合わせもできる。自動採番だと、順序の入れ替えで段階が黙って変わり、契約との差が検出できない

## 検討した他の選択肢

### クエリ文字列（`?slide=3&step=2`）で表す

構造化されていて解析が素直。

**却下理由**: 静的ホスティングでの共有が主目的（[DR-0006](./0006-online-sharing-first.md)）であり、hash なら同一ページ内の移動としてサーバへ問い合わせが飛ばない。URL としても短い。

### 段階も 1 始まりにして基数を揃える

読む側の説明が「どちらも 1 始まり」で済む。

**却下理由**: 初期状態を `#/3/0` と書くことになり、結局 0 が出てくる。揃ったように見えて揃わない。

### Fragment の段階を出現順から自動採番する

書き手は `index` を書かなくて済み、順序を入れ替えても壊れない。

**却下理由**: 段階の番号が DOM の並びに依存し、ソースからは読めなくなる。lint が段階を検査できず、deck 契約との突き合わせもできない。書く手間より、検査できることを取る。

## 帰結

- measure は `#/<n>` から `#/<n>/<最大段階>` まで URL を組み立てて巡回できる。段階数はソースから静的に読める
- Fragment の `index` の連番・重複・欠番は lint（#7）で検査する。ランタイムは登録された最大値を段階数として扱うだけで、欠番があっても止めない
- 段階数を超える段階を hash で指定された場合、ランタイムは丸めない。表示中のスライドが段階数を報告するまで正しい上限が分からないためで、指定された段階まで Fragment がすべて出た状態になる
