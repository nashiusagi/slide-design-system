# DR-0053: その周に立った観点は、走らせた側が記録として残す

- **状態**: 承認済み
- **日付**: 2026-09-22
- **関連**: [DR-0024](./0024-decision-records-not-adr.md), [DR-0025](./0025-issue-driven-development-flow.md), [DR-0052](./0052-review-loop-third-exit.md)
- **実装**: `.claude/skills/pr-review/SKILL.md`（手順1・手順4・手順6）, `.claude/skills/pr-review/references/review-file-format.md`, `.claude/skills/issue-workflow/SKILL.md`（手順3・手順5）

この DR は [DR-0052](./0052-review-loop-third-exit.md) の決定1 のうち、**絞られたかどうかの確かめ方**だけを置き換える。あちらが決めた抜け方（収束 / 確認未了 / 打ち切り）と収束の条件そのもの、そして「確かめられないなら収束にしない」はあちらのまま有効である。この DR が決めるのは、判定に要る情報を**誰が用意するか**と、**その情報がそろう周を呼ぶ側が要求できるようにするか**の2つ。

## 文脈

[DR-0052](./0052-review-loop-third-exit.md) 決定1 は、収束に使える周を「観点が絞られずに立ち、そのすべてが結果を返した周」と定めた。

この判定には「その周に何観点が立ったか」が要る。ところがその情報は、判定する側（`issue-workflow`）には無い。

- 立てる観点を決めるのは `pr-review` の手順4 で、再レビューでは前周に指摘ゼロだった観点を絞ってよいことになっている
- レビュー記録（`docs/reviews/pr-<N>.md`）の書式には、その周に立った観点を書く項目が無かった。各指摘の `指摘した観点` 欄から辿れるのは**指摘が出た観点だけ**で、**指摘ゼロで返った観点はどこにも残らない**
- 呼ぶ側には、絞らないでほしいと要求する口も無かった。頼むことはできても、`pr-review` の手順1 はそれを受け取る項目を持たず、絞るかどうかは差分の性質だけで決まっていた

PR #58 はこの穴を5周にわたって塞ごうとした（[docs/reviews/pr-58.md](../reviews/pr-58.md)）。抜け方を自己申告で回避できる経路が、周ごと消す → 観点を落とす → 観点を呼ばない → 頼んで確かめない、と単位を変えながら移動し、毎周 blocker になった。共通していたのは、**どれも「書き手がそう申告した」で通る形だった**ことだ。

最後に採った形——返ってきた結果で確かめ、確かめられないなら確認未了へ倒す——は正しい方向だが、確かめる材料が記録に無い以上、実際には人がレビュー全文を読んで数えるしかなかった。

## 決定

### 1. その周に立った観点は、`pr-review` がレビュー記録へ残す

指摘ゼロだった観点も含める。必須項目とする。

**`指摘した観点` 欄では代えられない。** あちらは1件の指摘がどの観点から挙がったかを示すもので、指摘ゼロで返った観点はそこに現れない。欄の置き場所・書き方・観点名の表記は `.claude/skills/pr-review/references/review-file-format.md` が持つ。

### 2. 呼ぶ側は「観点を絞らないでほしい」を渡せる

`pr-review` はこれを手順1 の入力として受け取り、渡されたら手順4 の絞り込みを行わない。渡されなければ、これまでどおり差分の性質で決める。

### 3. 判定は、伝えた事実ではなく記録で行う

`issue-workflow` は「絞らないよう伝えた」ことを収束の根拠にしない。レビュー記録の「立った観点」を見て判定し、**確かめられないなら収束にせず確認未了へ倒す**（[DR-0052](./0052-review-loop-third-exit.md) 決定1 の暫定をそのまま残す）。

## 理由

- **判定に使う情報は、判定する側が推測するのではなく、生成した側が残す。** 何観点が走ったかを知っているのは走らせた側だけだ。判定する側に数え直させると、数え方が判定する側の都合で揺れる——実際 PR #58 では「数え直す必要は無い」と書いて確認を免除する形まで現れた
- **「伝えた」を入力にすると、相手を拘束しない申告で結論を出せる。** 決定2 で要望を受け取れるようにしてもこれは変わらない。伝えたことと実際に立ったことは別で、後者だけが判定の材料になる
- **暫定（確かめられないなら確認未了へ倒す）は残す。** 記録が入れば「確かめられない」場合は減るが、ゼロにはならない——記録が書かれなかった周、書式より前のレビューが残る。倒す先が確認未了である限り、失敗は「収束しづらくなる」方向にしか働かない
- **絞り込みは「見直す価値が低い観点を省く」判断であって、抜け方を左右する重みを持たない。** `pr-review` 手順4 が挙げる根拠は「前周に指摘ゼロだった観点は、次の周で状況が変わる要素が無い」——値の高い情報を捨てているわけではない。だから要望があれば譲る（決定2）。絞ることで得るのは数分で、失うのは収束できる周だ

## 検討した他の選択肢

### `issue-workflow` がレビュー結果から立った観点を数える

記録の書式を変えずに済む。`pr-review` 側は何も変わらない。

**却下理由**: 指摘ゼロで返った観点は結果のどこにも現れないので、数えられない。数えられるのは「指摘が出た観点」だけで、それは絞られたかどうかとは別の量だ。無いものを数えさせる形になる。

### 収束の条件から観点の網羅性を外す

判定に要る情報が減り、この問題自体が消える。

**却下理由**: [DR-0052](./0052-review-loop-third-exit.md) 決定1 が観点の網羅性を条件に入れたのは、1観点だけが指摘ゼロで返った周を収束と呼べてしまう穴を塞ぐためだった。外せばその穴が戻る。条件を維持したまま、確かめる手段を用意する方を採る。

### `pr-review` が収束の可否まで判定して返す

判定と情報が同じ場所に揃い、受け渡しが要らなくなる。

**却下理由**: 抜け方の判定は `issue-workflow` の責務で、[DR-0052](./0052-review-loop-third-exit.md) がそう決めている。`pr-review` は「レビューの中身」を持ち、抜け方は持たない。判定を移すと、`pr-review` が上限の周回数・やり直しの上限・未対応の指摘の数まで知る必要が出る。

### 要望の口は設けず、絞られた周は収束に使えないまま運用する

決定1 だけで判定は成り立つ。`pr-review` に手を入れずに済む。

**却下理由**: 絞られた周は収束に使えないので、再レビューで絞られるたびに収束の機会が消える。`issue-workflow` は毎周の結果を見るまでどの周が収束になるか分からないから、絞られること自体を避けたい。絞ることで得るのは数分で、失うのは収束できる周だ。絞り込みは「前周に指摘ゼロだった観点は見直す価値が低い」という判断（`pr-review` 手順4）であって、抜け方を左右する重みは持たない。だから要望があれば譲る。

### 立った観点を `docs/review_log.md` へ残す

累計の記録と同じ場所にまとまる。

**却下理由**: あちらはカテゴリ別の累計を持つファイルで、周ごとの事実を持つ構造になっていない。レビュー履歴の行は PR につき1行で、周ごとには分かれない。

## 帰結

- レビュー記録の書式（`references/review-file-format.md`）が「立った観点」を必須項目として持つ。**この項目を落としたレビュー記録は、呼ぶ側から見れば「確かめられない」状態**であり、その周は収束に使えない
- `pr-review` は呼ぶ側の要望（観点を絞らないでほしい）を手順1 の入力として受け取る。**あちらが絞るかどうかの基準を、呼ぶ側へ書き写さない**（[DR-0025](./0025-issue-driven-development-flow.md) が固定した責務の切り方をそのまま保つ）
- [DR-0052](./0052-review-loop-third-exit.md) 決定1 の暫定（確かめられないなら確認未了へ倒す）は残る。**この DR はあちらの暫定を解くのではなく、倒す場合を減らす**
- 立った観点が記録に残るので、「その周に何観点が立ったか」は後から読み取れる形になった。ただし機械で数えるには観点名の表記が固定されている必要があり、それは書式（`review-file-format.md`）が持つ取り決めに依る。収束の判定そのものを機械検査にするかは、この DR では決めない
- `issue-workflow` は毎周この要望を渡すので、**`pr-review` 手順4 の絞り込み規則が効くのは、あちらを経由しない再レビューだけになる**。規則を残すのは、人が直接 `pr-review` を呼ぶ経路があるためだ
