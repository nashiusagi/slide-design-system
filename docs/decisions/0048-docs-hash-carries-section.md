# DR-0048: カタログの hash は `#/<ページID>/<節ID>` まで持つ

- **状態**: 承認済み
- **日付**: 2026-09-21
- **関連**: [DR-0029](./0029-position-in-url-and-explicit-fragment-index.md), [DR-0035](./0035-layout-component-contract-shape.md), [DR-0042](./0042-design-catalog-as-separate-build-entry.md), [DR-0047](./0047-catalog-previews-rebuild-the-canvas-box.md)
- **実装**: `src/docs/hash.ts`, `src/docs/DocsApp.tsx`, `src/docs/layouts.ts`（`layoutSectionId`）

## 文脈

[DR-0042](./0042-design-catalog-as-separate-build-entry.md) は、カタログのページ間の移動をハッシュルーティングで行い、書式を `#/<ページID>` と決めた。

部品のページを作る段になって、この書式では足りないことが分かった。部品契約は `allowedIn` でレイアウトを指しており（[DR-0035](./0035-layout-component-contract-shape.md)）、カタログはそこからレイアウトのページの**該当項目**へ辿れる必要がある。契約どうしの繋がりを画面上で追えることが、契約を1箇所にまとめて見る場所としてのカタログの値打ちだからだ。ページの先頭へ飛ぶだけでは、どのレイアウトの話かを読み手が探し直すことになる。

通常のアンカー（`#title`）は使えない。hash はページの指定そのものに使われているので、`#/layouts#title` と重ねると書式に合わなくなり、未知のページとして先頭へ落ちる。

## 決定

### 1. 書式を `#/<ページID>` と `#/<ページID>/<節ID>` の2つにする

節 ID は、ページの中の1項目（レイアウト1つ、部品1つ）を指す。セグメントの文字種はページ ID と同じ（英小文字・数字・ハイフン）。`parseDocsHash` は位置（`{ pageId, sectionId }`）を返し、節を指していなければ `sectionId` は `null` を返す。

### 2. 節が実在しなくても落とさず、ページを表示する

hash が指す節に対応する要素が無ければ、スクロールせずページの先頭を出す。契約を消したときに、その節を指す古いリンクが空白の画面になるより、ページが出た方がよい。

### 3. 節 ID と契約名の対応は、リンクを張る側と `id` を置く側で共有する

レイアウトの節 ID は `src/docs/layouts.ts` の `layoutSectionId` が持つ。リンクを張るのは部品のページ、`id` を置くのはレイアウトのページで、別のファイルにある。両方が「契約の名前をそのまま使う」と書くと、片方だけ変えたときにリンクが黙って外れる。

## 理由

- **契約どうしの繋がりを、画面上で辿れないカタログには値打ちが無い。** `allowedIn` は契約が持っている対応関係そのもので、それをリンクとして出せないなら、読み手は2つのページを行き来して目で照合することになる
- **アンカーを重ねる書き方は、この設計では取れない。** hash がページの指定に使われている以上、`#` は1つしか持てない。節を書式の中へ入れるのが唯一の道である
- **節が無いときに落とさないのは、リンクが契約の寿命より長く残るからだ。** 契約は消える。消えた先を指すリンクは、文書を書き換えるたびに生まれる（`writing/dangling-quote-reference` が累計5回出ているのと同じ形）。落ちるのではなく、ページが出る形にしておく
- **対応を1箇所に持たないと、リンクは押すまで壊れたことが分からない。** リンクは付いたまま、行き先だけが変わる。`layoutSectionId` を経由させ、全契約について hash を往復するテストを置く

## 検討した他の選択肢

### カタログをパスルーティングへ移す（`/docs/layouts#title`）

hash が空くので、通常のアンカーがそのまま使える。

**却下理由**: [DR-0042](./0042-design-catalog-as-separate-build-entry.md) が「静的ホスティングでサーバ側の rewrite を前提にしない」という理由でパスルーティングを却下している。カタログのリンクのためにホスティングの前提を変えるのは釣り合わない。

### リンクはページまでとし、節へは飛ばさない

書式を変えずに済む。

**却下理由**: Issue #36 の完了条件は「`allowedIn` から `#/layouts` の**該当レイアウト**へ移動できる」である。`allowedIn` が2つあってもリンク先が同じになり、対応関係を出した意味が消える。

### 節を state で持ち、URL には出さない

書式を変えずに、クリックでスクロールだけを行う。

**却下理由**: 位置が URL に出ないと、その項目を指して人に渡せない。[DR-0029](./0029-position-in-url-and-explicit-fragment-index.md) がスライドの現在位置を URL に出したのと同じ理由が、カタログにも当てはまる。

## 帰結

- **スライドの位置 hash と、2セグメントの形が重なった。** スライド側は `#/<番号>/<段階>`（[DR-0029](./0029-position-in-url-and-explicit-fragment-index.md)）で、カタログ側は `#/<ページID>/<節ID>`。書式の側では分けられない。両者を分けているのは「数字だけのページ ID を使わない」という [DR-0042](./0042-design-catalog-as-separate-build-entry.md) の取り決めだけで、その検査（`DOCS_PAGES` が数字だけの ID を持たない）が唯一の砦になる
- **書式の検査が1段ゆるくなった。** 以前は2セグメントの hash を `parseDocsHash` が弾いていた。いまは書式としては通り、ページ一覧に無いことで弾かれる。弾かれる場所が parser からページ解決へ移った
- 節を持つページを足すときは、節 ID の対応を contract 側の読み込み口（`src/docs/layouts.ts` の `layoutSectionId` に相当するもの）へ置き、リンク側と `id` 側の両方がそこから引く
