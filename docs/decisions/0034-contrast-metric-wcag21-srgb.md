# DR-0034: コントラストの指標は WCAG 2.1 とし、sRGB 色域に丸めた値で測る

- **状態**: 承認済み
- **日付**: 2026-09-08
- **関連**: [DR-0008](./0008-accent-hue-purple.md), [DR-0011](./0011-lint-and-measure.md), [DR-0033](./0033-derived-values-are-generated-and-checked.md)
- **実装**: `scripts/lib/color.mjs`
- **正本**: `design/tokens.json`（色の値）／ `design/rules.json`（閾値）

## 文脈

トークンの色は oklch で書き（[DR-0008](./0008-accent-hue-purple.md)）、コントラストを測って記録する（[DR-0033](./0033-derived-values-are-generated-and-checked.md)）。だが「何をコントラストと呼ぶか」は決めていなかった。指標が違えば同じ色でも合否が変わるので、記録された数値だけを見ても再現できない。

## 決定

**指標は WCAG 2.1 のコントラスト比とする。** 相対輝度は sRGB の 8bit へ丸めた値から求め、比は小数第 2 位で切り捨てる。トークンの色は sRGB 色域内に限り、外れたものは検査で落とす。

## 理由

- **ブラウザが実際に描く値で測る。** oklch は sRGB の外も表現できるが、画面へ出るときは色域へクリップされる。クリップ後の値で測らないと、記録と描画がずれる。8bit へ丸めてから測るのは、クリップと量子化の両方を通した後の値を見るため
- **切り捨てにするのは、基準ちょうどを甘く見せないため。** 四捨五入だと 4.495 が 4.5 として通る。検査が基準を割った色を通すより、通るはずの色を落とす方が安全側に倒れる
- **sRGB 色域へ限るのは、契約が保証できる範囲がそこまでだから。** P3 の色は対応していない環境で別の色に化ける。どの環境でも同じコントラストになる保証が要る
- WCAG 2.1 は既存の実装（ブラウザの開発者ツール、アクセシビリティ検査器）と数値が一致する。人が別のツールで確かめたときに食い違わない

## 検討した他の選択肢

### APCA（WCAG 3 のドラフト）

知覚との一致は WCAG 2.1 より良いとされ、明るい背景に対する細い文字の扱いが現実的になる。

**却下理由**: まだドラフトで、閾値の定義が変わりうる。契約の合否がドラフトの改訂で動くのは困る。既存ツールとの突き合わせもできない。WCAG 3 が固まった時点で新しい DR を立てて移る。

### oklch の L の差で判定する

トークンが oklch で書かれているので、変換を挟まずに済む。

**却下理由**: L の差はコントラスト比と単調に対応しない。彩度が高い色では、L が離れていても実際の比が基準を割る。[DR-0011](./0011-lint-and-measure.md) の measure 系がブラウザ上で測る値とも一致しなくなる。

## 帰結

- トークンへ色を足すときは sRGB 色域内であること。`pnpm design:check` が色域を検査する
- 算出値は WCAG 2.1 の比として `design/tokens.json` の `$measured.contrast` に記録される（[DR-0033](./0033-derived-values-are-generated-and-checked.md)）
- 閾値そのもの（本文 4.5:1、UI の境界とフォーカス 3:1）はここには書かない。正本は `design/rules.json` の `contrast`（[DR-0008](./0008-accent-hue-purple.md) / [DR-0011](./0011-lint-and-measure.md)）
- 色域を広げたくなったら、この DR を覆す新しい DR を立てる。検査を緩めるだけの変更はしない
