# DR-0018: スタイルは素の CSS + トークン変数で書き、Tailwind を使わない

- **状態**: 承認済み
- **日付**: 2026-09-06
- **関連**: [DR-0011](./0011-lint-and-measure.md), [DR-0009](./0009-five-layer-contract.md)

## 文脈

参考元のデザインシステムは Tailwind v4 + HeroUI という構成で、その no-raw-color 相当のルールは CSS ファイルを見て生の色値を検出していた。このプロジェクトは HeroUI を使わない（[DR-0003](./0003-custom-slide-runtime.md)）ため、Tailwind を採用するかは独立した判断になる。

## 決定

`design/layout.css`（レイアウトの実装。クラス名と値は `design/layouts/` の契約に従う）と、`tokens.json` から生成した `--dh-*` 変数で書く。Tailwind は使わない。クラス名は契約が定める。

## 理由

- Tailwind のユーティリティクラス（`text-[18px]`、`bg-red-500` など）は**トークン契約を素通りする抜け道**になる。契約による制御が効かなくなる
- lint が Tailwind のクラス名文字列まで解析する必要が生じ、実装が複雑化する
- 素の CSS なら生の px や色値の検出を CSS AST で素直に行える
- 参考元と同じ方式（レイアウトのクラス名を契約が指定し、実装はそれをそのまま使う）と相性が良い

## 検討した他の選択肢

### CSS Modules

スコープ分離が効く。

**却下理由**: クラス名がハッシュ化されるため、「契約がクラス名を指定する」という方式と噛み合わない。

### Tailwind v4

書く量が減り、参考元と同じスタックに揃う。

**却下理由**: 上記の抜け道問題と lint の複雑化。

## 帰結

- `design/layout.css` のクラス名が契約側の定義と一致することを検査する仕組みが要る
- スタイルの記述量は増える。ただしレイアウトが 3 種（[DR-0010](./0010-three-layouts.md)）なので許容範囲
