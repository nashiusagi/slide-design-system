# DR-0057: Ready 化の前に自分の差分を読み返し、検証可能な材料を残す

- **状態**: 承認済み
- **日付**: 2026-09-24
- **関連**: [DR-0025](./0025-issue-driven-development-flow.md), [DR-0052](./0052-review-loop-third-exit.md), [DR-0053](./0053-review-coverage-recorded.md), [DR-0054](./0054-decision-reference-checked-by-machine.md)
- **正本**: `.claude/skills/issue-workflow/references/self-check.md`

## 文脈

[`docs/review_log.md`](../review_log.md) に積まれた指摘のうち、機械で決着したものは検査へ昇格してきた（[DR-0044](./0044-bypass-fixtures-required.md) / [DR-0046](./0046-prose-checked-for-canonical-duplication.md) / [DR-0054](./0054-decision-reference-checked-by-machine.md)）。**残っているのは、意味を読まないと判定できないものだ。**

記録されない判断、実装と食い違う説明文、読んだ人が同じ判定に到達できない基準、スコープ外の混入、不変条件を示さないテストタイトル、統合パスを通していない完了条件、着手時のままの PR 本文。[#46](https://github.com/nashiusagi/slide-design-system/issues/46) が挙げた8カテゴリで、[DR-0054](./0054-decision-reference-checked-by-machine.md) が機械判定に向かないとして見送った領域と重なる。

**この形は減っていない。** #46 が立った時点で合計38回、現在は95回で、2.5倍になっている。

どれもレビュアーが毎回見つけている。**つまり読み返せば分かる。** 分からないのではない。共通するのはタイミングだ——実装が終わってから PR 本文を整え、DR を書くかどうかを考える。そのときにはもう、実装中に下した判断の大半が「当たり前のこと」に見えていて、記録に値すると思えない。

## 決定

### 1. Ready 化の直前に読み返す段を置く

`issue-workflow` の手順2 の末尾、`gh pr ready` の直前。**レビューの開始線の手前**に置く。

### 2. 手順の番号は振り直さない

新しい番号の手順にせず、手順2 の中の節として置く。`pr-review` が `issue-workflow` の手順5 を参照しており（あちらの手順1）、`issue-workflow` 自身も手順3〜7 を相互に参照している。**番号を1つ挿すと、それらの参照が黙ってずれる。**

### 3. 残すのは主張ではなく、突き合わせられる材料

「確認した」では残さない。下した判断とその行き先（DR 番号 / PR 本文 / 見送りの理由）、追加した説明文とそれが説明している実装の在り処、テストタイトルとその不変条件——**読み手が自分で開いて確かめられる形**で書く。

このリポジトリは一貫して申告を判定の入力にしない（[DR-0052](./0052-review-loop-third-exit.md) / [DR-0053](./0053-review-coverage-recorded.md)）。セルフチェックは構造的に自己申告なので、**検証を読み手側でできるようにする**ことで同じ扱いへ揃える。

### 4. 結果は PR コメントとして残す

PR 本文ではなくコメントにする。本文は手順6 で書き直すため、そこへ置くと読み返した時点の記録が上書きされる。**コメントが無い PR は、この段を通していない**——時系列で判別できる。

### 5. `pr-review` の観点からは外さない

この段で潰す想定のカテゴリも、レビュー観点の守備範囲に残す。二重に見る。

### 6. 効かなければ項目を見直す

この段を通った PR が**5本**たまった時点で、対象8カテゴリの1 PR あたりの計上回数を [`docs/review_log.md`](../review_log.md) で測り直す。**導入時点の基準は 28 PR / 累計95回 = 1 PR あたり 3.4 回。** これを下回っていなければ、項目が悪いか、段の置き場所が悪い。どちらかを見直す。

## 理由

**レビュアーが見つけられているなら、読み返せば分かる。** 機械が判定できないことと、人が読んで判定できないことは別だ。この8カテゴリは後者ではない。足りないのは能力ではなくタイミングで、実装直後という一番「当たり前」に見える瞬間に判断が埋もれる。

**Claude の消費を減らす経路が、指摘を減らすことしかない。** レビュー1周は6観点で50〜60万トークンかかる。周を1つ減らせばそれが丸ごと浮く。検査へ昇格できないカテゴリについては、**指摘が出る前に潰す**以外に周を減らす手が無い。

**二重に見ることは無駄ではない。** この8カテゴリは「書いた本人が見落とす形」を集めたものだ。だから本人のチェックが最も弱いのがまさにこの領域になる。観点を外すと、セルフチェックが見逃したものを誰も拾わない。節約したいのは周の数であって、見る目の数ではない。

## 検討した他の選択肢

**別のサブエージェントに読み返させる。** 自己申告を構造的に避けられる。採らないのは、Claude の消費を減らすのがこの決定の目的の一つで、そこへエージェントを1体足すのは目的と逆を向くからだ。成果物を検証可能にすれば、**検証はレビュアーと人が既に通る工程の中でできる。**

**この段で潰す想定のものをレビュー観点から外す。** 節約は最大になる（日本語ドキュメントの観点はほぼ仕事が無くなる）。採らない理由は決定5 のとおり。

**チェックしたことを主張するだけにする。** 最も軽い。採らないのは、それが現状と変わらないからだ。実装者は既に「読み返したつもり」でいる。

**新しい番号の手順にする。** 流れとしては読みやすい。採らない理由は決定2 のとおり。

## 帰結

- `issue-workflow` の手順2 に節が増え、Ready 化の前に PR コメントが1つ増える
- チェック項目とカテゴリの対応は `references/self-check.md` が持つ。累計の値は `docs/review_log.md` が正本で、書式側へ書き写さない
- [DR-0025](./0025-issue-driven-development-flow.md) が固定したフローに段が1つ増える。同 DR の状態欄へその旨を書く
- `docs/review_log.md` の対象8カテゴリの状態欄が「未着手」から、この段が扱う旨へ変わる。**検査へ昇格したわけではない**——機械は落とさない
- 効果は5本後に測る（決定6）。**減らなければ項目を見直す。** この決定自体は、効かないことが分かった時点で見直しの対象になる
