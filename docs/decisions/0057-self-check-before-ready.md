# DR-0057: Ready 化の前に自分の差分を読み返し、検証可能な材料を残す

- **状態**: 承認済み
- **日付**: 2026-09-24
- **関連**: [DR-0025](./0025-issue-driven-development-flow.md), [DR-0052](./0052-review-loop-third-exit.md), [DR-0053](./0053-review-coverage-recorded.md), [DR-0054](./0054-decision-reference-checked-by-machine.md)
- **正本**: `.claude/skills/issue-workflow/references/self-check.md`（チェック項目と書式）／`docs/review_log.md`（対象カテゴリ、累計、導入時点の基準値）

## 文脈

[`docs/review_log.md`](../review_log.md) に積まれた指摘のうち、機械で決着したものは検査へ昇格してきた（[DR-0044](./0044-bypass-fixtures-required.md) / [DR-0046](./0046-prose-checked-for-canonical-duplication.md) / [DR-0054](./0054-decision-reference-checked-by-machine.md)）。**残っているのは、意味を読まないと判定できないものだ。**

[#46](https://github.com/nashiusagi/slide-design-system/issues/46) が挙げた8カテゴリで、どれがそれかは [`docs/review_log.md`](../review_log.md) の状態欄と `references/self-check.md` の対応表が持つ。

**[DR-0054](./0054-decision-reference-checked-by-machine.md) が見送った `decisions/consequence-not-followed` などとは、判定不能の理由（意味を読まないと決着しない）を共有する。** ただしあちらが見送ったカテゴリをこの段が引き取るわけではない——DR-0054 の帰結「引き続きレビューの観点（決定記録との整合）が持つ」はそのまま有効だ。**8カテゴリの外には、機械へも昇格せずこの段も扱わないカテゴリが残る。**

**この形は減っていない。** #46 が立った時点の合計と現在の累計は [`docs/review_log.md`](../review_log.md) が持つ。2倍以上に増えている。

どれもレビュアーが毎回見つけている。**つまり読み返せば分かる。** 分からないのではない。共通するのはタイミングだ——実装が終わってから PR 本文を整え、DR を書くかどうかを考える。そのときにはもう、実装中に下した判断の大半が「当たり前のこと」に見えていて、記録に値すると思えない。

## 決定

### 1. Ready 化の直前に読み返す段を置く

`issue-workflow` の手順2 の末尾、`gh pr ready` の直前。**レビューの開始線の手前**に置く。

### 2. 手順の番号は振り直さない

新しい番号の手順にせず、手順2 の中の節として置く。`issue-workflow` の手順番号は複数の場所から指されている——`issue-workflow` 自身が手順3〜7 を相互に参照し、[DR-0052](./0052-review-loop-third-exit.md) と [DR-0053](./0053-review-coverage-recorded.md) が手順3・5・7 を引き、`references/*.md` も手順5 を引く。**番号を1つ挿すと、それらの参照が黙ってずれる。**

### 3. 残すのは主張ではなく、突き合わせられる材料

「確認した」では残さない。下した判断とその行き先（DR 番号 / PR 本文 / 見送りの理由）、追加した説明文とそれが説明している実装の在り処、テストタイトルとその不変条件——**読み手が自分で開いて確かめられる形**で書く。

このリポジトリは一貫して申告を判定の入力にしない（[DR-0052](./0052-review-loop-third-exit.md) / [DR-0053](./0053-review-coverage-recorded.md)）。セルフチェックは構造的に自己申告なので、**検証を読み手側でできるようにする**ことで同じ扱いへ揃える。

### 4. 結果は PR コメントとして残す

PR 本文ではなくコメントにする。本文は手順6 で書き直すため、そこへ置くと読み返した時点の記録が上書きされる。**コメントが無い PR は、この段を通していない**——時系列で判別できる。

### 5. `pr-review` の観点からは外さない

この段で潰す想定のカテゴリも、レビュー観点の守備範囲に残す。二重に見る。

### 6. 効かなければ項目を見直す

この段を通った PR が**5本**たまった時点で測り直す。導入時点の基準値と、その導出（レビュー履歴の行数と対象8カテゴリの累計）は [`docs/review_log.md`](../review_log.md) の候補表前書きが持つ。値をここへ書き写さない——累計はレビューのたびに動くので、写した時点で古くなる。

**測り方を一意にする。**

- **母数は、この段を通した PR だけ。** 通っていない PR は分子（計上回数）からも分母からも除く。通したかどうかの数え方は `references/self-check.md` が持つ
- **起点は PR #72 の次の PR から。** #72 はこの段を導入した PR で、基準値を出した母集団の外にある
- **比べるのは「その5本での対象8カテゴリの計上回数 ÷ 5」と、基準値。** 全 PR の累計で割らない——累計は分母が増えるだけで構造的に下がる

これを下回っていなければ、項目が悪いか、段の置き場所が悪い。どちらかを見直す。

**「5本」に強い根拠は無い。** この段を通した PR が対象8カテゴリを一巡するのに要る本数の見積もりで、それ以上ではない。最初の測定では、本数自体も見直しの対象にする。

## 理由

**レビュアーが見つけられているなら、読み返せば分かる。** 機械が判定できないことと、人が読んで判定できないことは別だ。この8カテゴリは後者ではない。足りないのは能力ではなくタイミングで、実装直後という一番「当たり前」に見える瞬間に判断が埋もれる。

**Claude の消費を減らす経路が、指摘を減らすことしかない。** レビュー1周は6観点で50〜60万トークンかかる。周を1つ減らせばそれが丸ごと浮く。検査へ昇格できないカテゴリについては、**指摘が出る前に潰す**以外に周を減らす手が無い。

**二重に見ることは無駄ではない。** この8カテゴリは「書いた本人が見落とす形」を集めたものだ。だから本人のチェックが最も弱いのがまさにこの領域になる。観点を外すと、セルフチェックが見逃したものを誰も拾わない。節約したいのは周の数であって、見る目の数ではない。

## 検討した他の選択肢

**別のサブエージェントに読み返させる。** 自己申告を構造的に避けられる。採らないのは、Claude の消費を減らすのがこの決定の目的の一つで、そこへエージェントを1体足すのは目的と逆を向くからだ。材料を検証可能にすれば、**検証はレビュアーと人が既に通る工程の中でできる**——`pr-review` の手順2 と手順4 が、セルフチェックのコメントを収集して各観点へ渡す。

**この段で潰す想定のものをレビュー観点から外す。** 節約は最大になる（日本語ドキュメントの観点はほぼ仕事が無くなる）。採らない理由は決定5 のとおり。

**チェックしたことを主張するだけにする。** 最も軽い。採らないのは、それが現状と変わらないからだ。実装者は既に「読み返したつもり」でいる。

**新しい番号の手順にする。** 流れとしては読みやすい。採らない理由は決定2 のとおり。

**Draft PR を作った直後に置く（決定1 の代案）。** 判断を下したそばから書けるので記憶が新しい。採らないのは、**その時点では差分がまだ無い**からだ。この段が見るのは「追加・変更した説明文」「追加したテスト」「完了条件の達成」で、どれも実装が揃ってからでないと書けない。**レビュー呼び出しの中に埋める案**も採らない——あちらはレビュアーを立てる工程で、実装者が自分の差分を読み返す工程とは担い手が違う。

**毎 PR で測る（決定6 の代案）。** 効かないと分かるのが早い。採らないのは、1本では対象8カテゴリのどれが出るかが偏り、増減を項目の良し悪しと切り分けられないからだ。**10本や期間で区切る案**も同じ軸の選択で、本数が増えるほど判定は安定するが見直しが遅れる。5本はその中間の見積もりで、最初の測定で本数ごと見直す（決定6）。

## 帰結

- `issue-workflow` の手順2 に節が増え、Ready 化の前に PR コメントが1つ増える
- チェック項目とカテゴリの対応は `references/self-check.md` が持つ。累計の値は `docs/review_log.md` が正本で、書式側へ書き写さない
- [DR-0025](./0025-issue-driven-development-flow.md) が固定したフローに段が1つ増える。同 DR の**状態欄・該当する決定・帰結の3箇所**へその旨を書き、関連欄にもこの DR を足す（`docs/decisions/README.md` の一部置き換えの運用）
- `docs/review_log.md` の対象8カテゴリの状態欄が「未着手」から、この段が扱う旨へ変わる。**検査へ昇格したわけではない**——機械は落とさない
- 効果は5本後に測る（決定6）。**減らなければ項目を見直す。** この決定自体は、効かないことが分かった時点で見直しの対象になる
- **`0056` は欠番。** [PR #71](https://github.com/nashiusagi/slide-design-system/pull/71) で起こした DR を、その PR ごと取り下げたため。番号は詰めずに空けたままにする——取り下げた経緯を追えるようにするためだ。`decisions:check` は欠番そのものを落とさない（索引の網羅と昇順しか見ない）が、**欠番の番号を地の文で参照すると『存在しない DR』として落ちる**ので、番号はインラインコードで書く
