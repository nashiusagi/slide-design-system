# DR-0003: スライド機構は自作の薄いランタイムで持つ

- **状態**: 承認済み
- **日付**: 2026-09-06
- **関連**: [DR-0004](./0004-phase-1-runtime-scope.md), [DR-0021](./0021-starter-contains-runtime-only.md)

## 文脈

ページ送り、段階表示、スピーカーノート、PDF 印刷、アスペクト比固定のスケーリングといったスライド機構をどこから調達するか。Atlas は業務 UI 部品を HeroUI から調達し「契約は自分が持つ」形を取った。その構造をスライドへ写像するなら、対応する既製基盤を選ぶ判断が必要になる。

## 決定

`Deck` / `Slide` / `Fragment` の 3 コンポーネントと CSS を自作する。既存のスライドフレームワークは使わない。

## 理由

- 既製品を使う価値は「部品が豊富にあるとき」に出る。しかしスライドで必要な部品（タイトル、箇条書き、対比、コード、図）は、どのフレームワークも**デザインシステムとしては**提供しない。既製品から得られるのは機構だけで、契約を書きたい部分は結局自作になる
- 他人の DOM 構造とクラス体系が混ざると、`no-raw-color` や `component-approved` のような契約検査が著しく書きにくくなる
- 実装量は 200〜300 行程度で、難所はスケーリング計算のみ

## 検討した他の選択肢

### Spectacle（React 製プレゼンフレームワーク）

React ネイティブで、ノートや進行制御が最初から使える。

**却下理由**: 内部 DOM とスタイルの制約を背負い、トークンを向こうのテーマへ流し込む層が一枚増える。得られる機構は Phase 1 のスコープ外のものが大半。

### reveal.js を React で包む

印刷・ノート・断片表示が最も成熟している。

**却下理由**: reveal が DOM を直接操作するため React と衝突する。最終 HTML に reveal のクラス体系が混ざり、契約検査の対象が汚れる。

## 帰結

- スピーカーノート表示と PDF 印刷は自前で作ることになる。Phase 1 ではスコープ外とする（[DR-0004](./0004-phase-1-runtime-scope.md)）
- このランタイムは Baseline と Harness の両方へ共通で渡す「機構」の実体になる（[DR-0021](./0021-starter-contains-runtime-only.md)）
