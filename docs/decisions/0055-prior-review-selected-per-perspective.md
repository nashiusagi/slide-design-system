# DR-0055: 前周のレビューは全文を配らず、観点ごとに選別して渡す

- **状態**: 承認済み
- **日付**: 2026-09-24
- **関連**: [DR-0052](./0052-review-loop-third-exit.md), [DR-0053](./0053-review-coverage-recorded.md)
- **実装**: `scripts/select-review-findings.mjs`

## 文脈

`pr-review` は再レビューで、対象差分を前周からの増分へ絞る一方、**前周のレビュー全文を全観点のレビュアーへ渡していた**（手順2）。渡す理由は同じ場所に書かれている——「何を指摘され、それがどう直ったかが見えると、同じ指摘の再生産が減る」。

レビュー記録は周を重ねるほど伸びる。増分は小さくなるのに、添える文脈だけが単調に増える。[PR #61](../reviews/pr-61.md) の5周では、各周の開始時点の記録（ファイル全体の文字数）が 16,266 → 27,641 → 35,000 → 39,607 と伸び、これを観点の数だけ配っていた。

**指摘は既に「どの観点のものか」を持っている。** 各指摘の `指摘した観点` 欄（[`review-file-format.md`](../../.claude/skills/pr-review/references/review-file-format.md)）と、カテゴリIDの接頭辞（[`finding-format.md`](../../.claude/skills/pr-review/references/finding-format.md)）だ。判定を足さなくても選別できる。

## 決定

### 1. 観点ごとに選別して渡す

`scripts/select-review-findings.mjs` が、レビュー記録を指摘単位へ分解し、その観点へ渡す分だけを出す。手順2 がこれを呼び、出力を手順4 のプロンプトへ入れる。

### 2. 選別に判定を持ち込まない

読むのは `指摘した観点` 欄とカテゴリIDの接頭辞だけで、指摘の中身は読まない。**意味の判定を挟むと、この工程自体が確率的になり、渡し漏れの原因がレビューの外側へ移る。** 観点をまたぐ関連の拾い上げは [#65](https://github.com/nashiusagi/slide-design-system/issues/65) で別に扱う。

### 3. 欄と接頭辞は和集合を取る

両方が読めたときも、どちらか一方を優先して切り落とさない。欄だけを見ると、欄が省かれた指摘（実データに存在する）が接頭辞という手掛かりを失う。接頭辞だけを見ると、複数観点から挙がったことが消える。**どちらの取りこぼしも渡し漏れであり、決定4 と同じ理由で渡す側へ倒す。**

### 4. 迷ったら渡す

次はいずれも、選別の結果によらず全観点へ渡す。

- **`blocker`。** 最も重い指摘を仕分けで落とす形にしない
- **複数観点から挙がった指摘は、その全部へ。** 独立した観点から同じ問題が見えたことは強い信号で（`review-file-format.md`）、片方だけに渡すとその信号が消える
- **`指摘した観点` 欄の観点名を1つでも解決できなかった指摘。** 接頭辞で確定させると、解決できなかった観点へ渡らないまま「決まった」ことになる
- **欄も接頭辞も解決できない指摘**

### 5. 読めない記録は選別せず全文を渡す

カテゴリID形の見出しを1つでも指摘として取り込めなかったファイルは、選別をやめて全文を出す（警告つき）。

**指摘単位の退避路（決定4）だけでは足りない。** 見出しの形が想定と違って指摘として立ち上がらなかったぶんは、件数にすら入らず、退避路の手前で消える。ファイル単位の退避路がなければ、最も起きやすい失敗の形が無言で通る。

### 6. 観点は絞らない

選別が削るのは**渡す文脈**であって、**立てる観点**ではない。観点が絞られた周は収束に使えない（[DR-0052](./0052-review-loop-third-exit.md) 決定1）。この決定はそこへ影響しない。

### 7. 渡さなかった指摘を記録する

どの指摘をどの観点へ渡さなかったかを、その周の記録に残す（手順6）。**この選別が成立しているかは「渡さなかったせいで同じ指摘が再生産されたか」でしか判定できない。** 記録が無ければ検証できない。

値は手順2 で選別したときの出力をそのまま書く。記録を書く時点ではその周の指摘が追記済みで、測り直すと別の集合を測ることになる。

## 理由

**渡す量が周ごとに増えるのは、渡し方の問題であって、渡すこと自体の問題ではない。** 前周の指摘を渡す目的（再生産を防ぐ）は、その観点に関係する指摘が届けば果たされる。他の観点の指摘まで読ませているぶんは、目的に寄与しない。

**選別の材料を新しく作らない。** 指摘は既に「どの観点から挙がったか」を書いている。判定を足せば観点をまたぐ関連まで拾えるが、それは外部サービスへの依存と、可否の判断を伴う。**土台を先に置き、その上の増分として測る**ほうが、効いたかどうかを切り分けられる。

**失敗の重さが非対称だから、倒し方も非対称にする。** 渡しすぎは選別前の状態に戻るだけで済む。渡し損ねると同じ指摘が再生産され、周が1回伸びる。周が1回伸びれば、削減した量は容易に食い潰される。決定3・4・5 はすべてこの非対称から出ている。

## 検討した他の選択肢

**接頭辞だけで切る。** 指摘を必ず1観点へ割り当てる形で、削減は最も大きい。採らないのは、複数観点から挙がった指摘という**既にある情報**を捨てるからだ。接頭辞は「誰が書いたか」の慣習であり、`指摘した観点` 欄のほうが実データに近い。

**欄が読めたら接頭辞を使わない。** 欄のほうが実データに近いという理屈の素直な延長。採らないのは、欄が省かれた指摘が実データに存在し（`docs/reviews/` には欄を持たない指摘がある）、そこで手掛かりを1つ失うからだ。決定3 のとおり和集合を取る。

**意味の判定で選別する。** 観点をまたぐ関連まで拾えるが、外部サービスへの依存が要り、可否の判断が別にある。#65 で扱う。

**渡すのをやめる。** 記録の再読はゼロになるが、再生産を防ぐ働きも失う。手順2 が全文を渡していた理由を捨てることになる。

**渡さなかった指摘を記録しない（決定7 の代案）。** 記録の手間と、レビュー記録が伸びるぶんを節約できる。採らないのは、それをやると選別が効いているかを誰も確かめられなくなるからだ。この決定は「渡す量を減らすと再生産が増えるかもしれない」というトレードオフの上に立っており、**増えたかどうかを観測できない形で入れるなら、入れない方がよい。**

## 帰結

- `pr-review` 手順2 は、前周のレビュー全文ではなく選別後のものを渡す。手順4 のプロンプトにその受け口がある
- その周の記録に、渡した量と渡さなかった指摘が残る（手順6 / `review-file-format.md`）
- 接頭辞と指示ファイルの対応は `finding-format.md` が持ち、観点名と指示ファイルの対応は `SKILL.md` 手順4 の観点表が持つ。**どちらも観点名と接頭辞の両方を持たない**——両方が持つと、呼び方を変えたときに片方だけが古くなる。重要度の語彙も `finding-format.md` の重要度表から読む
- 観点名の照合は、正本の名前と欄の値の両方を同じ規則で正規化してから行う。**正本の観点名そのものが括弧を含みうる**（`決定記録（DR）との整合`）ため、注記だけを剥がす形にすると正本が照合できなくなる
- 選別の効きは PR ごとに変わる。`blocker` が多い周、複数観点から挙がった指摘が多い周ほど削減は小さくなる（いずれも全観点へ渡るため）
- 実測（[PR #61](../reviews/pr-61.md) の記録、46件 / 6観点）: **271,344 文字 → 113,222 文字、削減 58%。** 母数は「記録の全文 × 観点数」で、選別前に実際に渡していたものと同じ取り方にしてある。接頭辞で各指摘を1観点へ割り当てるだけなら削減 83%（残り 17%）まで届くが、決定3・4 で上乗せして渡すぶんを引いた結果が、この 58% にあたる
