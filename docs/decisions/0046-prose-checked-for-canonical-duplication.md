# DR-0046: 正本の複製は散文まで機械検査の対象にする

- **状態**: 承認済み
- **日付**: 2026-09-12
- **関連**: [DR-0009](./0009-five-layer-contract.md), [DR-0013](./0013-agent-skill-and-resolver.md), [DR-0024](./0024-decision-records-not-adr.md), [DR-0028](./0028-single-check-entry-point.md), [DR-0033](./0033-derived-values-are-generated-and-checked.md), [DR-0044](./0044-bypass-fixtures-required.md)
- **実装**: `scripts/check-canonical-duplication.mjs`
- **正本**: 検査が読む値と一覧は `design/tokens.json` / `design/rules.json` / `design/layouts/` / `design/components/`。走査する場所は同スクリプトの `SCAN_ROOTS`、例外は `scripts/canonical-duplication-allowlist.json`

## 文脈

[指摘ログ](../review_log.md)で最も体積が大きい塊は「正本に置いた値・一覧が、正本を参照できない場所へ写し取られた」ことだ。`contract/design-data-duplicated` / `contract/contract-structure-duplicated` / `contract/value-outside-source-of-truth` / `decisions/dr-restates-canonical-value` の4カテゴリで、初出は PR #13、最終は PR #51、合計は26回になる。

26回とも人のレビューが見つけた。見つけられたということは、26回とも書かれてしまったということでもある。書いた側は複製だと思っていない。理由は毎回「読み手に親切だから」「ここにも無いと分からないから」で、もっともらしい。**もっともらしい違反は、人の注意では止まらない。**

[DR-0033](./0033-derived-values-are-generated-and-checked.md) は「導出値は生成し、再計算と突き合わせる」ことを決めた。しかし散文——生成できない文章、すなわち `README.md` / DR / `SKILL.md` やカタログのコードに書かれた説明——は生成できない。以後この DR ではこれらをまとめて「文書」と呼ぶ。生成できない場所は、これまで人のレビューだけが見ていた。

## 決定

**正本の値・一覧・対応表が、正本の外の文書に現れることを機械検査の対象にする。** `scripts/check-canonical-duplication.mjs` を `pnpm canonical:check` として `pnpm check` の静的検査段へ置く（[DR-0028](./0028-single-check-entry-point.md)）。

検査は3つの決めごとで成り立つ。

**1. 集める先は正本そのもの。** 検出する値・一覧をスクリプトへ列挙しない。トークンの値、`design/rules.json` の閾値、layout / component の名前と `allowedIn` の対応は、すべて実行時に正本を読んで組み立てる。正本が変われば検出対象も変わる。

**2. 値の一致は「値らしい形」で判定する。** 散文には正本と無関係な数字が現れる（「Phase 1.5」「3 周」）。そのままの数値一致では誤検出が支配的になり、検査が無視される。数値について判定する形は3つに絞る。

- 数値に `px` / `%` が続く形
- インラインコードだけで置かれた値
- キャンバス寸法の対（`<幅>x<高さ>`）

文字列の値（色・書体・影）は、散文の普通の語と衝突しない長さを持つものだけ、形を問わず一致で見る。下限に満たない短い値（`none` など）は見ない。下限の数値そのものはスクリプトが持つ。判定の調整は実装側の裁量で、正本でも決定でもないからだ。例外の理由に求める最小の文字数も同じ扱いにする。

**3. 一覧・対応表の複製は順序を問わずに見る。** 正本の一覧（layout 名、component 名、ルールID）の項目が、同じ表・箇条書きの中に1行1件で2件以上並べば複製として報告する。1行にその一覧の全項目が並ぶ形も報告する。項目のあいだに空行が入っていても1つの箇条書きとして扱う。対応表（`allowedIn`）は、正本にある対が同じ行に並ぶ行を数える。component と layout が同名の対は、1つの語が両側を兼ねて対応表でない箇条書きまで報告するため、この判定では見ない。

例外は `scripts/canonical-duplication-allowlist.json` に `path` / `target` / `reason` / `count` で登録する。**`reason` が無い、または短すぎるエントリは検査が落ちる。** 使われていないエントリ、抑えた件数が `count` と違うエントリも落ちる。

`docs/reviews/` は走査しない。レビュー記録は過去の指摘を引用するために値を含むのが正常であり、書き換えない履歴だからだ。

## 理由

- **26回のうち26回を人が見つけた、という事実は自動化の根拠として十分に強い。** 同じ判断を人が繰り返す場所は、機械が持つべき場所である
- **集める先を正本にすると、検査自身が複製にならない。** 値をスクリプトへ列挙すると、この検査こそが `contract/design-data-duplicated` の最新の実例になる
- **「値らしい形」に絞るのは、検査を無視されないため。** 誤検出が多い検査は、例外登録で骨抜きにされるか、実行されなくなる。塞げていない形は既知の抜け道として帰結に書き、テストで固定する（[DR-0044](./0044-bypass-fixtures-required.md) の考え方を、スライドの検査ルール以外へも当てる）
- **順序を問わないのは、並べ替えで素通りさせないため。** Issue #42 は「同順で並ぶ」形を挙げているが、順序を要求すると行を入れ替えるだけで抜けられる。順序を問わない判定は同順の場合を含む
- 例外に理由を必須にするのは、「もっともらしい理由」を書き残させるため。理由が書かれていれば、次のレビューがその理由自体を検査できる。件数まで固定するのは、1つの例外がそのファイルの新しい複製を黙って飲み込まないため

## 検討した他の選択肢

### 値の一致をそのまま（形を問わず）見る

抜け道が最も少ない。

**却下理由**: `design/tokens.json` の `space` は素の整数で刻まれており、散文のあらゆる数字と衝突する。誤検出が本物を埋め、例外リストが数百行になる。塞ぎ方を強くした結果として検査が使われなくなるのでは、塞いでいない。

### 検出する値をスクリプトの定数として列挙する

形ごとに細かく調整でき、誤検出を個別に潰せる。

**却下理由**: 正本の値をスクリプトへ書き写すことになる。この検査が禁じている行為そのものであり、正本を直したときに検査だけが古い値を見る。

### 既存の `checkSkillNoDesignDataDuplication`（`scripts/validate-design.mjs`）を拡張する

新しいスクリプトを増やさない。

**却下理由**: あちらの対象は `skills/slide-harness/SKILL.md` 1ファイルで、色の値と、文章（layout の役割説明、rule の description、`DESIGN.md` の行）を、そのファイルに含まれるかどうかで見る（[DR-0013](./0013-agent-skill-and-resolver.md) 帰結）。こちらは走査対象が広く、判定も値・一覧・対応表で分かれる。同じ関数に入れると、対象と判定形式の組み合わせが増えて守備範囲が読めなくなる（`inspection/rule-scope-inconsistent`）。**文章の複製は既存の検査、値・一覧・対応表は新しい検査**と分ける。

### 正本の宣言を機械可読な1ファイルへ集約する

`contract/source-of-truth-ambiguous`（通算5回）にも同時に効く。

**却下理由**: この検査が要るのは「どの値が正本にあるか」であって、「どのファイルが正本か」の宣言ではない。集約ファイルを作れば `README.md` の正本表と二重管理になり、本 DR が潰そうとしている複製をもう1つ増やす。`source-of-truth-ambiguous` は別の Issue で扱う。

## 帰結

- 検査を `pnpm check` の `design:check` の直後に置く。正本を読むだけで走り、ビルド出力を要さない（[DR-0028](./0028-single-check-entry-point.md)）
- 走査する場所の一覧は `scripts/check-canonical-duplication.mjs` の `SCAN_ROOTS` が持つ。ここへは写さない。除外の方針だけを決めておく——この検査が読む正本そのもの（対象にすると自己言及になる）、正本の一部として値や名前を持つ契約データ（`design/decks/`）、書き換えない履歴（`docs/reviews/`）は走査しない
- **塞げていない形は次のとおり。** いずれも既知の抜け道として残し、テストで固定する
  - 単位もインラインコードも伴わない裸の数値（「コントラスト比は 9.9 以上」のように書く形）
  - `px` / `%` 以外の単位、および数値と単位のあいだに装飾が入る形
  - 散文の普通の語と衝突する短い文字列の値
  - HTML の表や見出しで一覧を組む形（箇条書き・表の記法だけを見る）
- **例外と報告の粒度には、次の限界がある。** どれも「もっと細かくすると維持できなくなる」側で選んでいる
  - 例外は行の位置を固定しない。同じファイルの同じ正本について、登録済みの複製が消えて別の箇所に同数の複製が生まれると、`count` は一致したままになる。行番号を持たせると、無関係な編集のたびに例外が壊れる
  - 同じ値を複数の正本が持つとき（別のトークンが同値のとき）、報告は1件で、在り処をすべて挙げる。例外はそのうち1つを名指しすれば足りる。文書に書かれた値が同じである以上、どちらを写したのかは区別できない
  - 一覧の判定は「同じ箇条書き・表に2件以上」で、書かれている話題までは見ない。別々の話題の項目が同じ箇条書きに並び、それぞれ別の名前に触れていると複製として報告する。誤検出を避けるために離して書けるようにすると、離すだけで抜けられる
- SKILL.md の色の値は、既存の `checkSkillNoDesignDataDuplication` とこの検査の両方が報告する。どちらか一方へ寄せるかは、どちらかの守備範囲を変える Issue で決める
- 例外を足すときは `reason` に「なぜ正本を参照できないのか」を書く。例外にしてよいのは次の型で、**これに当てはまらないなら本文を正本参照へ書き換える**
  - その文書がその値・一覧を決めた当事者である（決定記録そのもの、実験の記録）
  - 正本とは無関係な記述の値が偶然一致しただけで、正本が変わっても追随してはならない
  - その場所から正本を参照する手段が無い（CSS から JSON を読めない、など）
- 正本に値・一覧を足すと検出対象が自動で増える。既存の文書が落ちたときは、上の切り分けで直すか登録するかを決める
- `docs/reviews/` を除外している以上、レビュー記録の中の値は誰も検査しない。レビュー記録は履歴であり、そこから値を写す読み手を想定しない
