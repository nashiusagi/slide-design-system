# DR-0061: このリポジトリの言語は語彙・意味・語用を `docs/glossary.json` に持ち、統語は既存の正本へ委ねる

- **状態**: 承認済み
- **日付**: 2026-10-11
- **関連**: [DR-0024](./0024-decision-records-not-adr.md), [DR-0028](./0028-single-check-entry-point.md), [DR-0033](./0033-derived-values-are-generated-and-checked.md), [DR-0046](./0046-prose-checked-for-canonical-duplication.md), [DR-0057](./0057-self-check-before-ready.md), [DR-0060](./0060-self-check-measurement-aligned.md)

## 文脈

レビューで最も多く出ている日本語ドキュメントの指摘は `writing/term-inconsistency`（同じものが複数の呼び名を持ち、外延も揺れる）で、累計は [`docs/review_log.md`](../review_log.md) が持つ。[#44](https://github.com/nashiusagi/slide-design-system/issues/44) は、これを用語集と機械検査で止めると決め、何をどこに持つかの判断を [#80](https://github.com/nashiusagi/slide-design-system/issues/80) に切り出した。

この DR では、`docs/glossary.json` を**用語集**と呼ぶ。人が読むために生成する `docs/GLOSSARY.md` は**用語集の生成物**と呼び、用語集とは別のものとして扱う。

用語集は、言語の4層——**語彙**（どんな語があるか）・**統語**（概念が何から成るか）・**意味**（語が何を指し、何を指さないか）・**語用**（文脈で意味がどう変わるか）——のうち、語彙だけを書いた成果物になりやすい（[ユビキタス言語](https://scrapbox.io/kawasima/%E3%83%A6%E3%83%93%E3%82%AD%E3%82%BF%E3%82%B9%E8%A8%80%E8%AA%9E)）。

このリポジトリで出た `writing/term-inconsistency` を `docs/reviews/*.md` の指摘の見出しから拾い、どの層の問題かで振り分けた（2026-10-11 時点で見出し31件。同じ PR の中の重複を含む）。**振り分けは人の読みによる。** 1件ずつの振り分けと拾い方は、[PR #85 のコメント](https://github.com/nashiusagi/slide-design-system/pull/85#issuecomment-6106023587)に残してある。

- **語彙**が過半。別の呼び名が並んだもの（`layout` とレイアウト、構文木と `AST`、検証ルールと検査ルールなど）
- **意味**がおよそ3分の1。語は1つなのに指す範囲がずれたもの（[PR #60](../reviews/pr-60.md) の「立った観点」と「返した観点」、[PR #78](../reviews/pr-78.md) の「観点が欠けた PR」、「実測」が2つの意味を持つなど）
- **語用**が少数。文書をまたぐと意味が変わったもの（「ページ送り」が [DR-0031](./0031-navigation-keys-and-no-history.md) と [DR-0003](./0003-custom-slide-runtime.md) で違うなど）
- **統語**は見当たらなかった。DR やレビュー記録の構成は、既に書式ファイルとスキーマが持っている

語彙だけを持つと、意味と語用のずれは止められない。

## 決定

### 1. 用語集は、語彙・意味・語用の3層を持つ。統語は既存の正本へ委ねる

1語ごとに、次を持つ。

- **語彙** — 正式な呼び名（1つ）と、使ってはいけない別称
- **意味** — 外延（何を含み、何を含まないか）と、他の語との関係（例: 立てた観点 ⊇ 返した観点）
- **語用** — 意味が文脈で割れる語だけが持つ、文脈ごとの意味（決定2）

**統語は持たない。** 概念が何から成るかは、既にそれを持つ正本——書式ファイル（例: `.claude/skills/pr-review/references/review-file-format.md`）、`design/schemas/`、`docs/decisions/README.md`——へリンクする。用語集へ写すと、構成の正本が2つになる（[DR-0046](./0046-prose-checked-for-canonical-duplication.md)）。

### 2. 語用は、語ごとの文脈欄で持つ。文脈欄は意味だけを持ち、機械は読まない

文脈の一覧を先に固定しない。意味が文脈で割れる語にだけ、「この文脈ではこの意味」を書く。

**文脈欄は、別称を禁じる範囲を持たない。** 範囲を持たせると、文脈欄が「文脈ごとの意味」と「別称を禁じる範囲」の2役を兼ね、1語が複数の文脈を持つときや、両方の文脈にまたがるファイル（`docs/decisions/`、`README.md`）で、どこで落とすかが決まらなくなる。

文脈をパスで固定する方式（例: 設計契約 = `design/` ほか、開発フロー = `.claude/skills/` ほか）へ切り替える条件と、一部の場所でだけ別称を禁じたい語の扱いは、[#84](https://github.com/nashiusagi/slide-design-system/issues/84) が受け持つ。

### 3. 用語集は `docs/glossary.json`。生成物の `docs/GLOSSARY.md` はそこから作る

用語集を `docs/glossary.json` に置き、その形を検証するスキーマを `docs/glossary.schema.json` に置く。`docs/GLOSSARY.md` は生成物で、直接編集しない。生成結果と用語集の乖離は `pnpm check` で検出する（[DR-0033](./0033-derived-values-are-generated-and-checked.md) と同じ扱い）。

`design/` には置かない。用語は設計契約と開発フローの両方にまたがり、`design/` はスライドの設計契約を置く場所だからだ。

### 4. 機械で検査するのは語彙だけ。別称は語に1つの一覧で、走査範囲の全体で落とす

`pnpm check` は、用語集に載った別称が走査範囲の文書に現れたら落とす。別称の一覧は語に1つで、場所によって変えない（決定2）。

除外の方針は [DR-0046](./0046-prose-checked-for-canonical-duplication.md) に揃える。走査する場所の一覧は実装が持ち、ここには方針だけを書く。

- **走査しない** — 用語集そのものと生成物の `docs/GLOSSARY.md`（別称を載せるのが役目で、対象にすると自己言及になる）、書き換えない履歴（`docs/reviews/`）
- **使用と言及を書き方では区別しない** — 別称を例として挙げる文（この DR の文脈節など）も、その別称を使った文と同じく落ちる。インラインコードや鉤括弧で囲めば通る、という抜け道を作らないためだ
- **通すときは例外リストに理由と件数つきで載せる** — 例外の型は DR-0046 と同じく、その文書が別称を決めた当事者である（決定記録そのもの）ことと、後から書き換えない記録であることに限る。件数が合わなくなった例外は検査が落とす

意味（外延のずれ）と語用（文脈による意味の違い）は、文を読まないと判定できない。Ready 化前のセルフチェック（決定5）と、`pr-review` の日本語ドキュメント観点で見る。

### 5. 新しい語には、セルフチェックで気付く

`.claude/skills/issue-workflow/references/self-check.md` に、「この PR で新しく定義した語・意味を変えた語」を挙げ、用語集へ載せたか、載せないならなぜかを書く節を足す。`pr-review` の日本語ドキュメント観点は、これまでどおり見る（[DR-0057](./0057-self-check-before-ready.md) 決定5 と同じく、二重に見る）。

### 6. `README.md` の正本表と用語集は、持つものを分ける

`README.md` の「正本の在り処」は、**どのファイルが何の正本か**を持つ。用語集は、**語が何を指すか**を持つ。互いに書き写さない。正本表には `docs/glossary.json`（用語集）と `docs/glossary.schema.json`（その形）の行を足し、`docs/GLOSSARY.md` は `design/theme.css` と同じく生成物として書く。

## 理由

**意味の層を持つのは、意味のずれがレビューで繰り返し出ているからだ。** 別称の禁止だけでは、PR #60 の「立った観点」のように語が1つのまま範囲がずれる形を止められない。外延を用語集に書いておけば、書く人も読む人も同じ定義へ戻れる。

**統語を委ねるのは、既に正本があり、指摘も見当たらないからだ。** 振り分けで統語に入った指摘は無かった。新しく持つと、書式ファイルやスキーマと二重になるだけだ。

**語用を語ごとに持つのは、文脈の一覧を決める材料がまだ少ないからだ。** 語用の指摘は少数で、どんな文脈があるかを先に固定すると、外れたときに一覧ごと直すことになる。意味が割れた語から書き始め、文脈が積み上がってから固定するかを決める（#84）。

**文脈欄に別称の禁止範囲を持たせないのは、範囲の規則が文脈の決め方に依存するからだ。** 範囲を持たせると、1語の複数の文脈の範囲をどう合わせるか、どちらの文脈にも属するファイルをどう数えるかを、文脈の一覧が無いまま決めることになる。それは #84 で文脈の切り方と一緒に決める方が筋がよい。それまでは、別称は場所を問わず別称として扱う。

**JSON を用語集にするのは、検査が読む値だからだ。** 別称の一覧は `pnpm check` が読む。Markdown を解析する方式は書式の揺れに弱い。`scripts/select-review-findings.mjs` は、見出しの深さが記録ごとに揺れていたせいで、指摘を丸ごと取りこぼしたことがある（`parseFindings` のコメント）。人が読む形は生成で用意できる。

**機械で語彙だけを見るのは、それが文字列の一致で判定できる唯一の層だからだ。** 意味や語用を機械で見ようとすると、誤検知を抱えた警告にしかならない。それは人が読む段に置く。

**除外の方針を DR-0046 に揃えるのは、同じ形の検査だからだ。** どちらも散文を文字列で走査し、決めた当事者の文書と履歴に正当な出現がある。方針を揃えれば、例外リストの読み方も1つで済む。

**新しい語に気付く段をセルフチェックに置くのは、語を定義したのが書いた本人だからだ。** 新しい語を足したことを最も確実に知っているのは書いた本人で、Ready 化の前ならまだ直せる。

**正本表と用語集を分けるのは、二重管理を避けるためだ。** DR-0046 は「正本の宣言を機械可読な1ファイルへ集約する」案を、`README.md` の正本表と二重管理になるとして却下した。用語集が「どのファイルが何の正本か」まで持てば、同じ二重管理を作る。用語集が持つのは語の意味で、ファイルの役割は正本表が持つ。

## 検討した他の選択肢

**4層すべてを持つ。** 統語まで1箇所で読める。採らないのは、書式ファイルとスキーマが既に統語を持ち、二重になるからだ。

**語彙と意味だけを持ち、語用は別の語として登録する。** 最も小さく始められる。採らないのは、同じ語が文脈で別のものを指すこと自体が残り、2つの語の関係が用語集から読めなくなるからだ。

**文脈をパスで固定する。** 機械で扱いやすい。採らないのは、`docs/decisions/` と `README.md` が両方の文脈にまたがり、固定すると最初から例外が要るからだ。切り替えの条件は #84 で考える。

**文脈欄に別称を禁じるパスの範囲を持たせる。** 一部の場所でだけ禁じたい語を扱える。採らないのは、上の「理由」のとおりで、範囲の合わせ方とまたがるファイルの扱いが文脈の決め方に依存するからだ。

**インラインコードや鉤括弧で囲んだ別称を、言及とみなして落とさない。** 例外リストが要らなくなる。採らないのは、囲むだけで別称を通せる抜け道になるからだ。

**`docs/GLOSSARY.md` を Markdown のまま用語集にする。** 生成の仕組みが要らない。採らないのは、検査が読む値を Markdown の書式から取ると、書式の揺れで検査が黙って外れるからだ。

**`design/glossary.json` に置く。** 機械が読む正本を `design/` に集められる。採らないのは、`design/` の意味が「スライドの設計契約」から広がるからだ。

**新しい語に気付く経路を `pr-review` の観点だけにする、または機械で候補を挙げる。** 前者は書いた本人の段を増やさずに済む。後者は人に頼らない。採らないのは、前者は Ready 化の後にしか気付けず、後者は太字の定義文などを拾う誤検知が多く、落とさない警告にしかならないからだ。

**正本ファイルを語として用語集に載せ、正本表をそこから引く。** 「正本」が何を指すかと、どのファイルが正本かを1箇所で読める。採らないのは、決定6 の理由のとおり、`README.md` の正本表と二重管理になるからだ。

## 帰結

- 用語集・スキーマ・生成・別称の検査・例外リストは [#81](https://github.com/nashiusagi/slide-design-system/issues/81) が作る。用語集の項目の形はスキーマが正本になり、この DR は層と置き場所と方針だけを持つ。#81 で `**正本**:` 行と、`README.md` の正本表の2行を足す
- **文字列の一致で塞げない書き方がある。** 大文字と小文字、全角と半角、語の間に空白を挟む形、改行で語を割る形などだ。#81 は、正規化して塞ぐ形と塞がない形を列挙し、塞がない形をテストで固定する（DR-0046 と同じ扱い）
- `self-check.md` に節が1つ増える（決定5）。これも #81 が入れ、同ファイルの「チェック項目と、対応するカテゴリ」の表に `writing/term-inconsistency` の行を足す
- **`writing/term-inconsistency` は、セルフチェックの効果測定の対象に入る。** #81 は `docs/review_log.md` の候補表でこのカテゴリの状態を `セルフチェックで扱う` にし、別称は `pnpm check` が落とすことを併記する。`review-log-format.md` の状態の値の表は `セルフチェックで扱う` を「`pnpm check` は落とさない」と書いているので、一部を機械が見るときは併記する旨をあわせて足す。状態が変わるので、[DR-0060](./0060-self-check-measurement-aligned.md) の帰結に従って基準値を数え直す
- 文脈をパスで固定する方式へ切り替える条件と、一部の場所でだけ別称を禁じたい語の扱いは、#84 で決める
- 意味と語用は機械では落ちない。外延のずれは、これからもセルフチェックとレビューで見つける形になる
