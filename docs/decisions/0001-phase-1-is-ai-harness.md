# DR-0001: Phase 1 は「AI に書かせる Harness」から始める

- **状態**: 承認済み
- **日付**: 2026-09-06
- **関連**: [DR-0014](./0014-baseline-comparison.md), [DR-0017](./0017-key-message-required-body-optional.md)

## 文脈

「スライド作成環境」には二つの重心がありうる。AI が主役でデザイン契約と機械検査が妥当性を担保する形（Design Harness の適用）と、人間が主役でデザインシステムが「整ったテーマ」として機能する形（オーサリング環境）である。両者は必要な実装が大きく異なり、同時に着手すると両方が半端になる。

## 決定

Phase 1 で「AI に書かせる Harness」を作り、Phase 2 で「人間が書くオーサリング環境」へ広げる。

## 理由

- Harness を先に作ると、契約・検査・修正ループという最も難しい部分の設計が固まる。オーサリング環境はその上に載る
- 逆順にすると、後から契約と検査を差し込む際に、人間が書いた自由なコードが契約に適合せず作り直しになる
- Phase 1 の成果物（契約・lint・measure）は Phase 2 でもそのまま働く。逆方向の再利用は成り立たない

## 検討した他の選択肢

### 人間が書くオーサリング環境から始める

Markdown 等を書けば整った HTML スライドが出る形。デザインシステムは「テーマ」として機能する。

**却下理由**: 「AI が生成するデザインの妥当性を誰がどう担保するか」という Design Harness の主題が消える。ビルダがすべて保証してしまい、検査対象が痩せる。

### 両方をフル装備する

**却下理由**: 作るものが倍になり、どちらも完成しないリスクが高い。

## 帰結

- Phase 1 の設計判断はすべて「AI が読めるか」「機械が検査できるか」を基準に行う
- ただし Phase 2 で困らないことを都度確認する。特に deck 契約の形式（[DR-0016](./0016-deck-contract-markdown.md)）と AI の裁量範囲（[DR-0017](./0017-key-message-required-body-optional.md)）は両フェーズの接合部として設計する
