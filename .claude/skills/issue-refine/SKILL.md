# Issue の現状把握・分割・書き直し

## このスキルが解こうとしている問題

Issue が大きくなると、1本に論点・人の判断待ち・実装作業が詰め込まれる。本文も長くなり、読み手が「結局何をすれば終わりか」を掴むまでに時間がかかる。そのまま `issue-workflow` に乗せると、判断待ちの項目で手が止まるか、1 PR に収まらずレビューの上限周回に当たる。

分割や書き直しは毎回手作業で行われていて、やり方がぶれる。このスキルは**何を読んで現状を掴むか、いつ分けるか、どの形で書くか、何を確かめてから反映するか**を固定する。

決めた理由と却下した選び方は [DR-0058](../../../docs/decisions/0058-issue-refine-skill.md) にある。手順を変えるときは先にそちらを読むこと。

## 手順

### 0. Issue と周辺を読む

```bash
gh issue view <番号> --json number,title,body,labels,state,comments,parent,subIssues,url
gh api --paginate repos/{owner}/{repo}/issues/<番号>/timeline --jq '.[] | select(.event=="cross-referenced") | .source.issue | {number, title, state, pull_request: (.pull_request != null)}'
```

本文とコメントに加えて、**この Issue を参照している PR と Issue**を timeline から拾う。本文だけを読むと、コメントで方針が変わった、関連 PR で一部が片付いた、といった現状を落とす。

本文やコメントが指している DR・レビュー記録・コードも開く。**書かれている「現状」が今も正しいかは、指している先で確かめる。** Issue が立ってから main が動いていることは珍しくない。

`state` が `CLOSED` なら、ここで止めてユーザーに伝える。閉じた Issue を書き換えない。`parent` が既にある（この Issue 自身がサブ Issue）なら、分割はしない（手順2）。

### 1. 現状を整理する

読んだ結果を、次の3つに振り分ける。

- **終わっている** — 根拠（PR・コミット・ファイル）を添える。根拠を示せないものはここに入れない
- **残っている（実装）** — 読めば手を動かせる作業
- **残っている（判断待ち）** — 次の2つのどちらかに当たる項目**だけ**が入る。Issue が「人が決める」と明示しているもの／選択肢を並べて結論を書いていないもの。**それ以外は、人の判断が要りそうに見えても「残っている（実装）」に入れ、提示の中で触れる**——実行する側の見立てで判断待ちを増やすと、判定1（手順2）の結果が実行ごとに揺れる

**元の本文の完了条件（チェックリスト）は1件ずつ、上の3つのどれかへ入れる。** 手順4の行き先表の入力になる。

あわせて、**元の本文が挙げている問題（困りごと）を列挙する。** 見出しの名前は問わない（「問題1」「目的」など）。手順2 の判定2 と、手順3 の「解決したい課題」の入力になる。元の本文が問題を挙げていなければ、その旨を書く。

### 2. 分けるかを判定する

次のどちらかに当たれば分ける。どちらにも当たらなければ分けずに書き直すだけにする。

1. **判断待ちと実装が混ざっている** — 手順1で「残っている（判断待ち）」と「残っている（実装）」の両方が1件以上ある
2. **独立にマージできるまとまりが2つ以上ある** — 残っている実装を、「それだけを先に main へ入れても `pnpm check` が通り、かつ手順1 で列挙した元の本文の問題のどれか1つをそれだけで解消する」単位に分けたとき、2つ以上になる。**突き合わせるのは元の本文の問題で、これから書く「解決したい課題」ではない**——書き手が課題の切り方で判定を動かせないようにするためだ

**分け方は判定の形に合わせる。**

- 判定1に当たったら、**判断を1本のサブ Issue にする。** そのゴールは「どれを採るかと理由が DR に記録されている」ことにする。判断に依存する実装は別のサブ Issue にし、「やること」の先頭に依存先を書く
- 判定2に当たったら、まとまりごとにサブ Issue にする

**分けるのは1階層だけ。** この Issue が既にサブ Issue なら分割しない。サブ Issue をさらに分けたくなったら、提示の時点でユーザーにそう書く。階層が深いと、どこを見れば全体が分かるかが消える。

**親 Issue は閉じずに残す。** 親は全体の目的と、サブ Issue の並び・依存関係を持つ場所になる。

### 3. 書き直し案を作る

親もサブも、4節で書く。書式は `references/issue-body.md`。

- **背景** / **解決したい課題** / **やること** / **ゴール**（チェックリスト）

**何を本文に残すかは、`issue-workflow` が実装とその完了判定に使うかで決める。** 使わない経緯・実測の表・議論の往復は、元の本文を退避したコメント（手順5）と、関連 PR・DR・レビュー記録へのリンクで渡す。消すのではなく、置き場所を移す。

**終わっている項目は「やること」から外し、ゴールには `[x]` と根拠のリンクを付けて残す。** 何が済んだかが本文から消えると、次に読む人は同じ確認をやり直す。

案はスクラッチ領域にファイルとして書く。リポジトリの中に置かない（次のコミットに紛れ込む）。

### 4. 案を提示し、承認を待つ

書式は `references/proposal.md`。**この手順が終わるまで、`gh issue edit` / `gh issue create` / `gh issue comment` を一切実行しない。**

**提示の節は、書式のどれも省かない。** とくに本文案は、長くても親・サブすべての全文を会話に出す。要点だけやファイルの在り処だけで承認を取らない——承認する人は、反映後の姿を見ないまま了承することになる。

承認は**明示的な了承の返事**で得る。修正を求められたら案を直し、**直した案をもう一度提示する**。直しただけで反映に進まない。承認は提示した版に対するもので、直した版はまだ誰も承認していない。

### 5. 反映する

承認された案を、次の順で反映する。**順番は、途中で失敗しても元の本文が失われないように決めてある。**

**1. 元の本文を親 Issue のコメントへ退避する。**

```bash
gh issue comment <親番号> --body-file <スクラッチ領域の退避コメント>
```

退避コメントの形は `references/proposal.md` の「退避コメント」。**本文の書き換えより先に行う。** 書き換えに失敗しても、元の本文はコメントに残っている。

**2. サブ Issue を作り、親に紐づける。** 案の並び順に1本ずつ作る。

```bash
gh issue create --parent <親番号> --title "<タイトル>" --body-file <スクラッチ領域のサブ本文>
```

親にラベルが付いていれば、同じラベルを `--label` で付ける。親にラベルが無ければ `--label` を渡さない。

作るたびに発番された番号を控え、**まだ作っていないサブ Issue と親の案に出てくる仮の名前（`サブ1` など）を実番号 `#N` へ置き換えてから**次を作る。後に作るサブ Issue が前のサブ Issue を依存先として指すことがあるからだ。

**逆向きの参照は、作った時点では置き換えられない。** 先に作ったサブ Issue が後のサブ Issue を仮の名前で指している（「実装はサブ2 が受け持つ」など）なら、全部を作り終えてから、そのサブ Issue の本文を置き換えて `gh issue edit <サブ番号> --body-file <置き換えた本文>` で更新する。仮の名前を実番号にするだけで、承認された内容は変えない。

**3. 親 Issue の本文を書き換える。** 仮の名前がすべて実番号になっていることを確かめてから行う。

```bash
gh issue edit <親番号> --body-file <スクラッチ領域の親本文>
```

分割しなかった場合は、1 のあとにこの 3 だけを行う。

### 6. 反映を確かめる

```bash
gh issue view <親番号> --json body,subIssues,comments
gh issue view <サブ番号> --json body,parent   # 作ったサブ Issue ごとに
```

親の `subIssues` はサブの番号とタイトルしか返さず、本文を含まない。**サブの本文は1本ずつ読まないと確かめられない。**

次を確かめ、結果をユーザーへ短く報告する。

- 親の `subIssues` に、作ったサブ Issue がすべて並んでいる
- 各サブの `parent` が親を指している
- 親・サブの本文に、仮の名前（`サブ1` など）が残っていない
- 退避コメントが親に付いている

**食い違いがあれば、黙って直さずに報告する。** 承認されたのは提示した案であって、確認後の手直しではない。

## やらないこと

- **承認前に Issue を書き換えない。** コメント・作成・編集のどれも、手順4の承認より前に行わない
- **分割後の実装をしない。** それは `issue-workflow` の仕事
- **Issue を閉じない。** 終わっている項目が見つかっても、閉じるかどうかは人が決める
- **元の本文を捨てない。** 書き換えの前に必ず退避コメントを残す
- **頼まれていない Issue に手を広げない。** 関連 Issue に気づいたら、提示の中で触れるだけにする

## 参照ファイル

- `references/issue-body.md` — 親・サブ Issue の本文の書式（4節）
- `references/proposal.md` — 承認を求める提示の書式と、退避コメントの書式
