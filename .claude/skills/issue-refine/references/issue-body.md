# Issue 本文の書式（親・サブ共通の4節）

`issue-refine` が書き直す Issue は、親もサブもこの4節で書く。決めた理由は [DR-0058](../../../../docs/decisions/0058-issue-refine-skill.md)。

## なぜ4節か

長い Issue で読み手が迷うのは、**背景・課題・作業・完了条件が同じ文章に混ざっている**ときだ。どこまでが事情の説明で、どこからが頼まれていることかを、読み手が自分で切り分けることになる。

節を固定すると、`issue-workflow` の手順0 が読む場所も決まる。スコープは「やること」、完了の判定は「ゴール」。

## 書式

```markdown
## 背景

<なぜ今これをやるのか。この Issue が生まれた経緯を、判断に要る分だけ書く。
 詳しい経緯・実測・議論は本文に写さず、リンクで渡す（元の本文の退避コメント、PR、DR、レビュー記録）>

## 解決したい課題

<何が困っているのか。箇条書きで、1項目1つの問題>

- <問題>

## やること

<手を動かす作業を、着手できる粒度で並べる。順序や依存があれば書く。
 親 Issue では、サブ Issue を並べる場所になる（下の「親 Issue の場合」）>

1. <作業>

<やらないことがあれば、この節の末尾に置く>

**やらないこと**

- <スコープ外。なぜ外すか、どこで扱うか>

## ゴール

<満たしたら閉じてよい条件。1項目ずつ、読んだ人が「満たした／満たしていない」を
 同じように判定できる形で書く>

- [ ] <条件>
```

## 各節で守ること

**背景は、本文から消しても `issue-workflow` が困らないものを書かない。** 残すかどうかの基準は「実装か完了判定に使うか」で、読み物として面白いかではない。使わないものは消すのではなく、リンク先へ置き場所を移す。

**解決したい課題は、解決策を書かない。** 「〜を作る」は「やること」に書く。課題の節に解決策が入ると、別の解き方を検討する余地が本文から消える。

**やることは、読んだ人がそのまま着手できる粒度にする。** 「検討する」「整理する」で終わる項目は、何ができたら終わりかが読めない。人の判断が要る項目は、実装と同じ Issue に置かない（`SKILL.md` 手順2 の判定1）。

**ゴールは判定できる形にする。** 「分かりやすくなっている」のように、読む人によって判定が割れる項目を書かない。何を開けば確かめられるか（ファイル、コマンド、GitHub 上の表示）が読み取れる形にする。

**終わっている項目はゴールに `[x]` で残し、根拠を添える。**

```markdown
- [x] <条件>（#<PR番号> で済んだ）
```

## 親 Issue の場合

「やること」にサブ Issue を並べ、依存を書く。ゴールには、サブ Issue が閉じることに加えて、**サブ Issue のどれにも属さない全体の条件**があれば書く。

```markdown
## やること

1. #<サブ1> — <一行>
2. #<サブ2> — <一行>（#<サブ1> の判断を待つ）

## ゴール

- [ ] #<サブ1> が閉じている
- [ ] #<サブ2> が閉じている
- [ ] <サブ Issue をまたぐ条件があれば>
```

提示の時点ではサブ Issue の番号が無いので、`#<サブ1>` の代わりに `サブ1` と書く。実番号への置き換えは `SKILL.md` の手順5 で行う。

## サブ Issue の場合

背景の先頭に親を書く。GitHub 上でも親に紐づくが、本文だけを読んだ人にも辿れるようにする。

```markdown
## 背景

#<親番号> の一部。<このサブ Issue が受け持つ範囲>
```

判断を受け持つサブ Issue（`SKILL.md` 手順2 の判定1）は、ゴールに「どれを採るかと、その理由が DR に記録されている」を入れる。**選択肢そのものは「やること」に並べる。** 判断する人が本文だけで比べられるようにする。
