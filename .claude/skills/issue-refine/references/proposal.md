# 承認を求める提示と、退避コメントの書式

## 提示

`SKILL.md` の手順4 でユーザーへ出す。GitHub には書かない——会話に出す。**承認を得るまで、GitHub 上の Issue には何も起きていない状態を保つ。**

```markdown
## #<番号> のリファイン案

### 現状

- **終わっている**: <項目>（<根拠: PR・コミット・ファイル>）
- **残っている（実装）**: <項目>
- **残っている（判断待ち）**: <項目>

<該当が無い区分には「無し」と書く>

### 分割の判定

<判定1（判断待ちと実装の混在）/ 判定2（独立にマージできるまとまりが複数）の
 どちらに当たったか。当たったなら、何と何が根拠か。どちらにも当たらなければ「分けない」>

### 元の完了条件の行き先

| 元の完了条件 | 行き先 |
|---|---|
| <元の項目> | 親 ゴール <n> / サブ1 ゴール <n> / 外した（<理由>） |

<元の本文に完了条件が無ければ、その旨と、ゴールを何から起こしたかを書く>

### 反映の内容

- 親 #<番号> に元の本文を退避するコメントを付ける
- サブ Issue を <n> 本作り、#<番号> に紐づける（<付けるラベル。無ければ「ラベル無し」>）
- 親 #<番号> の本文を下の案で置き換える

### 親 #<番号> の本文案

<全文>

### サブ1: <タイトル>

<全文>

### サブ2: <タイトル>

<全文>

---

この内容で反映してよいですか。直したい箇所があれば教えてください。
```

**本文案は親・サブとも全文を出す。長くても削らない。** 差分や要約、ファイルの在り処だけで出すと、承認する人は反映後の姿を見ずに承認することになる。#73 への最初の適用では、サブ Issue の本文を要点だけ出して承認を取ってしまった。

**行き先表は省略しない。** 元の完了条件が1件も落ちていないことを、承認する人が本文案を読み比べずに確かめられるのはこの表だけだ。

## 退避コメント

`SKILL.md` の手順5 の 1 で、親 Issue に付ける。本文の書き換えより先に投稿する。

````markdown
この Issue を `/issue-refine` で書き直した。書き直す前の本文を残しておく。

<サブ Issue を作った場合は「あわせてサブ Issue を <n> 本に分けた。」と1行添える。
 番号はこの時点では未発番なので書かない——親の本文の「やること」が一覧になる>

<details>
<summary>書き直す前の本文</summary>

<元の本文をそのまま。一切手を入れない>

</details>
````

**元の本文には手を入れない。** 誤字もリンク切れも直さない。退避の目的は「書き直す前に何が書かれていたか」を残すことで、直すとその目的が崩れる。

**上の書式を囲む4連のバッククォートは、この文書での表示用だ。** コメントには含めない。元の本文がコードフェンスを含んでいても、`<details>` の中にそのまま置けば崩れない。`</summary>` の後の空行は消さない——無いと GitHub が中身を Markdown として描画しない。
