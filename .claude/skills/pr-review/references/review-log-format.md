# `docs/review_log.md` の書式

観点別カテゴリの累計。**このファイルが、レビューを検査ルールへ育てる経路になる。**

同じ指摘が何度も出るなら、それは人が毎回見つけるべきものではなく、機械が毎回捕まえるべきものだ。だから数える。

```markdown
# 指摘ログ

レビューで指摘されたカテゴリと、その通算回数。

累計が3回以上になったカテゴリは、`design/rules.json` へのルール化候補として扱う。
何度も人が見つけているなら、機械に見つけさせた方がよい。
ルール化するかどうかの判断は人が行う。このファイルは候補を示すところまで。

**数え方**: 1つのカテゴリは、1つの PR につき1回だけ数える。同じ PR の中で同じカテゴリの
違反箇所が5つ見つかっても +1。数えているのは「違反の数」ではなく
「そのカテゴリが問題として浮上した回数」だから。箇所の数で数えると、
1回のレビューで閾値に到達してしまい、ルール化の判断材料にならない。

最終更新: <YYYY-MM-DD>

## ルール化候補（累計3回以上）

| カテゴリID | 要約 | 累計 | 最終指摘 | 状態 |
|---|---|---|---|---|
| `contract/design-data-duplicated` | 設計データが正本以外へ複製された | 4 | PR #21 | 未着手 |

## 全カテゴリ

| カテゴリID | 観点 | 要約 | 累計 | 初出 | 最終指摘 |
|---|---|---|---|---|---|
| `contract/design-data-duplicated` | 設計契約 | 設計データが正本以外へ複製された | 4 | PR #5 | PR #21 |
| `writing/ambiguous-criterion` | 日本語ドキュメント | 判断基準が曖昧で解釈が割れる | 2 | PR #13 | PR #18 |

## レビュー履歴

| PR | 日付 | blocker | should | consider | レビュー |
|---|---|---|---|---|---|
| #21 | 2026-09-20 | 0 | 3 | 1 | [pr-21.md](./reviews/pr-21.md) |
| #13 | 2026-09-06 | 1 | 8 | 6 | [pr-13.md](./reviews/pr-13.md) |
```

## 更新の手順

1. このファイルを読み、既存のカテゴリIDを把握する
2. 今回の各指摘について、既存カテゴリに合致するか判断する
   - 合致する → 累計を +1、最終指摘を今回のPR番号に更新
   - 合致しない → 新しい行を追加（累計 1、初出と最終指摘は今回のPR番号）
3. 累計が 3 以上になったカテゴリを「ルール化候補」の表へ移す（全カテゴリの表からは消さない。両方に載る）
4. レビュー履歴へ今回の行を足す（新しいものが上）。**同じ PR の行が既にあれば足さず、その行を更新する。** 件数はその PR のそれまでの全周を合算した値にする（置き換えない。累計を減らさないため）
5. 最終更新日を更新する

## 状態の値

ルール化候補の表で使う。

| 値 | 意味 |
|---|---|
| `未着手` | 候補として挙がったが、まだ検討していない |
| `ルール化済み` | `design/rules.json` へ追加した。ルールIDを要約欄に併記する |
| `見送り` | 機械判定に向かないと判断した。理由を要約欄に併記する |

`ルール化済み` になったカテゴリは、その後に同じ指摘が出たら**ルールの抜け道**を意味する。その場合は累計を増やした上で、`inspection/rule-has-bypass` としても記録する。

## 守ること

**カテゴリIDを揺らさない。** 同じ問題に別のIDを与えると集計が壊れる。迷ったら既存IDを使う方へ倒す。

**同じ PR を再レビューしたときは、その PR でまだ数えていないカテゴリだけを足す。** 判定は記憶ではなくこのファイルの状態で行う。全カテゴリ表の「最終指摘」列が既に今回の PR 番号になっていれば計上済み、なっていなければ未計上だ。会話の記憶に頼ると、文脈が圧縮された後に判定できなくなる。

**累計を減らさない。** 指摘が解決されても数は減らない。これは「未解決の問題の数」ではなく「何回見つけたか」の記録だから。減らすと、ルール化すべきかどうかの判断材料が失われる。
