# 指摘の書式（サブエージェントが返す形）

統合役が重複を潰し、カテゴリを付け、重要度順に並べる。そのために形を揃える。

## 返す形

観点ごとに、次の見出しで始める。

```markdown
## 観点: <観点名>

<指摘が無い場合はここに「今回の差分に、この観点で報告すべきものは無い」と書いて終わる>
```

指摘があれば、1件ずつこの形で並べる。

```markdown
### [<重要度>] <一行の要約>

- **カテゴリ候補**: <観点>/<問題の要約をkebab-caseで>
- **場所**: <path>:<line>（複数あれば列挙）
- **何が起きているか**: 事実だけを1〜3文。
- **なぜ問題か**: このプロジェクトで何が壊れるか。可能なら根拠（DR番号、契約ファイル、ルールID）を示す。
- **失敗シナリオ**: 具体的な入力・状態 → 起きること。書けない場合はこの項目を省かず「該当なし（設計上の問題であり実行時の失敗ではない）」と書く。
- **提案**: どう直すか。複数案があるなら並べる。
```

## 重要度

| 値 | 意味 |
|---|---|
| `blocker` | マージ前に直すべき。正本が壊れる、検査が機能しない、DRに反する |
| `should` | 直した方がよい。放置すると後で効いてくる |
| `consider` | 判断は人に委ねる。好みや優先度の問題を含む |

迷ったら低い方を選ぶ。`blocker` が多いレビューは信用されなくなる。

## カテゴリ候補の付け方

既知のカテゴリ一覧を渡されている。**同じ問題なら必ず同じIDを使う。** 表記が違うだけで別IDにすると、集計が意味を失う。

既知に無い問題なら新しいIDを作る。形は `<観点>/<問題の要約>`。

観点のプレフィックスは次を使う。

`contract` / `inspection` / `decisions` / `phase` / `writing` / `code`

例:

- `contract/design-data-duplicated` — 設計データが正本以外へ複製された
- `inspection/rule-has-bypass` — 検査ルールに抜け道がある
- `decisions/undocumented-decision` — DRに無い判断が実装に入った
- `phase/out-of-scope-addition` — フェーズのスコープ外が混入した
- `writing/ambiguous-criterion` — 判断基準が曖昧で解釈が割れる
- `code/silent-failure` — 失敗が握り潰されている

## 守ること

**実際に読んで確かめたことだけを書く。** 差分の行だけを見て推測しない。関連するファイルを開いて確認する。

**成立しない指摘は出さない。** 件数を稼ぐ必要はない。0件で返してよい。

**自分の観点の外へ出ない。** 他は別のレビュアーが担当している。越境すると統合時に重複が増えるだけになる。
