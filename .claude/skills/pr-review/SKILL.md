# PR レビュー（多観点・並列）

## このスキルが解こうとしている問題

このリポジトリは「設計契約 → AI生成 → 機械検査 → 修正」のループを作ることを目的にしている。だから壊れ方が普通のコードベースと違う。よくある壊れ方はこうだ。

- **正本が複製される** — 設計データが Skill やドキュメントや実装へコピーされ、正本が二つになる
- **契約と実装が乖離する** — 契約には書いたが実装が従っていない、あるいはその逆
- **DRに無い決定が黙って入る** — 実装しながら判断したことが、記録されないまま既成事実になる
- **フェーズが溶ける** — Phase 1 のスコープ外のものが混入する、あるいは Phase 2 を塞ぐ設計が入る
- **検査が形だけになる** — ルールは追加されたが抜け道があり、実際には違反を捕まえられない

一般的なバグや可読性の問題は `/code-review` が見る。このスキルは上の5つを主眼に置き、そこへ汎用のコード品質を1枠だけ足した構成にしている。

もう一つの目的がある。**同じ指摘が何度も出るなら、それはレビューで直すべきものではなく、機械検査へ昇格すべきものだ。** だから指摘を観点ごとに数える。3回を超えたカテゴリは `design/rules.json` へルール化する候補として扱う。レビューが検査ルールを育てる経路になる。

**機械へ昇格できないカテゴリは、`issue-workflow` が Ready 化の前に読み返す段で扱う**（[DR-0057](../../../docs/decisions/0057-self-check-before-ready.md)）。意味を読まないと判定できず、`pnpm check` では落ちないものだ。**それらの観点をここから外してはいない。** 二重に見る——あの段は書いた本人が自分の差分を読み返すもので、集めた項目はどれも「書いた本人が見落とす形」だ。本人のチェックが最も弱いのがまさにその領域になる。あちらが潰せていれば、ここへ届く指摘が減る。それが狙いで、見る範囲を狭めることは狙いではない。

## 手順

### 1. 対象の PR を特定する

引数に番号があればそれを使う。無ければ現在のブランチに紐づく PR を探す。

```bash
gh pr view --json number,title,url 2>/dev/null || gh pr list --head "$(git branch --show-current)"
```

どちらでも見つからなければ、PR番号を尋ねる。推測で進めない。

**呼び出しが「再レビュー」だと明示している場合は、以降の手順が変わる。** 同じ PR を何周も回す運用（`issue-workflow` スキル）がある。再レビューかどうかで、見る差分・立てるレビュアーの数・記録の仕方の3つが変わる。呼ぶ側は次を渡してくる。

- **前周のレビュー時点のコミット** — 対象差分の起点になる
- **前周で指摘が出た観点** — 立てるレビュアーを絞る根拠になる
- **観点を絞らないでほしいという要望**（任意） — 渡されたら手順4の絞り込みを行わない

前の2つが渡されていなければ初回として扱う。

**要望が渡されたら、絞らない。** 呼ぶ側には絞られると困る事情がある——`issue-workflow` は、観点が絞られた周を収束に使えない（[DR-0052](../../../docs/decisions/0052-review-loop-third-exit.md) 決定1）。こちらの絞り込みは「前周に指摘ゼロだった観点は見直す価値が低い」という判断（手順4）であって、あちらの抜け方を左右するほどの重みは持たない。要望が無ければ、これまでどおり手順4の基準で決める。

### 2. 差分と文脈を集める

```bash
gh pr view <N> --json number,title,body,files,baseRefName,headRefName
gh pr diff <N>
```

差分が大きい場合も全体を取得する。サブエージェントには差分そのものではなく**取得コマンド**を渡し、各自に読ませる。そうすれば観点ごとに必要な深さで読める。

**再レビューでは、対象を前周からの増分に差し替える。**

```bash
git diff <前周のコミット>..HEAD
```

`gh pr diff` は base からの全差分を返すので、毎周そのまま渡すと既に直した箇所を読み直すことになる。周を重ねるほど無駄が積み上がる。

**あわせて前周の指摘を渡す。何を指摘され、それがどう直ったかが見えると、同じ指摘の再生産が減る。** ただし全文ではなく、その観点に関係する分だけを渡す。

```bash
node scripts/select-review-findings.mjs --review=docs/reviews/pr-<N>.md --perspective=<agents/*.md>
```

出力を、手順4 のプロンプトの「前周の指摘」ブロックへそのまま入れる。**観点ごとに中身が変わる**ので、6つのプロンプトはここだけが異なる。

レビュー記録は周を重ねるほど伸び、それを観点の数だけ配るので、全文を渡すと読ませる量が単調に増える。選別は判定を伴わない——指摘が既に持っている `指摘した観点` 欄とカテゴリIDの接頭辞だけを読み、両方の対応先へ渡す。根拠は [DR-0055](../../../docs/decisions/0055-prior-review-selected-per-perspective.md)。

**渡し損ねを黙って起こさない。** 次はいずれも全観点へ渡る。

- `blocker` の指摘
- 複数観点から挙がった指摘（挙がったすべての観点へ）
- `指摘した観点` 欄の観点名を1つでも解決できなかった指摘
- 欄も接頭辞も解決できなかった指摘

**カテゴリID形の見出しを1つでも指摘として読めなかった記録では、スクリプトが選別をやめて全文を出す**（標準エラーへ警告を出す）。その周はそのまま全文を渡し、書式のどこが読めなかったかを確かめること。

**渡した量と渡さなかった指摘は、その周の記録に残す**（手順6）。この選別が成立しているかは「渡さなかったせいで同じ指摘が再生産されたか」でしか判定できない。

```bash
node scripts/select-review-findings.mjs --review=docs/reviews/pr-<N>.md --report
```

**この出力を控えておく。** 手順6 で書くのは「手順2 で渡した量」であり、そのときファイルにはその周の指摘が追記済みで、走らせ直すと別の集合を測ることになる。

**初回・再レビューを問わず、`docs/reviews/` と `docs/review_log.md` は対象から外す。** これはこのスキル自身の出力であり、レビュー結果をレビューして直す作業は際限なく伸びる。

### 3. 既知の指摘カテゴリを読む

`docs/review_log.md` が既にあれば読む。ここにあるカテゴリIDと要約を、次のステップで全レビュアーへ渡す。既知のカテゴリを知っていると「またこれか」を見つけやすくなり、集計も正確になる。

無ければ空のまま進む（初回）。

### 4. 6つのレビュアーを同時に立てる

**初回は、1回の応答の中で6つすべてを spawn する。** 順番に立てると待ち時間が6倍になる。

**再レビューでは、前周で指摘が出た観点だけを立ててよい。** 指摘ゼロだった観点は、その PR がその観点の守備範囲に触れていないことが多く、次の周で状況が変わる要素が無い。ただし**差分に実装コードが含まれるなら観点は絞らない**（対象の増分への絞り込みは続けてよい）。修正が別の観点を壊す回帰は、絞った観点からは見えないからだ。絞ってよいのは、差分がドキュメント・契約・Skill に閉じているときだけ。

**呼ぶ側が絞らないでほしいと渡してきたなら、差分の性質にかかわらず絞らない**（手順1）。`issue-workflow` は毎周それを渡すので、上の絞り込みが効くのはあちらを経由しない再レビュー——人が直接このスキルを呼ぶ場合だけだ。

**再レビューのレビュアーは Sonnet で立てる**（`model: sonnet`）。初回は Opus のままにする。

差分の性質が違うからだ。初回は base からの全差分を、足場なしで読む。何が正本で何が参照側か、この PR で何が新しく持ち込まれたかを、リポジトリ全体から組み立てる必要がある。再レビューは違う。対象は前周からの増分に絞られ、前周の指摘のうちその観点に関係する分という足場がある。「何を指摘され、それがどう直ったか」が渡っている状態で、その修正が新しい穴を作っていないかを見る仕事になる。

PR #17 の3周目で、4観点すべてを Sonnet に切り替えて確かめた。質は落ちなかった。書かれた指示と実際に書かれた値の食い違いや、追記の見出しが自分自身の周と衝突することまで見つけている。**ただし観測は1回だけで、差分はドキュメントに閉じていた。** 実装コードを含む大きな再レビューで同じかは分かっていない。そういう差分では Opus に戻すことを検討する。

**統合（手順5）は Opus のまま行う。** 成立しない指摘を落とす工程が偽陽性を止める唯一の関門で、ここが緩むと記録された数字そのものが信用できなくなる。

各サブエージェント（`subagent_type: general-purpose`）へ渡すプロンプトは、次の要素で組み立てる。

```
あなたは PR #<N> を「<観点名>」の観点だけからレビューする。

観点の詳細な指示: .claude/skills/pr-review/agents/<file>.md を読むこと。

対象:
  gh pr view <N> --json title,body,files,baseRefName
  gh pr diff <N>

既知の指摘カテゴリ（同じ問題なら同じIDを使うこと）:
<review_log.md のカテゴリID一覧と要約。無ければ「まだ無い」>

前周の指摘（この観点に関係する分。初回はこのブロックごと置かない）:
<手順2 の select-review-findings.mjs --perspective=<この観点の指示ファイル> の出力。
 スクリプトが全文へ縮退した周は、その旨を添えてレビュー記録の全文>

制約:
- 読むだけ。ファイルを編集しない
- 差分に現れていない既存の問題は報告しない。ただし差分が既存の問題を悪化させる場合は報告してよい
- 推測で断定しない。実際にファイルを読んで確認したことだけを書く
- 自分の観点の外は見ない。他の観点は別のレビュアーが担当している

出力形式: .claude/skills/pr-review/references/finding-format.md に従う
```

観点とファイルの対応:

| 観点 | 指示ファイル |
|---|---|
| 設計契約との整合 | `agents/contract.md` |
| 検査ルールの実効性 | `agents/inspection.md` |
| 決定記録（DR）との整合 | `agents/decisions.md` |
| フェーズスコープ | `agents/phase.md` |
| 日本語ドキュメント | `agents/writing.md` |
| コード品質 | `agents/code-quality.md` |

### 5. 統合する

6人の報告が揃ったら、次の順で処理する。

**重複を潰す。** 別の観点から同じ問題が報告されることがある。その場合は一つにまとめ、「複数観点から指摘された」ことを記録する。複数から挙がった指摘は重要度が高い傾向にある。

**検証する。** 各指摘が実際に成立するか、自分でファイルを読んで確かめる。サブエージェントは差分の一部しか見ていないことがあり、文脈を取り違えることがある。**成立しない指摘は落とす。** 落とした理由は会話で一言触れる（黙って消すと、次に同じ指摘が出たときに判断がやり直しになる）。

**カテゴリを付ける。** 既存カテゴリに合致するなら既存のIDを使う。しないなら新しいIDを作る。IDは `<観点>/<問題の要約>` の形にする（例: `contract/design-data-duplicated`）。**同じ問題に別のIDを与えないこと。** 集計が意味を失う。

**重要度順に並べる。** `blocker`（マージ前に直すべき）→ `should`（直した方がよい）→ `consider`（判断はお前次第）。

### 6. 2つのファイルへ記録する

**`docs/reviews/pr-<N>.md`** — このPRのレビュー全文。指摘の本体はここに書く。書式は `references/review-file-format.md`。

**その周に立った観点は必須項目。** 書き方と置き場所は書式が持つ（`references/review-file-format.md`）。なぜ走らせた側が残すのかは [DR-0053](../../../docs/decisions/0053-review-coverage-recorded.md)。

**`docs/review_log.md`** — 観点別カテゴリの累計。既存カテゴリなら回数を +1 し、最終指摘PRを更新する。新規なら行を足す。書式は `references/review-log-format.md`。

**再レビューでは、手順2 で渡した量と渡さなかった指摘も `docs/reviews/pr-<N>.md` へ残す。** 書式は `references/review-file-format.md`。選別が成立しているかは、渡さなかった指摘が後の周で再生産されたかでしか判定できない（[DR-0055](../../../docs/decisions/0055-prior-review-selected-per-perspective.md) 決定7）。

**再レビューでは、その PR でまだ数えていないカテゴリだけを足す。** 既にこの PR で計上済みのカテゴリは、再び指摘されても +1 しない。計上済みかどうかは、手順3で読んだ `docs/review_log.md` の全カテゴリ表で判定する。「最終指摘」列が既に今回の PR 番号になっていれば計上済みだ。**自分がさっき何を数えたかという記憶で判定しない。** 長い並列レビューを挟むと文脈は圧縮され、記憶は残らない。ファイルの状態だけが残る。累計は「そのカテゴリが問題として浮上した回数」であって「指摘された回数」ではなく、1つの PR につき1回だけ数えるからだ（`references/review-log-format.md`）。3周回して3回数えると、1つの PR だけでルール化候補の閾値に届いてしまい、判断材料が壊れる。レビュー履歴の行も、その PR につき1行だけ持つ。件数はその PR の全周を合算した値へ更新する（最新の周の値で置き換えない。収束した周で置き換えると、それまで積み上がった件数が消える）。

**逆に、2周目で初めて出たカテゴリは足す。** そのカテゴリはまだ一度も数えられていない。

累計が3回以上になったカテゴリには、ルール化候補の印を付ける。**その場で `rules.json` を書き換えてはいけない。** 候補として挙げるところまでがこのスキルの仕事で、ルール化するかどうかは人が決める。

### 7. 会話へ要約を出す

ファイルへ書いただけで終わらせない。ターミナルに出すのは次の3つ。

- `blocker` の指摘（あれば全文、無ければ「blocker なし」と明言する）
- `should` 以下は件数と一行要約
- **今回ルール化候補になったカテゴリ**（あれば。これが一番価値のある出力になることがある）

書いたファイルのパスも示す。

## やらないこと

- **ファイルを直さない。** 指摘するところまで。修正するかは人が決める
- **PR へコメントを投稿しない。** 記録はリポジトリ内のファイルに残す
- **`design/rules.json` を書き換えない。** ルール化候補として挙げるだけ
- **差分に無い既存の問題を掘らない。** レビューの単位は PR

## 参照ファイル

- `agents/*.md` — 各観点の詳細な指示。サブエージェントが読む
- `references/finding-format.md` — サブエージェントが返す指摘の書式
- `references/review-file-format.md` — `docs/reviews/pr-<N>.md` の書式
- `references/review-log-format.md` — `docs/review_log.md` の書式
