# 観点: 日本語ドキュメント

## 何を守っているのか

このリポジトリのドキュメントは二つの読者を持つ。人間と、**契約として読む AI** だ。特に `DESIGN.md`、`design/**/*.json` の説明文、`skills/*/SKILL.md`、Issue の完了条件は、AI が判断の根拠にする。曖昧な記述は、AI の出力の揺れとしてそのまま現れる。

だから「読みやすさ」より前に、**解釈が一つに定まるか**を見る。

## 見るべきこと

**多義的な指示**。「適切に」「必要に応じて」「なるべく」のような、判断基準を示さない語。これらは AI にとって何の制約にもならない。基準を数値か具体的な条件で書けるはずのものが、ぼかされていないか。

**選択基準の欠落**。layout や component の契約には「どういうときにこれを選ぶか」が要る。「見た目がこう」ではなく「そのスライドが担う役割がこう」という書き方になっているか。基準が無いと AI は見た目で選び、契約が効かない。

**用語の揺れ**。同じものが複数の呼び名を持っていないか。このプロジェクトでは特に次が揺れやすい。

- 契約 / 設計契約 / デザイン契約
- 正本 / source of truth / 原典
- レイアウト / layout / variant
- 決定記録 / DR / ADR（ADR は使わない。DR-0024 で決めた）
- 検査 / 検証 / チェック（`lint` / `measure` / `review` は固有の意味を持つ語として使う）

**Do と Don't の非対称**。`DESIGN.md` のような方針文書では、「してよいこと」だけでなく「してはいけないこと」が要る。特に、その方針が**誤解されやすい方向**を Don't として書けているか。「整った業務台帳」というメタファに対して「紙の罫線を模すことではない」と書くような、比喩の暴走を止める記述があるか。

**日本語として読めるか**。翻訳調、主語の欠落、係り受けの曖昧さ。ただしこれは上の項目より優先度が低い。

**Issue とコミットメッセージ**。何をしたかではなく、なぜしたかが書かれているか。ただし過剰な要求はしない。

## 報告するときの注意

「曖昧だ」と言うなら、**具体的にどう解釈が割れるかを二通り示すこと**。「Aとも読めるしBとも読める」と書けば、書いた人はすぐ直せる。「曖昧です」だけでは直しようがない。

言い回しの好みは指摘しない。解釈が一つに定まっているなら、多少ぎこちなくてもよい。この観点は文体の統一ではなく、契約としての明確さを見る。
