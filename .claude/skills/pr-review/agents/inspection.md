# 観点: 検査ルールの実効性

## 何を守っているのか

このプロジェクトの主張は「AI が生成したスライドの妥当性を機械判定で担保できる」というものだ。だから検査ルールが**形だけ存在して実際には違反を捕まえない**状態は、他のどんなバグより重い。テストが通っているのに何も検証していない、という状態と同じだからだ。

検査は2系統ある。

- **lint**（ESLint / 静的）
- **measure**（Playwright / ビルド出力に対して実測）

どのルールがどちらの系統かは `design/rules.json` の各ルールの `method` が持つ。

判断が分かれるものは `review` として人が見る。

## 見るべきこと

**抜け道**。追加・変更されたルールを、違反する側の立場で読む。そのルールを回避して同じ問題を起こす書き方が残っていないか。例えば「JSX の色リテラルを検出する」ルールなら、変数経由、テンプレートリテラル、CSS-in-JS、`style` 属性、外部ファイルからの import で回避できないか。**回避方法を具体的に一つ挙げられるなら、それは指摘に値する。**

**テストが違反を捕まえているか**。ルールの追加には invalid ケースのテストが要る。valid だけのテストは「何も検出しないルール」でも通ってしまう。invalid ケースが、実際に想定している違反の形になっているかも見る。

**ルールIDの対応**。`design/rules.json` に書かれたルールと、実装されたルールが1対1で対応しているか。片方だけ増えていないか。rules.json に書いてあるのに実装が無いルールは、「検査していると思っていたが実はしていなかった」を生む。

**severity と method の妥当性**。`error` にすべきものが `warn` になっていないか。機械判定できるものが `review`（人が判断）に逃がされていないか。逆に、判断が分かれるものが機械判定にされて誤検出を生まないか。

**measure 系の検査対象**。measure はビルド出力（`dist/`）に対して実行することになっている。開発サーバーやソースに対して実行していると、本番と違うものを検査することになる。

**`no-overflow` の測り方**。これは検査の中核なので厳しく見る。はみ出しの判定は、要素の実測矩形とキャンバス矩形の比較で行う必要がある。`overflow: hidden` で隠れているだけの要素を「収まっている」と判定していないか。スケーリング（`transform: scale()`）が掛かった状態の座標系で正しく比較しているか。

## 報告するときの注意

「抜け道がある」と言うなら、**その抜け道を通る具体的なコード片を書くこと**。抽象的な懸念は直しようがない。

まだルールが実装されていない段階なら、この観点は空振りする。その場合は「今回の差分に検査ルールの変更は無い」と明言して終える。無理に何かを見つけようとしない。
