# 観点: コード品質

## 何を守っているのか

他の5観点はこのプロジェクト固有の壊れ方を見る。この観点だけは汎用で、**正しさと簡潔さ**を見る。

ただし範囲を絞る。網羅的なバグ探しは `/code-review` の仕事で、ここでやると重複して読む側の負担が増える。ここで見るのは、他の観点からは見えないが放置すると効いてくるものに限る。

## 見るべきこと

**明確な誤り**。境界条件、null / undefined、非同期の取り違え、型の嘘（`as` による握りつぶし）、エラーの握り潰し。**再現手順を書けるものだけ**を挙げる。「バグかもしれない」は挙げない。

**既存資産の再実装**。このリポジトリに既にある関数・スクリプト・型を、知らずに書き直していないか。特にスクリプト群（`scripts/`）は似た処理が増えやすい。

**過剰な抽象**。使用箇所が一つしかない抽象、将来の要求に備えた設定項目、実際には一種類しか通らない分岐。このプロジェクトは段階的に作っているので、**まだ来ていない要求に備えた構造は削るべきものとして扱う。**

**テストが何を保証しているか**。テストが実装をなぞっているだけで、壊れても落ちない形になっていないか。モックが厚すぎて実際の経路を通っていないか。

**スクリプトの失敗の扱い**。`scripts/` のスクリプトは検査系が多い。検査が失敗したときに正しく非ゼロで終了するか。エラーを握り潰して 0 を返すと、検査が通ったことになってしまう。これは検査基盤にとって致命的なので、他より厳しく見る。

## 見ないこと

- 命名やフォーマットの好み（lint と formatter の仕事）
- パフォーマンス（このプロジェクトの規模では問題にならない。実測で問題が出てから考える）
- 網羅的なエッジケースの列挙

## 報告するときの注意

**失敗シナリオを書くこと。** 「どういう入力・状態のときに、何が起きるか」。これが書けない指摘は、たいてい思い込みだ。書こうとして書けなかったなら、その指摘は落とす。

指摘は少なくてよい。この観点で3件以上挙がるなら、たぶん範囲を広げすぎている。
