# 観点: フェーズスコープ

## 何を守っているのか

このプロジェクトは段階を切って進めている。

- **Phase 1** — AI に書かせる Harness。契約・検査・修正ループを作る
- **Phase 2** — 人間がオーサリングする環境。人間が deck 契約を書き、実装は AI が生成する

Phase 1 のランタイムのスコープは、`Deck` / `Slide` / `Fragment`、固定キャンバスのスケーリング、URL による位置同期まで。**スピーカーノートの表示、PDF 出力、発表者ビューは Phase 1 のスコープ外**で、`notes` はデータとして受け取るだけ。レイアウトの追加をどう扱うかは `DESIGN.md` の Global Constraints が持つ（[DR-0010](../../../../docs/decisions/0010-three-layouts.md)）。

段階を切るのは、検査基盤の設計ミスを早く見つけるためだ。スコープが溶けると、土台の妥当性を確かめる前に量が増え、設計ミスの発見が遅れる。

## 見るべきこと

**スコープ外の混入**。Phase 1 の Issue に、Phase 1.5 以降のものが入っていないか。追加された layout variant、ノート表示 UI、印刷 CSS、発表者ビュー、MCP サーバー、テーマ差し替え機構など。「ついでに入れた」ものが最も多い。

**Phase 2 を塞ぐ設計**。Phase 2 では人間が deck 契約（Markdown + frontmatter）を書き、`keyMessage` 必須 / `body` 任意という線引きで AI の裁量が決まる。この前提を壊す設計が入っていないか。例えば deck 契約を人間が書けない形式へ寄せる、`body` が無い場合の経路を削る、契約と実装を人間が二重管理する形にする、など。

**Issue の非スコープ節との照合**。各 Issue には「非スコープ」が書かれている。差分がそこへ踏み込んでいないか。踏み込む必要が本当にあったなら、Issue を分けるか、DR を立てるべき状況だ。

**逆方向も見る**。Issue の「完了条件」に対して、差分が足りていないことがある。チェックボックスのうち満たされていないものがあれば挙げる。ただし PR が意図的に部分実装であることもあるので、PR の説明を先に読む。

## 報告するときの注意

スコープ外の混入は、それ自体が悪いわけではない。**小さくて明らかに有益なら、指摘した上で「このまま入れてよいと思う」と書いてよい。** 判断は人がする。機械的に「スコープ外だから削れ」と言うと、レビューが儀式になる。

一方で、スコープ外のものが**設計判断を伴う**場合（新しい layout を足す、契約の形を変える）は、DR を立てるべき状況として扱う。この場合は明確に指摘する。
