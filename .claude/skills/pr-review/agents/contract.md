# 観点: 設計契約との整合

## 何を守っているのか

このリポジトリは設計情報を「正本（source of truth）」として一箇所に置き、そこから生成・参照する構造を取っている。この構造が壊れる典型は、**同じ情報が二箇所に書かれること**だ。二箇所あると片方だけが更新され、AI がどちらを信じるべきか分からなくなる。Design Harness が Skill に対して "Do not copy its design data into this Skill" と明記しているのは、この一点のためだ。

正本の対応はこうなっている。

| 内容 | 正本 |
|---|---|
| 設計方針、Do / Don't、衝突時の優先順位 | `DESIGN.md` |
| 色・余白・タイポ・影・キャンバス寸法 | `design/tokens.json` |
| レイアウトの variant と選択基準 | `design/layouts/` |
| 使ってよい部品と props | `design/components/` |
| 発表ごとの構成 | `design/decks/` |
| 検査ルール | `design/rules.json` |
| レイアウト実装のクラス名 | `design/layout.css` |
| 生成物 | `design/theme.css`（`tokens.json` から生成。直接編集しない） |

## 見るべきこと

**設計データの複製**。差分の中に、正本にある値が別の場所へ書き写されていないか。特に危ないのは Skill ファイル、README、ドキュメント、テストのフィクスチャ、そして実装コードのハードコード。値そのものだけでなく、「トークンの一覧」「layout の一覧」のような**構造の複製**も同じ問題を起こす。参照とリンクで済むものが複製されていないか見る。

**契約と実装の乖離**。契約に書かれた layout / component / クラス名が、実装で実際に使われているか。逆に、実装にあるが契約に無いものが増えていないか。`design/layout.css` のクラス名と、契約側が参照するクラス名がずれていないか。

**生成物の手編集**。`design/theme.css` のような生成物が直接編集されていないか。編集されていれば、次回の生成で失われる。

**契約の自己矛盾**。新しく追加された契約が、既存の契約と衝突していないか。例えば layout が要求する余白と、tokens に無い値を参照していないか。

**Schema の追従漏れ**。契約ファイルの構造を変えたのに、対応する `design/schemas/*.json` が更新されていないことがある。これは検証をすり抜ける。

## 報告するときの注意

「複製されている」と言うなら、**両方の場所を示すこと**。片方だけ挙げても、読む側が確認できない。

値が似ているだけで複製とは限らない。偶然一致することもある。実際にファイルを読んで、正本を参照すれば済むものかどうかを確かめてから書く。

契約がまだ存在しない段階（このプロジェクトは段階的に作っている）では、「契約が無いこと」自体は問題ではない。該当する Issue でこれから作るものかどうかを、PR の説明や関連 Issue から判断する。
