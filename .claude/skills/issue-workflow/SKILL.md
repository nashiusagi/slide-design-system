# Issue から PR 完了までの開発フロー

## このスキルが解こうとしている問題

実装そのものより、その前後が毎回抜ける。ブランチ名がばらつく、PR が実装の後追いで作られて途中経過が見えない、レビューを受けたのに指摘が半分だけ反映される、PR 本文が着手時のまま実態と食い違う、終わったのかどうかが Issue からも PR からも分からない。

どれも小さいが、積み重なると「何がどこまで終わったか」を人が読み取れなくなる。このスキルは**流れの順番と、各段階で残す痕跡**を固定する。実装の中身は Issue と正本（`DESIGN.md` / `design/`）が決めることで、ここでは扱わない。

レビューは `pr-review` スキルが持っている。ここでその仕事を再実装しない。**このスキルはレビューを呼び出し、その結果をコードへ反映し、どう抜けるかを決める役**に徹する。

このフローを固定した理由と、他の選び方を却下した理由は [DR-0025](../../../docs/decisions/0025-issue-driven-development-flow.md) にある。手順5の抜け方だけは [DR-0052](../../../docs/decisions/0052-review-loop-third-exit.md) が置き換えている。手順を変えるときは先にそちらを読むこと。

## 番号の書き方

この文書では Issue 番号と PR 番号を区別する。`<Issue番号>` と `<PR番号>` は別の値で、取り違えると参照先が存在しないパスになる。

- `<Issue番号>` — 引数として受け取る番号。ブランチ名と `Closes` に使う
- `<PR番号>` — 手順1で PR を作ったときに発番される番号。`gh pr` 系のコマンドと `docs/reviews/pr-<PR番号>.md` に使う

## 手順

### 0. Issue を読む

```bash
gh issue view <Issue番号> --json number,title,body,labels,url
```

タイトル・本文・完了条件を読む。**完了条件（チェックリスト）があれば、それが実装のスコープになる。** 書かれていないことを勝手に足さない。

読んで曖昧な点があれば、この段階で人に聞く。ブランチを切った後に前提が崩れるのが一番高くつく。

### 1. ブランチ → 空コミット → push → Draft PR

ブランチ名は `feature/<Issue番号>_<内容>` にする。`<内容>` は Issue タイトルから起こした短い英小文字スラグ（ハイフン区切り）。

```bash
git checkout main && git pull
git checkout -b feature/<Issue番号>_<slug>
git commit --allow-empty -m "chore: <何を始めるか>

Refs #<Issue番号>"
git push -u origin feature/<Issue番号>_<slug>
gh pr create --draft --title "<Issue タイトル>" --body "Closes #<Issue番号>

<何をやるかの一行>

作業中。"
```

作成された PR の番号を控える。以降の `<PR番号>` はこれを指す。

**空コミットで先に PR を立てるのは、着手を可視化するため。** 実装が終わってから PR を作ると、走っている最中は誰にも見えない。本文の `Closes #<Issue番号>` はマージ時の Issue 自動クローズに必要なので必ず入れる。

Draft なのは、この時点ではレビュー対象になっていないから。人の目を無駄に呼ばない。

### 2. 実装 → Ready 化

Issue のスコープに沿って実装し、意味のある単位でコミットして push する。

このリポジトリで実装するなら、正本（`DESIGN.md` / `design/`）に従う。設計データを Skill やドキュメントへ複製しない。

実装しながら判断したことは、次の基準で行き先を決める。**後から別の実装が同じ判断を必要とするなら、決定記録（`docs/decisions/`）を起こす。** 命名規約、閾値、抽象の切り方、ライブラリ選定はここに入る。この PR に閉じた選択なら PR 本文の「なぜこうしたか」に書く。迷ったら DR に倒す。PR 本文はマージ後に読まれないが、DR は残る。

Draft を外すのは、**Issue の完了条件をすべて満たし、追加・変更する予定のファイルがすべて差分に入ったとき**。「動くかどうか」を基準にしない。ドキュメントや Skill だけの差分では動かすものが無く、基準にならないからだ。

#### Ready 化の前に読み返す

**Ready にする前に、自分の差分を読み返して結果を PR へコメントする。** 書式は `references/self-check.md`。根拠は [DR-0057](../../../docs/decisions/0057-self-check-before-ready.md)。

```bash
gh pr comment <PR番号> --body-file <スクラッチ領域のファイル>
```

狙うのは、**機械では判定できないのにレビューで繰り返し出ている形**だ——記録されない判断、実装と食い違う説明文、同じ判定に到達できない基準、スコープ外の混入、不変条件を示さないテストタイトル、統合パスを通していない完了条件、着手時のままの PR 本文。どのカテゴリを見るかは書式が持つ。

**この形が繰り返すのはタイミングの問題だ。** 実装が終わってから PR 本文を整え、DR を書くかどうかを考える。そのときにはもう、実装中に下した判断の大半が「当たり前のこと」に見えていて、記録に値すると思えない。だから書かれない。読み返す段を、レビューの前に置く。

**書くのは「確認した」ではなく、後から突き合わせられる材料だ。** 下した判断とその行き先、説明文とそれが説明している実装の在り処、テストタイトルとその不変条件。読み手が自分で開いて確かめられる形にする。主張だけを残すなら、この段は無いのと同じになる。

**この段で潰す想定のものも、`pr-review` の観点からは外さない。** セルフチェックが見逃したものを誰も拾わなくなるからだ。節約したいのは周の数であって、見る目の数ではない。二重に見ることは無駄ではない——**書いた本人が見落とす形を集めた項目なので、本人のチェックが最も弱いのがまさにこの領域だ。**

```bash
gh pr ready <PR番号>
```

**Ready 化がレビューの開始線になる。** ここを越えるまでレビューを呼ばない。半端な差分をレビューさせると、指摘のほとんどが「まだ書いてないだけ」で埋まる。

### 3. レビュー

`pr-review` スキルを `<PR番号>` 付きで呼ぶ。レビューの観点も記録先も、あちらが持っている。ここでは結果だけ受け取る。

**呼ぶ直前に、その時点のコミットを控える。**

```bash
git rev-parse HEAD
```

次の周は、この地点からの差分が対象になる。控えておかないと、2周目で起点を `git log` から推測することになり、同じ周の修正コミットを丸ごと差分から落としかねない。

結果には `blocker` / `should` / `consider` の重要度が付いている。レビュー全文のファイルパスは `pr-review` が返すので、それを控えて以降の参照に使う。

**毎周、観点を絞らないよう伝える。** 収束に使えるのは絞られなかった周だけで（手順5）、どの周が収束になるかは回してみるまで決まらない。伝えないと、再レビューでは絞られうる。

**それでも、収束の判定は伝えた事実ではなくレビュー記録で行う**（手順5）。`pr-review` はこの要望を受け取る項目を持つが（あちらの手順1）、伝えたことと実際に立ったことは別だ。判定の入力を申告側に戻さない。

**2周目以降を呼ぶときは、同一 PR の再レビューであることを伝え、前周のコミットと、前周で指摘が出た観点を渡す。** `pr-review` はこれを受けて、対象差分・立てるレビュアー・記録の仕方を切り替える（`pr-review/SKILL.md` の手順1）。

これを受けて `pr-review` が何を変えるか——対象を増分に絞る、観点を絞る、指摘ログの計上を抑える、自身の出力を対象から外す——は、あちらの手順1・2・4・6が持っている。**ここに書き写さないのは、その判断の基準だ。** 呼ぶ側にも同じ条件分岐を置くと、片方だけ変更されたときに食い違いが検出できなくなる。**あちらの入力項目や記録先が「どこにあるか」を指すのは、書き写しに当たらない**——基準の中身ではなく所在を参照しているだけで、あちらが動けば参照が外れて気づける。ここでの責務は、判断に必要な材料を渡すことだけだ。

### 4. 指摘を反映する

- **`blocker`** — 直す
- **`should`** — 直す。直さないと決めたなら理由を残し、その PR は**打ち切り**として扱う（手順5の残指摘コメントを出す）
- **`consider`** — 判断する。直さないなら理由を残す。見送っても打ち切りにはならない

直したらコミットして push する。**直さないと決めた指摘は、黙って飛ばさない。** 何を見送ったかが残っていないと、次の周で同じ指摘が出たときに判断をやり直すことになる。見送りの理由は PR 本文かコメントに書く。

**レビュー成果物は実装の修正と混ぜず、別のコミットにする。** 何がレビューの記録で何が修正なのかが、後から差分を読む人に分かる。

指摘が根本的な作り直しを示している場合は、パッチを重ねずに一度戻って作り直す方が早いことがある。周回数を消化することが目的ではない。

### 5. 3と4を繰り返す

**上限は3周。** 収束するか、上限に達するまで、3と4を繰り返す。以下でこの節が「上限」と呼ぶのはこの値で、周の数え方もここが決める。

**レビューが1件も結果を返さなかった回は、周として数えずにやり直す。** 数えないのは、**立てた観点のどれ一つとして結果が返らなかった**ときだけだ（レビュアーが全滅した、外部の制約で走らせられない）。一部の観点が返したなら、返った分がその周の結果になる——残りが落ちたことを理由に、返ってきた指摘ごと無かったことにはしない。**ただしその周は収束には使えない**（下の「1. 収束」）。観点が絞られた周も同じ扱いになる。

**やり直しは同じ周について2回まで。** 3度目も1件も返らなければ、その回を1周として数える。数えた以上は上限が進むが、**指摘の有無を判定できていない**ので収束には使えない。この値を選んだ規準と、上限を置く理由は [DR-0052](../../../docs/decisions/0052-review-loop-third-exit.md) の決定4 と、その理由にある。

**何回やり直したかは、どの抜け方で終わっても書く**（この節の末尾）。やり直しはどの周でも起こりうるので、記録先を1つの書式に限ると、そこを通らずに終わった PR では上限を守ったことが残らない。

抜け方は3つある。上から順に判定する。

**1. 収束 — 指摘ゼロのレビューを1周通った。** 何周目でもよい。直した結果として未対応がゼロになった状態は、まだ収束ではない。その修正自体は誰にも見られていないからだ。最後の周に出た指摘を直して終わるのは収束ではない。

**収束に使えるのは、観点が絞られずに立ち、そのすべてが結果を返した周だけだ。** 観点が絞られた周も、一部が落ちた周も、返った指摘がその周の結果になり上限も進むが、収束には使えない（[DR-0052](../../../docs/decisions/0052-review-loop-third-exit.md) 決定1）。

**絞られたかどうかは、レビュー記録の「立った観点」で確かめる。** `pr-review` はその周に立った観点を、指摘ゼロだったものも含めて `docs/reviews/pr-<PR番号>.md` へ残す（[DR-0053](../../../docs/decisions/0053-review-coverage-recorded.md)）。絞らないよう伝えることはできるが（手順3）、伝えた事実は判定の入力にならない。**確かめられないなら収束にしない**——確認未了へ倒す。記録が無い、あるいは立った観点が絞られている周を収束と呼べるなら、判定は書き手の申告に戻る。**絞られていない状態が何観点かは、`pr-review` の観点表（あちらの手順4）で確かめる。** ここには書き写さない——数が変わったときに片方だけ古くなる。

ここでの「指摘ゼロ」は `blocker` / `should` がゼロで、かつ `consider` を直していないことを指す。**`consider` を理由つきで見送った周は収束を妨げない**——見送りは差分を変えないので、その周が見たものが最新のままだ。`consider` を直したなら、その修正は誰も見ていないので収束ではない。

収束していなければ、上限に達するまで繰り返す。**上限に達したら、残っている未対応の `blocker` / `should` を数える。** 数えるのは「直していない指摘」だけで、差分の性質（検査を含むか、実装だけか）は見ない。

**2. 確認未了 — 上限を終え、未対応の `blocker` / `should` がゼロ。** 直すべきものは全部直したが、最後の修正を見たレビューの周を回せていない。やり直してもレビューを走らせられないまま上限に達した場合もここに入る。

**3. 打ち切り — 上限を終えてもなお未対応の `blocker` / `should` が残っている。** または `should` を見送ると判断した。上限まで回して収束しないなら、それは実装の問題ではなく前提の問題であることが多い。粘るより人に渡す方が速い。

確認未了と打ち切りでは、次に人がやることが違う。確認未了は「見てほしい」、打ち切りは「判断してほしい」。**どちらも完了報告は出さない**（手順7）。

**確認未了で抜けた場合は、未確認の範囲を PR にコメントする。**

```bash
gh pr comment <PR番号> --body "<未確認の範囲>"
```

書式は `references/unconfirmed-comment.md`。**どのコミットからどのコミットまでが未確認かを名指しする。** 範囲が無いと、読み手は差分全体を見直すことになり、レビューを回した意味が消える。レビューを走らせられなかった回があるなら、そのこともここへ書く。

**打ち切りで抜けた場合は、残った指摘を PR にコメントする。**

```bash
gh pr comment <PR番号> --body "<残指摘のまとめ>"
```

書式は `references/pending-comment.md`。何が残っていて、なぜ今回直さないのかを書く。レビュー全文のパスを添えると読み手が追える。

**3つのコメント（完了報告・未確認・残指摘）のどれにも、最後の周に立った観点と、やり直した回数（無ければ「無し」）を書く。** 抜け方を決めた条件——観点が絞られなかったか、やり直しの上限を守ったか——を、読み手が確かめられるようにするためだ。**観点は、レビュー記録の「立った観点」欄をそのまま写す。** 呼ぶときに何を頼んだかでも、指摘を返した観点だけでもない。収束で抜けるなら、それが絞られていないことをどう確かめたかも添える。

**3つのコメントのどれにも、指摘の対応結果を一覧で入れる。** 各 `blocker` / `should` を直したか見送ったか、そして**見送った `consider`** を、同じ一覧に並べる。抜け方は `blocker` / `should` の数え方ひとつで決まるので、それが残らなければ「未対応はゼロ」は書き手の申告にしかならない。`consider` は抜け方を左右しないが、見送ったものが残っていないと、次に読む人は「見落とし」と「見送り」を区別できない。

### 6. PR 本文を整える

着手時の本文は「これからやること」で書かれている。最終的な差分に合わせて書き直す。

```bash
gh pr diff <PR番号> --stat
gh pr edit <PR番号> --body "$(cat <<'BODY'
<本文>
BODY
)"
```

書式は `references/pr-body.md`。`Closes #<Issue番号>` は消さない。

本文を一時ファイルへ書いてから `--body-file` で渡してもよいが、その場合はリポジトリの外（スクラッチ領域）に置く。リポジトリ直下に置くと、次のコミットで差分に紛れ込む。

**ここを飛ばすと、マージ後に残るのは実態と違う説明だけになる。** PR 本文はコミットログより読まれる。

### 7. 完了を報告する

**収束して抜けた場合のみ**、完了コメントを出す。確認未了なら手順5の未確認コメント、打ち切りなら残指摘コメントが最終報告になる。終わっていないものに完了報告を重ねると、通知だけを見た人が完了扱いでマージ判断に入る。

```bash
gh pr comment <PR番号> --body "<完了報告>"
```

書式は `references/completion-comment.md`。実装が終わったこと、レビューを何周したこと、残っている判断があればそれを書く。

最後に、人が判断すべきこと（マージの可否、残指摘の扱い）を会話へ短く出す。**マージはしない。**

## やらないこと

- **マージしない。** PR を出して報告するところまで。マージは人が決める
- **レビューの中身を自前で作らない。** `pr-review` に委譲する
- **Issue に書かれていないことを実装しない。** 気づいたことは Issue かコメントで提案する
- **打ち切りと確認未了を黙って行わない。** 残指摘も、未確認の範囲も、必ず PR に残す
- **未対応がゼロのことを「収束」と呼ばない。** 最後の修正を誰も見ていないなら確認未了であり、完了報告は出さない
