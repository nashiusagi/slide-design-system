# Issue から PR 完了までの開発フロー

## このスキルが解こうとしている問題

実装そのものより、その前後が毎回抜ける。ブランチ名がばらつく、PR が実装の後追いで作られて途中経過が見えない、レビューを受けたのに指摘が半分だけ反映される、PR 本文が着手時のまま実態と食い違う、終わったのかどうかが Issue からも PR からも分からない。

どれも小さいが、積み重なると「何がどこまで終わったか」を人が読み取れなくなる。このスキルは**流れの順番と、各段階で残す痕跡**を固定する。実装の中身は Issue と正本（`DESIGN.md` / `design/`）が決めることで、ここでは扱わない。

レビューは `pr-review` スキルが持っている。ここでその仕事を再実装しない。**このスキルはレビューを呼び出し、その結果をコードへ反映し、いつ打ち切るかを決める役**に徹する。

このフローを固定した理由と、他の選び方を却下した理由は [DR-0025](../../../docs/decisions/0025-issue-driven-development-flow.md) にある。手順を変えるときは先にそちらを読むこと。

## 番号の書き方

この文書では Issue 番号と PR 番号を区別する。`<Issue番号>` と `<PR番号>` は別の値で、取り違えると参照先が存在しないパスになる。

- `<Issue番号>` — 引数として受け取る番号。ブランチ名と `Closes` に使う
- `<PR番号>` — 手順1で PR を作ったときに発番される番号。`gh pr` 系のコマンドと `docs/reviews/pr-<PR番号>.md` に使う

## 手順

### 0. Issue を読む

```bash
gh issue view <Issue番号> --json number,title,body,labels,url
```

タイトル・本文・完了条件を読む。**完了条件（チェックリスト）があれば、それが実装のスコープになる。** 書かれていないことを勝手に足さない。

読んで曖昧な点があれば、この段階で人に聞く。ブランチを切った後に前提が崩れるのが一番高くつく。

### 1. ブランチ → 空コミット → push → Draft PR

ブランチ名は `feature/<Issue番号>_<内容>` にする。`<内容>` は Issue タイトルから起こした短い英小文字スラグ（ハイフン区切り）。

```bash
git checkout main && git pull
git checkout -b feature/<Issue番号>_<slug>
git commit --allow-empty -m "chore: <何を始めるか>

Refs #<Issue番号>"
git push -u origin feature/<Issue番号>_<slug>
gh pr create --draft --title "<Issue タイトル>" --body "Closes #<Issue番号>

<何をやるかの一行>

作業中。"
```

作成された PR の番号を控える。以降の `<PR番号>` はこれを指す。

**空コミットで先に PR を立てるのは、着手を可視化するため。** 実装が終わってから PR を作ると、走っている最中は誰にも見えない。本文の `Closes #<Issue番号>` はマージ時の Issue 自動クローズに必要なので必ず入れる。

Draft なのは、この時点ではレビュー対象になっていないから。人の目を無駄に呼ばない。

### 2. 実装 → Ready 化

Issue のスコープに沿って実装し、意味のある単位でコミットして push する。

このリポジトリで実装するなら、正本（`DESIGN.md` / `design/`）に従う。設計データを Skill やドキュメントへ複製しない。

実装しながら判断したことは、次の基準で行き先を決める。**後から別の実装が同じ判断を必要とするなら、決定記録（`docs/decisions/`）を起こす。** 命名規約、閾値、抽象の切り方、ライブラリ選定はここに入る。この PR に閉じた選択なら PR 本文の「なぜこうしたか」に書く。迷ったら DR に倒す。PR 本文はマージ後に読まれないが、DR は残る。

Draft を外すのは、**Issue の完了条件をすべて満たし、追加・変更する予定のファイルがすべて差分に入ったとき**。「動くかどうか」を基準にしない。ドキュメントや Skill だけの差分では動かすものが無く、基準にならないからだ。

```bash
gh pr ready <PR番号>
```

**Ready 化がレビューの開始線になる。** ここを越えるまでレビューを呼ばない。半端な差分をレビューさせると、指摘のほとんどが「まだ書いてないだけ」で埋まる。

### 3. レビュー

`pr-review` スキルを `<PR番号>` 付きで呼ぶ。レビューの観点も記録先も、あちらが持っている。ここでは結果だけ受け取る。

結果には `blocker` / `should` / `consider` の重要度が付いている。レビュー全文のファイルパスは `pr-review` が返すので、それを控えて以降の参照に使う。

**2周目以降を呼ぶときは、同一 PR の再レビューであることを伝える。** `pr-review` の指摘ログ（`docs/review_log.md`）は「1つのカテゴリは1つの PR につき1回だけ数える」規約で、その数がルール化の判断材料になっている。同じ PR で3回呼んで3回数えると、1つの PR だけでルール化候補の閾値に届いてしまう。2周目以降はレビュー全文のファイルだけを更新させ、指摘ログは触らせない。

**2周目以降は、対象と観点の両方を絞る。** `gh pr diff` は main からの全差分を返すので、そのまま渡すと毎周フルスキャンになり、既に直した箇所を読み直す時間が積み上がる。2周目以降は前周をレビューした時点のコミットからの差分（`git diff <前周の HEAD>..HEAD`）を対象にし、前周のレビュー全文を一緒に渡す。「何を指摘され、それがどう直ったか」が見えると、同じ指摘の再生産が減る。

観点は、前周で指摘が出た観点に絞ってよい。指摘ゼロだった観点は、その PR がその観点の守備範囲に触れていないことが多く、2周目で状況が変わる要素が無い。

**ただし実装コードを含む差分では絞らない。** 修正が別の観点を壊す回帰は、絞った観点からは見えない。絞ってよいのは、差分がドキュメント・契約・Skill に閉じていて、回帰の射程が狭いときだけだ。

**前の周のレビュー成果物はレビュー対象外として扱う。** `docs/reviews/` と `docs/review_log.md` は `pr-review` 自身の出力なので、これをレビューさせると、レビュー結果をレビューして直す作業が際限なく伸びる。

### 4. 指摘を反映する

- **`blocker`** — 直す
- **`should`** — 直す。直さないと決めたなら理由を残し、その PR は**打ち切り**として扱う（手順5の残指摘コメントを出す）
- **`consider`** — 判断する。直さないなら理由を残す。見送っても打ち切りにはならない

直したらコミットして push する。**直さないと決めた指摘は、黙って飛ばさない。** 何を見送ったかが残っていないと、次の周で同じ指摘が出たときに判断をやり直すことになる。見送りの理由は PR 本文かコメントに書く。

**レビュー成果物は実装の修正と混ぜず、別のコミットにする。** 何がレビューの記録で何が修正なのかが、後から差分を読む人に分かる。

指摘が根本的な作り直しを示している場合は、パッチを重ねずに一度戻って作り直す方が早いことがある。周回数を消化することが目的ではない。

### 5. 3と4を繰り返す

次のどちらかで抜ける。

- **収束** — 未対応の `blocker` と `should` がゼロになった
- **打ち切り** — 3周を終えた、または `should` を見送ると判断した

3周で収束しないなら、それは実装の問題ではなく前提の問題であることが多い。粘るより人に渡す方が速い。

**打ち切りで抜けた場合は、残った指摘を PR にコメントする。**

```bash
gh pr comment <PR番号> --body "<残指摘のまとめ>"
```

書式は `references/pending-comment.md`。何が残っていて、なぜ今回直さないのかを書く。レビュー全文のパスを添えると読み手が追える。

### 6. PR 本文を整える

着手時の本文は「これからやること」で書かれている。最終的な差分に合わせて書き直す。

```bash
gh pr diff <PR番号> --stat
gh pr edit <PR番号> --body "$(cat <<'BODY'
<本文>
BODY
)"
```

書式は `references/pr-body.md`。`Closes #<Issue番号>` は消さない。

本文を一時ファイルへ書いてから `--body-file` で渡してもよいが、その場合はリポジトリの外（スクラッチ領域）に置く。リポジトリ直下に置くと、次のコミットで差分に紛れ込む。

**ここを飛ばすと、マージ後に残るのは実態と違う説明だけになる。** PR 本文はコミットログより読まれる。

### 7. 完了を報告する

**収束して抜けた場合のみ**、完了コメントを出す。打ち切りで抜けた場合は、手順5の残指摘コメントが最終報告になる。終わっていないものに完了報告を重ねると、通知だけを見た人が完了扱いでマージ判断に入る。

```bash
gh pr comment <PR番号> --body "<完了報告>"
```

書式は `references/completion-comment.md`。実装が終わったこと、レビューを何周したこと、残っている判断があればそれを書く。

最後に、人が判断すべきこと（マージの可否、残指摘の扱い）を会話へ短く出す。**マージはしない。**

## やらないこと

- **マージしない。** PR を出して報告するところまで。マージは人が決める
- **レビューの中身を自前で作らない。** `pr-review` に委譲する
- **Issue に書かれていないことを実装しない。** 気づいたことは Issue かコメントで提案する
- **打ち切りを黙って行わない。** 残指摘は必ず PR に残す
