# 未確認コメントの書式（確認未了で抜けたとき）

レビューの上限周回を終え、**未対応の `blocker` / `should` はゼロだが、最後の修正を見たレビューの周を回せていない**場合に、PR へコメントする（[DR-0052](../../../../docs/decisions/0052-review-loop-third-exit.md)）。上限と周の数え方は `SKILL.md` の手順5が正本で、ここでは数字を持たない。

レビューを実行できなかった回は周として数えない（`SKILL.md` 手順5）。やり直してもなお走らせられないまま上限に達した場合が、この書式の出番のひとつになる。

残指摘が1件でもあるなら、こちらではなく `pending-comment.md` を使う。

```markdown
レビューを <n>周した。未対応の指摘は無いが、**最後の修正を見たレビューの周を回せていない**。

最後の周: <立った観点>。やり直し <回数。無ければ「無し」>

## 未確認の範囲

`<起点のコミット>..<HEAD>` — <その範囲で何をしたか。1〜3行>

- `<パス>` — <何を変えたか>
- `<パス>` — <何を変えたか>

<なぜその周を回せなかったか。上限に達した／レビューを実行できなかった、のどちらかと、その事情>

## 対応済みの指摘

<各 `blocker` / `should` を1行ずつ。直したのか見送ったのかが、読み手にも同じ数え方で追える形で書く>

- **[blocker] <指摘の要約>** — 直した（<どう直したか>）
- **[should] <指摘の要約>** — 直した（<どう直したか>）
- **[consider] <指摘の要約>** — 見送った（<理由>）

## 見立て

<残っている危険についての推測。指摘の収束の傾向（何件 → 何件 → 何件）を添えると、読み手が警戒度を決められる>

レビュー全文: `<pr-review が返したレビューファイルのパス>`
```

## 書くときの判断

**「未確認である」ことを先に書く。** 読み手が最初に知るべきは、この PR が完了報告を出していない理由だ。対応済みの指摘を並べてから最後に書くと、通知の1行目だけを見た人が完了扱いで読む。

**やり直した回数を書く。** レビューが返らずにやり直した回は周として数えないが、数えないままにできる回数には上限がある（`SKILL.md` 手順5）。何回やり直したかが残らなければ、その上限を守ったことは書き手の申告にしかならない。3つの書式すべてが同じ項目を持つのはそのためだ。立った観点も同じ扱いで、返ってきたレビュー結果に現れたものを書く（完了報告だけは、絞られていないことを確かめた場所も添える。収束の判定にだけ絞り状態が効くからだ）。

**未確認の範囲はコミットで示す。** 「最後の修正」という言い方では、読み手がどこを見ればよいか決められない。`git log --oneline <起点>..HEAD` で出る範囲をそのまま書けばよい。

**完了報告（`completion-comment.md`）を重ねない。** 確認未了の場合は、このコメントが最終報告になる。

**対応結果の一覧を省かない。** 確認未了と打ち切りの分かれ目は「未対応がゼロか」だけで、その数え方が残らなければ、抜け方の選択は書き手の申告にしかならない。`consider` は抜け方を左右しないが、見送ったものは同じ一覧に並べる——次の人が「見落としたのか、見送ったのか」を判別できる。

**「直っているはず」と書かない。** 確かめていないことがこのコメントの主題であって、書き手の見込みは判断材料にならない。書くなら「見立て」の節で、根拠（指摘の減り方、残る観点）と一緒に書く。
