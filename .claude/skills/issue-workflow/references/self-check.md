# Ready 化前のセルフチェックの書式（#46 / DR-0057）

Ready 化の直前に読み返し、結果を PR へコメントする。**書くのは「確認した」ではなく、読み手が後から突き合わせられる材料だ。**

## なぜ主張では足りないか

この段が狙うのは、機械で判定できない8つのカテゴリ（下表）だ。どれもレビュアーが毎回見つけている——つまり**読み返せば分かる**。分からないのではなく、実装が終わった時点では自分の判断が「当たり前のこと」に見えていて、記録に値すると思えないだけだ。

だから「読み返しました」と書いても何も変わらない。**読み返した結果として何が見つかり、どこへ行ったか**を、読み手が検証できる形で残す。このリポジトリは一貫して申告を判定の入力にしない（[DR-0052](../../../../docs/decisions/0052-review-loop-third-exit.md) / [DR-0053](../../../../docs/decisions/0053-review-coverage-recorded.md)）。ここも同じ扱いにする。

## 書式

```markdown
## Ready 化前のセルフチェック

### 実装中に下した判断

<この PR で下した判断を、行き先とともに列挙する。1つも無いなら「無し」と書き、
 なぜ無いのかを1行添える——判断を一度もしていない実装は稀だ>

- <判断> → DR-00NN
- <判断> → PR 本文の「なぜこうしたか」
- <判断> → 記録しない（<理由>）

### 説明文と実装の読み合わせ

<この PR で追加・変更した説明文（docstring / DR / README / 契約の $comment）ごとに、
 それが説明している実装の在り処を書く。読み手はその2つを開いて突き合わせられる>

- `<説明文のある場所>` — `<説明している実装の場所>`

### 追加した基準・条件

<この PR が足した判断基準を列挙し、それぞれ「読んだ人が同じ判定に到達するか」を書く。
 到達できないものは数値か列挙へ置き換える。置き換えないと決めたなら、その理由を書く。
 無ければ「無し」>

- <基準> — <到達できる / できないので〜へ置き換えた / 到達できないが置き換えない（理由）>

### Issue のスコープ

- **完了条件**: <Issue の完了条件を**全件**挙げ、それぞれ満たした／満たしていないを書く。未達が無ければ最後に「未達なし」と書く>
- **統合パスを通した確認**: <どのコマンド・どの経路で確かめたか。単体テストだけなら、そう書く>
- **スコープ外を足していないか**: <足したものがあれば、なぜ必要だったかと、どこに記録したか>
- **DR に接続しているか**: <この差分の判断が DR へ繋がっているか。繋がらないものは落としたか、別 Issue に切ったか>

### 追加したテスト

<テストを足したなら、タイトルとその不変条件の対応を書く。壊して落ちることを確かめたなら、
 どう壊したかを書く。足していないなら「無し」と、なぜ要らないかを1行>

- `<テストタイトル>` — <固定している不変条件>

### PR 本文

<**Ready にする時点で、本文を実態に合わせておく。** 「作業中。」のままにしない——
 レビュアーが読むのはこの時点の本文だからだ。手順6 の仕上げはそのうえで行う。
 ここには、本文が何を述べているかを1〜2行で書く>
```

## チェック項目と、対応するカテゴリ

各項目は、繰り返し出ている指摘のカテゴリから起こしている。累計は [`docs/review_log.md`](../../../../docs/review_log.md) が正本で、ここには書き写さない。

| 節 | 捕まえたいカテゴリ |
|---|---|
| 実装中に下した判断 | `decisions/undocumented-decision` |
| 説明文と実装の読み合わせ | `writing/inaccurate-rationale` / `writing/contradictory-instruction` |
| 追加した基準・条件 | `writing/ambiguous-criterion` |
| Issue のスコープ | `phase/out-of-scope-addition` / `phase/completion-criterion-not-verified-e2e` |
| 追加したテスト | `writing/test-title-ambiguous` |
| PR 本文 | `writing/incomplete-pr-description` |

## 書くときの注意

**「無し」と空欄を区別する。** 該当が無い節にも「無し」と書き、理由を添える。空欄は「見ていない」と読まれる。

**見つけたものを直してから書く。** この節は発見の記録であって、未対応の一覧ではない。直さないと決めたなら、その理由をその場に書く。

**判断を「当たり前」で省かない。** ここで一番落ちるのがこれだ。命名の選択、閾値、抽象の切り方、既存コードへ手を入れた範囲——後から別の実装が同じ判断を必要とするなら、それは記録に値する（`SKILL.md` 手順2）。

**説明文の読み合わせは、実際に両方を開いて行う。** 記憶で「合っているはず」と書かない。この形の指摘（`writing/inaccurate-rationale`）が最も多いのは、書いた本人が合っていると思っているからだ。

**とくに「○○という記述が実在する」と書くときは、その文字列で検索して確かめる。** PR #72 のセルフチェックは、存在しない引用符付きの文字列を「実在すること」として挙げ、レビューで4観点に指摘された。

## この段を通した PR の数え方

**`gh pr ready` より前に投稿されたこのコメントがある PR を、通した PR と数える。** 時刻はタイムラインで確かめる。

```bash
gh api repos/{owner}/{repo}/issues/<PR番号>/timeline --jq '.[] | select(.event=="ready_for_review") | .created_at'
gh pr view <PR番号> --comments
```

**中身の下限もある。** 各節に「無し」以外の実体が1つ以上あるか、「無し」に理由が添えてあること。全節が理由なしの「無し」だけのコメントは、通したとは数えない。

通さずに Ready にしたこと自体は止めない。ただし**通していない PR は、効果を測る母数（[DR-0057](../../../../docs/decisions/0057-self-check-before-ready.md) 決定6）に入らない。**
